## SUMMARY
This template defines the canonical structure for all pattern documents in
the DLMS corpus. Patterns capture reusable, named solutions to recurring
design problems within the DLMS and its multi-agent architecture. They
encode collective knowledge in a form that is directly consumable by the
Knowledge Base Agent and surfaced to agents during context curation.

### Additional_Fields

pattern_name:
  name:        pattern_name
  type:        string
  required:    true
  nullable:    false
  position:    immediately after audit_ref
  description: >
    The canonical short name for this pattern. Used as a human-readable
    identifier in cross-references and the Knowledge Base.
  format:      Title Case, 2–5 words
  examples:
    - "Narrow Context Wide Knowledge"
    - "Structural Verification Independence"
    - "Immutable Audit Record"
    - "Context Curator Compression"
  constraints:
    - Unique across the pattern corpus
    - Immutable after first approved version
    - Used in RELATED_PATTERNS cross-references by name, not doc_id

pattern_type:
  name:        pattern_type
  type:        enum
  required:    true
  nullable:    false
  position:    after pattern_name
  values:
    architectural:  Governs how agents, systems, or components are
                    structured and related.
    operational:    Governs how a process or workflow is executed.
    governance:     Governs how decisions, policies, or standards are
                    managed and enforced.
    data:           Governs how information is structured, stored,
                    or transferred.
  constraints:
    - A pattern may belong to only one primary type
    - Immutable after first approved version

maturity:
  name:        maturity
  type:        enum
  required:    true
  nullable:    false
  position:    after pattern_type
  values:
    candidate:  Pattern is proposed and under review. Not yet in
                active use. May be referenced but not relied upon.
    approved:   Pattern has been confirmed through at least one
                verified KNOWN_USE. May be relied upon.
    deprecated: Pattern has been superseded or found to cause more
                problems than it solves. Retained for historical record.
                New documents must not implement deprecated patterns.
  constraints:
    - maturity: approved requires at least one entry in KNOWN_USES
    - maturity: deprecated requires a superseded_by doc_id pointing
      to the replacing pattern, if one exists
    - maturity is updated by SysAdmin directive, not by Author Agent

## REQUIRED_SECTIONS

SUMMARY:
  heading:     ## SUMMARY
  required:    true
  position:    1
  description: >
    A dense, factual statement of the pattern's name, type, the problem
    class it addresses, and its core mechanism.
  constraints:
    - Exactly 2–3 sentences
    - Must name the pattern and its type
    - Must be parseable as a standalone description

PROBLEM:
  heading:     ## PROBLEM
  required:    true
  position:    2
  description: >
    A precise statement of the recurring problem this pattern solves.
    Describes the problem space, not the solution. Explains why the
    problem is non-trivial and what makes it recurring.
  constraints:
    - 2–6 sentences; no solution content
    - Must be recognisable to an agent or designer encountering
      this problem for the first time
    - Ends with a clear statement of what a good solution must achieve

CONTEXT:
  heading:     ## CONTEXT
  required:    true
  position:    3
  description: >
    The conditions under which this pattern applies. Defines the
    system state, agent configuration, or design situation in which
    this pattern is the right choice.
  constraints:
    - Describes when to use this pattern, not how
    - Must specify conditions that distinguish this pattern's context
      from related patterns
    - 2–5 sentences or a structured list

FORCES:
  heading:     ## FORCES
  required:    true
  position:    4
  description: >
    The competing constraints and tensions that the solution must
    balance. Forces are the reason the problem is hard — they pull
    in opposing directions and cannot all be fully satisfied.
  force_schema:
    name:
      type:     string
      required: true
      description: Short name for the force (e.g. Context Economy, Auditability)
    description:
      type:     string
      required: true
      description: What this force demands or constrains.
    tension_with:
      type:     string
      required: false
      description: >
        The name of a force this one pulls against.
        Null if this force has no direct opposing force.
  constraints:
    - Minimum 2 forces
    - At least one tension_with relationship must exist
      (a pattern with no tensions is not a design pattern)
    - Forces are not ranked — the solution balances them; it does
      not simply maximise one

SOLUTION:
  heading:     ## SOLUTION
  required:    true
  position:    5
  description: >
    The reusable solution structure that resolves the forces.
    Describes the arrangement of agents, artefacts, or process steps
    that constitutes the pattern. Specifies the invariants that must
    hold for the pattern to be correctly applied.
  solution_schema:
    mechanism:
      type:     string
      required: true
      description: >
        A concise description of how the pattern works.
        2–5 sentences. Dense. Present tense.
    invariants:
      type:     array of strings
      required: true
      min_items: 1
      description: >
        The conditions that must always be true when this pattern
        is correctly applied. These are what make it the same pattern
        across different instantiations.
    implementation_notes:
      type:     string
      required: false
      description: >
        Practical guidance for applying the pattern in the DLMS
        context. Not normative — this is guidance, not a rule.
  constraints:
    - mechanism must be comprehensible without reading PROBLEM or CONTEXT
    - invariants are the testable definition of the pattern;
      they are what a reviewer checks to confirm correct application

CONSEQUENCES:
  heading:     ## CONSEQUENCES
  required:    true
  position:    6
  description: >
    The results of applying this pattern — both the benefits gained
    and the liabilities accepted. Honest accounting of trade-offs
    so agents and designers can make informed decisions.
  consequence_schema:
    benefits:
      type:     array of strings
      required: true
      min_items: 1
      description: What is gained by applying this pattern.
    liabilities:
      type:     array of strings
      required: true
      min_items: 1
      description: >
        What is accepted or given up. No pattern is purely beneficial.
        A pattern with no liabilities is not fully analysed.
  constraints:
    - Minimum 1 benefit and 1 liability
    - Liabilities must be honest — not minimised or dismissed
    - Liabilities inform when NOT to apply this pattern

KNOWN_USES:
  heading:     ## KNOWN_USES
  required:    true
  position:    7
  description: >
    Documented instances where this pattern has been applied in the
    DLMS. Provides evidence of maturity and guides implementors
    with concrete examples.
  use_schema:
    location:
      type:     string
      required: true
      description: >
        Where in the DLMS this pattern is applied. References an agent
        name, stage, or doc_id.
    description:
      type:     string
      required: true
      description: >
        How the pattern manifests in this location. 1–3 sentences.
    evidence:
      type:     string
      required: false
      description: doc_id of a verification record or artefact that
                   confirms correct application.
  constraints:
    - For maturity: candidate, KNOWN_USES may be empty (state: none yet)
    - For maturity: approved, minimum 1 known use with evidence
    - For maturity: deprecated, known uses are historical; label them
      with "(historical)" in the description

RELATED_PATTERNS:
  heading:     ## RELATED_PATTERNS
  required:    true
  position:    8
  description: >
    Other patterns in the corpus that are meaningfully related —
    either complementary, alternative, or specialised versions.
  relation_schema:
    pattern_name:
      type:     string
      required: true
      description: The pattern_name of the related pattern.
    doc_id:
      type:     string
      required: true
      format:   DLMS-YYYY-NNNN
    relationship:
      type:     enum
      required: true
      values:
        complements:  >
          These patterns work well together and are often applied
          in the same context.
        alternative:  >
          These patterns solve the same problem differently.
          Use one or the other based on context.
        specialises:  >
          This pattern is a specific application of the related pattern.
        generalises:  >
          The related pattern is a specific application of this one.
  constraints:
    - If no related patterns exist, state: "No related patterns yet defined."
    - All doc_ids must exist in the DLMS registry
    - Relationships are declared from this pattern's perspective

CHANGE_LOG:
  heading:     ## CHANGE_LOG
  required:    true
  position:    last
  format:      "- v[version] | [YYYY-MM-DD] | [agent_id] | [change summary]"
  constraints:
    - Newest version first; one entry per version; immutable once written

## OPTIONAL_SECTIONS

NOTES:

  description: Non-normative design rationale or historical context.
  when_to_include: When design decisions benefit from explanation.
  position:    After CHANGE_LOG

COUNTEREXAMPLES:
  heading:     ## COUNTEREXAMPLES
  description: >
    Situations that look like they call for this pattern but do not.
    Helps agents avoid misapplication.
  when_to_include: >
    When the pattern is frequently misapplied or confused with
    a related pattern.
  position:    After NOTES if present, otherwise after CHANGE_LOG

## VALIDATION_RULES

V01:
  rule:     All nine REQUIRED_SECTIONS must be present in prescribed order.
  test:     >
    Sections SUMMARY, PROBLEM, CONTEXT, FORCES, SOLUTION, CONSEQUENCES,
    KNOWN_USES, RELATED_PATTERNS, CHANGE_LOG all present and in sequence.
  checked_by: Template Validator

V02:
  rule:     doc_type must be 'pattern'. pattern_name, pattern_type,
            and maturity must all be present with valid values.
  test:     >
    doc_type == 'pattern' AND pattern_name != null AND
    pattern_type IN [architectural, operational, governance, data] AND
    maturity IN [candidate, approved, deprecated]
  checked_by: Template Validator; Agent Format Validator

V03:
  rule:     retention_class must be RC-permanent for all pattern documents.
  test:     retention_class == 'RC-permanent'
  checked_by: Indexing Verifier

V04:
  rule:     FORCES must contain at least 2 forces. At least one
            tension_with relationship must be declared.
  test:     >
    len(FORCES) >= 2 AND
    count(F where F.tension_with != null) >= 1
  checked_by: Template Validator

V05:
  rule:     SOLUTION must contain a non-null mechanism and at least
            one invariant.
  test:     >
    SOLUTION.mechanism != null AND len(SOLUTION.invariants) >= 1
  checked_by: Template Validator

V06:
  rule:     CONSEQUENCES must contain at least 1 benefit and at least
            1 liability. Neither may be an empty array.
  test:     >
    len(CONSEQUENCES.benefits) >= 1 AND
    len(CONSEQUENCES.liabilities) >= 1
  checked_by: Template Validator

V07:
  rule:     Patterns with maturity: approved must have at least one
            KNOWN_USES entry with a non-null evidence field.
  test:     >
    IF maturity == 'approved' THEN
    len(KNOWN_USES) >= 1 AND
    count(KU where KU.evidence != null) >= 1
  checked_by: Template Validator; Perspective Reviewer (lens-accuracy)

V08:
  rule:     Patterns with maturity: deprecated must have a non-null
            superseded_by field (if a replacement exists) and must
            label all KNOWN_USES entries as historical.
  test:     >
    IF maturity == 'deprecated' THEN
    (superseded_by != null OR no replacement exists) AND
    all KU.description contains '(historical)'
  checked_by: Template Validator

V09:
  rule:     All doc_ids in RELATED_PATTERNS must exist in the DLMS
            registry. relationship must be a valid enum value.
  test:     >
    For all RP: RP.doc_id IN dlms-registry AND
    RP.relationship IN [complements, alternative, specialises, generalises]
  checked_by: Dependency Index Updater; Indexing Verifier

V10:
  rule:     CHANGE_LOG must have one entry per version, newest first,
            in the prescribed format.
  test:     >
    len(CHANGE_LOG entries) == len(version history) AND
    CHANGE_LOG[0].version == current version AND
    all entries match prescribed format.
  checked_by: Storage Verifier; Version Control Agent
