## SUMMARY
This template defines the canonical structure for all specification documents
in the DLMS corpus. Specifications describe what a system component, agent,
service, or artefact must do and be — combining a problem statement,
functional and non-functional requirements, design decisions, and acceptance
criteria into a single authoritative definition that governs implementation
and verification.

### Additional_Fields

spec_type:
  name:        spec_type
  type:        enum
  required:    true
  nullable:    false
  position:    immediately after audit_ref
  values:
    agent:        Specifies the behaviour, context boundaries, inputs,
                  outputs, and constraints of a DLMS agent.
    artefact:     Specifies the structure, schema, and validation rules
                  of a DLMS artefact (file, record, payload).
    service:      Specifies the interface, behaviour, and performance
                  characteristics of a DLMS service or layer.
    process:      Specifies the design of a multi-step process or
                  workflow not fully captured by a procedure document.
    integration:  Specifies how two or more DLMS components interact,
                  including interface contracts and data exchange formats.
  constraints:
    - Immutable after first approved version
    - spec_type: agent specifications are the primary reference for
      Agent Context Boundary Policy enforcement

subject:
  name:        subject
  type:        string
  required:    true
  nullable:    false
  position:    after spec_type
  description: >
    The specific agent, artefact, service, process, or integration
    this specification describes. Unambiguous identifier.
  examples:
    - "agent:context-curator"
    - "artefact:audit-event-payload"
    - "service:context-delivery-layer"
    - "process:bootstrap-review-process"
  constraints:
    - Format follows the agent ID convention for spec_type: agent
    - For other spec_types, use descriptive slug prefixed by type

implementation_status:
  name:        implementation_status
  type:        enum
  required:    true
  nullable:    false
  position:    after subject
  values:
    not-started:   Specification approved but implementation not begun.
    in-progress:   Implementation underway.
    implemented:   Implementation complete; awaiting verification.
    verified:      Implementation verified against acceptance criteria.
    deprecated:    Subject has been retired; spec retained for record.
  constraints:
    - Updated by SysAdmin directive or by the relevant stage verifier
    - implementation_status: verified requires a verification record

## REQUIRED_SECTIONS

SUMMARY:
  heading:     ## SUMMARY
  required:    true
  position:    1
  description: >
    A dense, factual statement of what this specification describes,
    the spec_type, the subject, and its primary responsibility within
    the DLMS.
  constraints:
    - Exactly 2–3 sentences
    - Must name the spec_type and subject
    - Must state the primary responsibility in one clause

SCOPE:
  heading:     ## SCOPE
  required:    true
  position:    2
  description: >
    What this specification covers and what it explicitly excludes.
    Defines the boundary of the subject's responsibilities.
  constraints:
    - At least one 'Covers:' statement
    - At least one 'Excludes:' statement
    - Must state which other specifications or documents govern
      the excluded areas

PROBLEM_STATEMENT:
  heading:     ## PROBLEM_STATEMENT
  required:    true
  position:    3
  description: >
    The problem or need this specification addresses. Establishes
    why the subject exists and what gap it fills in the DLMS.
    Written before the solution — describes the need, not the design.
  constraints:
    - 2–5 sentences
    - No solution content — describe the problem only
    - Must reference the system design principles (1–11) that
      motivate this specification, if applicable

CONTEXT_BOUNDARY:
  heading:     ## CONTEXT_BOUNDARY
  required:    true
  position:    4
  description: >
    For spec_type: agent — the explicit, linter-style context
    boundary definition. The authoritative declaration of what
    this agent reads, writes, and is forbidden from accessing.
    For other spec_types — the information boundary: what inputs
    this component accepts, what outputs it produces, and what
    it must not access or expose.
  required_fields:
    reads:
      type:     array of strings
      description: >
        Explicit list of file paths, artefact types, or data sources
        this subject consumes. Named items only — no categories.
    writes:
      type:     array of strings
      description: >
        Explicit list of file paths or artefact types this subject
        produces. One primary output artefact where possible.
    never:
      type:     array of strings
      description: >
        Explicit list of file paths, artefact types, or data sources
        this subject is forbidden from accessing. If it can reach
        it, it might load it — explicit prohibition prevents this.
    skill_files:
      type:     array of strings or empty array []
      description: >
        Skill files loaded on demand by this subject. Not loaded
        at startup. Loaded only when the specific capability is needed.
  constraints:
    - reads, writes, and never are all required (use [] if empty)
    - skill_files is required (use [] if none)
    - This section is the primary enforcement reference for
      Agent Context Boundary Policy
    - For spec_type: agent, this section is consumed directly by
      the agent instruction authoring process

REQUIREMENTS:
  heading:     ## REQUIREMENTS
  required:    true
  position:    5
  description: >
    The complete set of functional and non-functional requirements
    the subject must satisfy. Requirements are the testable heart
    of the specification.
  subsections:
    functional:
      heading:     ### Functional_Requirements
      description: >
        What the subject must do. Each requirement describes a
        discrete behaviour or capability.
      requirement_schema:
        id:
          type:     string
          format:   FR prefix + two-digit number (FR01, FR02, …)
        priority:
          type:     enum
          values:   [must-have, should-have, nice-to-have]
        requirement:
          type:     string
          description: >
            Declarative statement of a required behaviour.
            Active voice. "The subject must [verb] [object]."
        rationale:
          type:     string
          required: false
          description: Why this requirement exists.
      constraints:
        - Minimum 1 functional requirement
        - must-have requirements are non-negotiable for implementation_status: verified
    non_functional:
      heading:     ### Non_Functional_Requirements
      description: >
        Quality attributes the subject must exhibit: performance,
        reliability, security, maintainability, and context economy.
      requirement_schema:
        id:
          type:     string
          format:   NFR prefix + two-digit number (NFR01, NFR02, …)
        category:
          type:     enum
          values:   [performance, reliability, security,
                     context-economy, maintainability, auditability]
        requirement:
          type:     string
        measurement:
          type:     string
          description: How compliance with this NFR is measured.
      constraints:
        - Minimum 1 non-functional requirement
        - context-economy NFRs are mandatory for spec_type: agent
          (enforces Principles 7 and 9)
        - auditability NFRs are mandatory for all spec types
          (enforces Principle 3)

DESIGN:
  heading:     ## DESIGN
  required:    true
  position:    6
  description: >
    The selected design approach that satisfies the requirements.
    Describes the structure, key decisions, and the patterns applied.
    This is not a free-form essay — it is a structured record of
    design decisions that can be reviewed and traced.
  decision_schema:
    id:
      type:     string
      format:   DD prefix + two-digit number (DD01, DD02, …)
      required: true
    decision:
      type:     string
      required: true
      description: The design choice made.
    rationale:
      type:     string
      required: true
      description: Why this choice was made over alternatives.
    alternatives_considered:
      type:     array of strings
      required: false
      description: Other approaches evaluated and why they were not chosen.
    patterns_applied:
      type:     array of strings
      required: false
      description: >
        Pattern names (from the pattern corpus) applied in this design.
        Referenced by pattern_name, not doc_id.
    constraints_satisfied:
      type:     array of strings
      required: false
      description: >
        Requirement IDs (FR/NFR) this decision addresses.
  constraints:
    - Minimum 1 design decision
    - Every must-have functional requirement must be addressed by
      at least one design decision

ACCEPTANCE_CRITERIA:
  heading:     ## ACCEPTANCE_CRITERIA
  required:    true
  position:    7
  description: >
    The explicit, binary criteria that determine whether an
    implementation of this specification is complete and correct.
    These are the DoD for the implementation — they must exist
    before implementation begins (Principle 11).
  criterion_schema:
    id:
      type:     string
      format:   AC prefix + two-digit number (AC01, AC02, …)
      required: true
    requirement_ref:
      type:     string
      required: true
      description: The FR or NFR id this criterion verifies.
    criterion:
      type:     string
      required: true
      description: >
        Given/When/Then or declarative binary statement.
        Must be independently verifiable.
    verification_method:
      type:     enum
      required: true
      values:   [automated-check, agent-review, audit-trail-inspection,
                 output-comparison, manual-review]
    checked_by:
      type:     string
      required: true
  constraints:
    - Minimum 1 criterion per must-have functional requirement
    - Every AC must reference a valid FR or NFR id
    - Acceptance criteria are immutable once implementation begins
      (changes require a new spec version)

DEPENDENCIES:
  heading:     ## DEPENDENCIES
  required:    true
  position:    8
  description: >
    All DLMS documents, external systems, or components this
    subject depends on to function correctly. Supplements the
    frontmatter dependencies[] field with operational detail.
  dependency_schema:
    doc_id_or_name:
      type:     string
      required: true
      description: doc_id for DLMS documents; descriptive name for external.
    dependency_type:
      type:     enum
      required: true
      values:   [reads-from, writes-to, governed-by, implements,
                 co-depends, invokes]
    description:
      type:     string
      required: true
      description: How this dependency manifests operationally.
    failure_impact:
      type:     enum
      required: true
      values:   [blocking, degraded, negligible]
      description: >
        blocking:   Subject cannot function if this dependency is unavailable.
        degraded:   Subject functions at reduced quality or scope.
        negligible: Subject is unaffected by short-term unavailability.
  constraints:
    - All DLMS doc_id dependencies must also appear in frontmatter
      dependencies[]
    - Circular co-depends are forbidden
    - blocking dependencies are the primary risk surface for this spec

IMPLEMENTATION_NOTES:
  heading:     ## IMPLEMENTATION_NOTES
  required:    true
  position:    9
  description: >
    Guidance for the agent or team implementing this specification.
    Records implementation status, known constraints, and any
    verification records once implementation is complete.
  required_fields:
    implementation_status_ref:
      description: >
        Mirrors the frontmatter implementation_status field.
        Updated here with context (e.g. "In progress as of 2026-03-08").
    known_constraints:
      description: >
        Technical or operational constraints that affect how this
        specification can be implemented. Not requirements — these
        are real-world limits the implementor must work within.
    verification_record_ref:
      description: >
        doc_id of the verification record confirming this specification
        has been implemented correctly. Null until implementation_status:
        verified.
  constraints:
    - All three fields are required; known_constraints may be
      "None identified." if genuinely none exist
    - verification_record_ref must be non-null before
      implementation_status can be set to verified

REVIEW_SCHEDULE:
  heading:     ## REVIEW_SCHEDULE
  required:    true
  position:    10
  description: Maximum review interval and unscheduled review triggers.
  required_fields:
    interval_max:       6 months maximum (Tier 4 document)
    trigger_conditions: Minimum 2 conditions; at least one CI-related.

CHANGE_LOG:
