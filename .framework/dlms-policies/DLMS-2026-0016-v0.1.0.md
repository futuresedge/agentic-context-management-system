## SUMMARY
This policy governs the context boundary of every agent operating within
the DLMS — the explicit, enforced definition of what each agent reads,
writes, and is structurally prohibited from accessing. Every agent must
have an approved specification whose CONTEXT_BOUNDARY section is the
authoritative source for its instruction file. This is a Tier 2 policy
directly enforcing Principles 7 (Context Economy) and 9 (Narrow Context,
Wide Knowledge).

## SCOPE
Applies to: every agent operating in the DLMS pipeline regardless of
stage, role, or invocation frequency; all agent specification documents
(spec_type: agent); all agent instruction files derived from those
specifications; all Context Curator agents that assemble context packages;
the Context Delivery Layer that routes packages to agents.

Excludes: the DLM SysAdmin Agent, whose context boundary is governed
by the SysAdmin Policy and is intentionally system-wide; non-DLMS agents
that receive context packages as consumers but have no write access to
DLMS artefacts (they are recipients, not governed agents).

Bootstrap exception: Wave-1 through Wave-2 documents were produced before
agent specifications existed. Agent context boundaries for bootstrap agents
are declared retroactively in their Wave 4 specifications. Until those
specifications are approved, bootstrap agents operate under the minimal
viable boundary defined by this policy's general rules.

## DEFINITIONS

context package:
  The curated set of documents, artefact references, and structured
  data assembled by a Context Curator and delivered to an agent before
  it begins its task. The context package is the complete and only
  information source an agent receives for a given task invocation.

context boundary:
  The explicit, tripartite declaration of what an agent reads (may
  consume), writes (may produce), and is never permitted to access.
  Defined in the CONTEXT_BOUNDARY section of the agent's specification.

context overload:
  The condition in which an agent receives more context than it needs
  to perform its task, increasing noise, cost, and the risk of
  hallucination or instruction drift.

instruction file:
  The operational agent configuration that governs a specific agent's
  behaviour. For DLMS agents, the instruction file is derived directly
  from the agent's approved specification. The CONTEXT_BOUNDARY section
  of the specification is copied verbatim into the instruction file.

never list:
  The explicit list of file paths, artefact types, and data sources
  that an agent is structurally forbidden from accessing. If a resource
  can be reached by an agent, it might be loaded — the never list
  enforces the prohibition at the specification and instruction level.

skill file:
  A supplementary instruction or capability file loaded on demand by
  an agent when a specific capability is required. Skill files are not
  loaded at agent startup. They are declared in the agent's specification
  and loaded only when the triggering condition is met.

## RULES

### Specification_Requirement

R01:
  rule: >
    Every DLMS agent must have an approved specification document
    (doc_type: specification, spec_type: agent) before it may be
    deployed in a live pipeline stage. No agent may operate without
    an approved specification.
  test: >
    For all active agents A:
    exists S where S.doc_type == 'specification' AND
    S.spec_type == 'agent' AND S.subject == A.agent_id AND
    S.status == 'approved'
  checked_by: Stage Orchestrator (pre-stage agent activation check);
              CI Verifier

R02:
  rule: >
    The CONTEXT_BOUNDARY section of an agent's approved specification
    is the sole authoritative source for that agent's instruction file
    context configuration. No context configuration may be added to
    an instruction file that is not declared in the specification.
  test: >
    For all agents A: A.instruction_file.context_config is a
    strict subset of A.specification.CONTEXT_BOUNDARY.
    Any item in instruction_file.context_config NOT in
    specification.CONTEXT_BOUNDARY is a violation.
  checked_by: Agent Behaviour Analyst; CI Verifier

### Context_Boundary_Declaration

R03:
  rule: >
    Every agent specification must declare all four context boundary
    components: reads, writes, never, and skill_files. No component
    may be absent. An empty component must be declared as an empty
    array [].
  test: >
    For all specifications S where S.spec_type == 'agent':
    S.CONTEXT_BOUNDARY.reads != null AND
    S.CONTEXT_BOUNDARY.writes != null AND
    S.CONTEXT_BOUNDARY.never != null AND
    S.CONTEXT_BOUNDARY.skill_files != null
  checked_by: Template Validator; Agent Format Validator

R04:
  rule: >
    The reads, writes, and never lists must reference named,
    specific file paths or artefact types. Category-level references
    (e.g. "all policy documents") are prohibited. Every item must
    be individually enumerable by the Context Curator.
  test: >
    For all items I in reads, writes, never:
    I is a specific file path, a named artefact type, or a named
    DLMS registry entry — not a category, wildcard, or glob pattern.
  checked_by: Template Validator; Perspective Reviewer (lens-accuracy)

R05:
  rule: >
    No item may appear in both reads and never for the same agent.
    A resource is either accessible or prohibited — it cannot be both.
  test: >
    set(reads) ∩ set(never) == empty set
  checked_by: Template Validator; Agent Format Validator

R06:
  rule: >
    The writes list must contain at most one primary output artefact
    per task invocation. Agents that produce multiple artefact types
    in a single invocation must declare them individually and must
    not produce any artefact not listed in writes.
  test: >
    For all agents A: every artefact A produces during a stage
    execution is declared in A.specification.CONTEXT_BOUNDARY.writes.
    Audit Trail Agent verifies: set(A.actual_writes) is a subset of
    set(A.declared_writes).
  checked_by: Audit Trail Agent; Agent Behaviour Analyst

### Context_Package_Constraints

R07:
  rule: >
    The Context Curator assembling a context package for an agent
    must include only items declared in that agent's reads list.
    No item outside the reads list may be included in a context package,
    regardless of its relevance or availability.
  test: >
    For all context packages P assembled for agent A:
    set(P.items) is a strict subset of set(A.specification.reads)
  checked_by: Context Curator (self-check on assembly);
              Context Delivery Layer (pre-delivery validation)

R08:
  rule: >
    Context packages must be assembled to the minimum necessary
    size for the agent to perform its task. When a reads list item
    is available in multiple versions, only the current approved
    version is included unless historical comparison is explicitly
    required by the task definition.
  test: >
    Context Curator must document the inclusion rationale for each
    item in a context package artefact. Items with no documented
    rationale are a violation.
  checked_by: Context Curator (assembly artefact);
              Perspective Reviewer (lens-economy)

R09:
  rule: >
    Skill files declared in an agent's skill_files list must not
    be loaded at agent startup. They must be loaded on demand,
    only when the specific capability they provide is required
    for the current task. Skill files not declared in the specification
    must never be loaded.
  test: >
    For all agents A: A loads skill file F only when task requires F AND
    F IN A.specification.CONTEXT_BOUNDARY.skill_files.
    Any load event where F NOT IN declared skill_files is a violation.
  checked_by: Audit Trail Agent (skill-file-loaded event);
              Agent Behaviour Analyst

### Boundary_Enforcement_and_Drift

R10:
  rule: >
    When an agent specification is updated (new version), the
    agent's instruction file must be updated to match within one
    CI cycle. An agent operating with an instruction file derived
    from a superseded specification version is in a boundary drift
    state, which is a violation.
  test: >
    For all agents A:
    A.instruction_file.spec_version == A.specification.version
    (current approved version).
  checked_by: CI Verifier; Agent Behaviour Analyst

R11:
  rule: >
    The Agent Behaviour Analyst must check for context boundary
    violations at every CI cycle by comparing each agent's audit
    trail write events against its declared writes list and
    read events against its declared reads list.
  test: >
    CI cycle report includes a context boundary compliance check
    for every active agent. Any undeclared read or write is
    reported as a critical finding.
  checked_by: Agent Behaviour Analyst; CI Verifier

R12:
  rule: >
    Any agent found to have accessed a resource in its never list
    is immediately suspended from the pipeline pending SysAdmin
    review. A never list breach is the most severe context boundary
    violation class.
  test: >
    For all agents A: if audit trail contains an event where
    A accessed a resource R AND R IN A.specification.never:
    A is placed in suspended status and
    sysadmin:dlm-sysadmin is notified immediately.
  checked_by: Audit Trail Agent; Agent Behaviour Analyst;
              CI Verifier

## EXCEPTIONS_PROCESS
No exceptions process applies to this policy. Context boundaries are
structural invariants derived from agent specifications. The mechanism
for extending an agent's context access is a minor version update to
the agent's specification (adding items to reads or removing items from
never), which follows the standard specification authoring and approval
pipeline. There is no per-task or per-invocation waiver process.

## ENFORCEMENT
  primary_agent:    Agent Behaviour Analyst
  gate_positions:
    - Pre-deployment: Stage Orchestrator checks R01 before activating
      any agent in the pipeline
    - Context package assembly: Context Curator enforces R07–R08 on
      every package before delivery
    - CI cycle: Agent Behaviour Analyst enforces R10–R12 at every
      CI cycle via audit trail analysis
    - Never list breach: Immediate pipeline suspension per R12;
      no gate — this is a real-time interrupt
  audit: >
    All context boundary events are logged by Audit Trail Agent:
    context-package-assembled, skill-file-loaded, boundary-check-pass,
    boundary-check-fail, never-list-breach, boundary-drift-detected.
    Never list breaches produce event outcome: fail and trigger
    immediate escalation.
  violation_type:   Tier 2 principles violation
  escalation: >
    Never list breaches escalate immediately to sysadmin:dlm-sysadmin.
    Boundary drift violations escalate within one CI cycle.
    All escalations via SysAdmin Escalation Policy.

## REVIEW_SCHEDULE
  interval_max:      12 months (Tier 2 maximum)
  trigger_conditions:
    - A new agent is added to the DLMS pipeline
    - A never list breach is detected by Agent Behaviour Analyst
    - A CI cycle identifies systematic boundary drift across
      multiple agents
    - A structural change to the Context Delivery Layer alters
      how context packages are assembled or routed
    - A new spec_type is added to the specification template
      that requires a different context boundary model
