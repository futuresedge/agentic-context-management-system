## SUMMARY
This policy defines the canonical schema for all DLMS documents — the
complete set of frontmatter fields, their types, allowed values, constraints,
and the body section heading conventions that every document must conform to.
The Agent Format Validator and Template Validator are bound to this policy.

## SCOPE
Applies to: every document in the DLMS corpus regardless of doc_type.
Applies to: all agents that produce, validate, store, index, or consume
DLMS documents.
Bootstrap exception: DLMS-2026-0001 through DLMS-2026-0004 conform to
this schema by design but predate formal pipeline enforcement.

## DEFINITIONS
frontmatter:
  The YAML block delimited by triple-dashes (---) at the top of every
  DLMS document. It precedes all body content. It is the primary
  machine-readable metadata layer.

core field:
  A frontmatter field required in every DLMS document regardless of
  doc_type. There are exactly 16 core fields.

additional field:
  A frontmatter field required or optional for a specific doc_type only.
  Defined in the relevant template (TMPL-[type]-NNN) not in this policy.

body:
  All document content below the closing --- of the frontmatter.

section key:
  A machine-readable heading (## UPPER_SNAKE_CASE) identifying a body section.
  Section key naming rules are governed by Naming Convention Policy R10.

enum:
  A field whose value must be drawn from an explicit, closed list.
  Unlisted values are invalid regardless of semantic similarity.

## RULES

### Core Frontmatter Schema

R01:
  rule: >
    Every DLMS document must contain all 16 core frontmatter fields.
    No core field may be omitted, even if its value is null.
  fields_count: 16
  test:     All 16 field names are present in frontmatter YAML.
  checked_by: Agent Format Validator; Template Validator

R02:
  rule: >
    The frontmatter block must open and close with triple-dashes (---).
    It must be the first content in the file. No content precedes it.
  test:     File byte[0:3] == '---' AND matching closing '---' exists
            before first body content.
  checked_by: Agent Format Validator

R03:
  rule: >
    Fields within the frontmatter must appear in the canonical order
    defined in this policy's FIELD_ORDER section. Order is prescriptive
    to enable consistent positional parsing.
  test:     Field sequence in document matches FIELD_ORDER exactly.
  checked_by: Agent Format Validator

### Field Definitions

FIELD_01:
  name:        doc_id
  type:        string
  required:    true
  nullable:    false
  format:      DLMS-YYYY-NNNN (governed by Naming Convention Policy R01)
  immutable:   true (after first assignment)
  description: Unique system-assigned document identifier.
  constraints:
    - Assigned by Naming Convention Enforcer before Author activates
    - Globally unique across all doc_types and all years
    - Never reused even after archival

FIELD_02:
  name:        doc_type
  type:        enum
  required:    true
  nullable:    false
  immutable:   true (after first approved version)
  values:
    policy:        Rules document. Enumerated, testable, binary compliance.
    procedure:     Step-by-step operational guide.
    standard:      Technical or structural requirement (MUST/SHOULD/MAY).
    pattern:       Reusable solution to a recurring design problem.
    sla:           Performance target with measurement and breach conditions.
    specification: Detailed technical or functional requirements document.
    reference:     Lookup or catalogue document (taxonomy, schedule, registry).
    report:        Time-bound findings and evidence document.
    taxonomy:      Controlled vocabulary. One per DLMS.
    template:      Document structure schema for a specific doc_type.
  constraints:
    - Value determines which template is applied (TMPL-[doc_type]-NNN)
    - doc_type may not be changed after first approved version

FIELD_03:
  name:        status
  type:        enum
  required:    true
  nullable:    false
  values:
    draft:        Authored but not yet submitted for review.
    under_review: Submitted for review; review pipeline active.
    approved:     Verified and approved; authoritative version.
    superseded:   Replaced by a newer approved version.
    archived:     Retained but no longer active or superseded.
  transitions:
    draft:        [under_review]
    under_review: [draft, approved]
    approved:     [superseded, archived]
    superseded:   [archived]
    archived:     []
  write_authority: Status Transition Agent only (post-creation)
  constraints:
    - Only approved documents are context_eligible
    - No backward transitions without a SysAdmin change directive
    - A document may not remain in under_review beyond the
      stage SLA limit defined in Stage SLA Policy

FIELD_04:
  name:        version
  type:        string
  required:    true
  nullable:    false
  format:      MAJOR.MINOR.PATCH (governed by Naming Convention Policy R13)
  start_value: 0.1.0 (all bootstrap documents)
  first_approved: 1.0.0 (regardless of draft patch history)
  write_authority: Version Control Agent
  versioning_rules:
    major: Structural change — section added, removed, or renamed;
           schema field added or removed; any change that breaks
           existing consumers of this document.
    minor: Content change — rules updated, values revised, non-breaking
           additions that do not alter existing fields or sections.
    patch: Correction only — typo, formatting error, or factual
           correction with no semantic change.
  constraints:
    - A new version produces a new file; the previous version file
      is immutable
    - Version number is never decremented

FIELD_05:
  name:        created_at
  type:        timestamp
  required:    true
  nullable:    false
  format:      ISO 8601 with timezone offset (e.g. 2026-03-08T10:00:00+11:00)
  write_authority: Creation Orchestrator (not Author Agent)
  immutable:   true (after creation)
  constraints:
    - Timezone offset must be explicit; UTC 'Z' suffix is accepted
    - Reflects creation time of the document, not the version

FIELD_06:
  name:        created_by
  type:        string
  required:    true
  nullable:    false
  format:      agent:[agent-role-slug] OR bootstrap:[team-slug]
               (governed by Naming Convention Policy R07)
  immutable:   true (after creation)
  constraints:
    - Must reference an entry in /dlms/registry/agent-registry.md
    - bootstrap: prefix reserved for Wave-1 documents only

FIELD_07:
  name:        approved_at
  type:        timestamp or null
  required:    true
  nullable:    true (null until approved)
  format:      ISO 8601 with timezone offset (same as created_at)
  write_authority: Approval Gate Agent only
  immutable:   true (after being set to non-null)

FIELD_08:
  name:        approved_by
  type:        string or null
  required:    true
  nullable:    true (null until approved)
  format:      agent:[agent-role-slug] or null
  write_authority: Approval Gate Agent only
  constraints:
    - Must differ from created_by value (Verification Independence Policy)
    - Must differ from verified_by value

FIELD_09:
  name:        verified_by
  type:        string or null
  required:    true
  nullable:    true (null until verified)
  format:      agent:[agent-role-slug] or null
  write_authority: Stage Verifier agent for the relevant stage only
  constraints:
    - Must differ from created_by AND approved_by
    - Structural separation enforced by Verification Independence Policy

FIELD_10:
  name:        template_id
  type:        string
  required:    true
  nullable:    false
  format:      TMPL-[doc-type-slug]-[NNN] OR 'self' OR 'bootstrap'
  reserved_values:
    self:      Valid only for DLMS-2026-0002 (the meta-template)
    bootstrap: Valid only for DLMS-2026-0001 through DLMS-2026-0004
  constraints:
    - The referenced template must have status: approved at time of
      document creation (except bootstrap documents)
    - template_id is immutable after first approved version

FIELD_11:
  name:        template_ver
  type:        string or null
  required:    true
  nullable:    true (null for bootstrap and self)
  format:      MAJOR.MINOR.PATCH or null
  constraints:
    - Must match the version of template_id at time of creation
    - If the template is later updated (minor or patch), this field
      remains unchanged; Template Version Controller flags migration
    - If the template is major-version updated, this field triggers
      mandatory migration assessment

FIELD_12:
  name:        tags
  type:        array of strings
  required:    true
  nullable:    false
  min_items:   1
  format:      lowercase-hyphen-separated slugs
  write_authority: Classification Agent (validated by Taxonomy Validator)
  constraints:
    - All values must exist in the approved Taxonomy document
    - No free-text tags; no wildcards
    - Tag naming governed by Naming Convention Policy R09

FIELD_13:
  name:        supersedes
  type:        string or null
  required:    true
  nullable:    true (null if no prior version superseded)
  format:      doc_id of the superseded document or null
  write_authority: Version Control Agent
  constraints:
    - If set, the referenced document's superseded_by field must equal
      this document's doc_id
    - Both updates must be atomic (same Version Control Agent action)
    - The superseded document must have status: superseded after the update

FIELD_14:
  name:        superseded_by
  type:        string or null
  required:    true
  nullable:    true (null while document is the current version)
  format:      doc_id of the superseding document or null
  write_authority: Version Control Agent
  constraints:
    - Set when a superseding document is approved
    - A document with superseded_by != null must have status: superseded
    - Immutable after being set to non-null

FIELD_15:
  name:        retention_class
  type:        enum
  required:    true
  nullable:    false
  values:
    RC-permanent: No expiry. Retained indefinitely.
                  Required for: all bootstrap documents, all policies,
                  all templates, the Taxonomy, the Retention Schedule.
    RC-1:         Retain 7 years. (placeholder — defined in Retention Schedule)
    RC-2:         Retain 5 years. (placeholder — defined in Retention Schedule)
    RC-3:         Retain 3 years. (placeholder — defined in Retention Schedule)
    RC-4:         Retain 2 years. (placeholder — defined in Retention Schedule)
    RC-5:         Retain 1 year.  (placeholder — defined in Retention Schedule)
    RC-6:         Retain 6 months. (placeholder — defined in Retention Schedule)
    RC-7:         Retain 90 days. (placeholder — defined in Retention Schedule)
  forward_ref:  Full retention class definitions are in the Retention
                Schedule document (Wave 5). RC-1 through RC-7 placeholders
                will be updated when that document is approved.
  write_authority: Retention Evaluator (Archival stage)
  constraints:
    - Bootstrap documents and all corpus policies must declare RC-permanent
    - Stage artefacts (verification records, learnings, etc.) use
      shorter retention classes appropriate to their operational value

FIELD_16:
  name:        context_eligible
  type:        boolean
  required:    true
  nullable:    false
  description: >
    Whether this document may be included in context packages
    delivered to non-DLMS agents by the Context Delivery Layer.
  constraints:
    - Only documents with BOTH status: approved AND context_eligible: true
      may be included in context packages
    - Confidentiality classification (when that policy exists) may
      set this to false regardless of status
    - Stage artefacts (verification records, audit events, etc.) are
      context_eligible: false by default

FIELD_17:
  name:        dependencies
  type:        array of objects or empty array []
  required:    true
  nullable:    false (use [] if no dependencies)
  item_schema:
    doc_id:
      type:     string
      required: true
      format:   DLMS-YYYY-NNNN
    rel:
      type:     enum
      required: true
      values:
        implements:    >
          This document operationalises or applies the referenced document.
          Example: a procedure that implements a policy.
        references:    >
          This document cites, uses, or depends on content from the
          referenced document without being governed by it.
        supersedes:    >
          This document replaces the referenced document.
          Must be paired with that document's superseded_by field.
        is-governed-by: >
          The rules of the referenced document directly apply to
          this document. Used to declare policy applicability.
  constraints:
    - All referenced doc_ids must exist in the DLMS registry
    - Circular dependencies are forbidden
    - Dependency relationships are validated by Dependency Index Agent
      at every Indexing stage
    - Forward references (to documents not yet approved) are permitted
      in Wave-1 bootstrap documents only; must be flagged with a
      forward_ref comment

FIELD_18:
  name:        agent_path
  type:        string
  required:    true
  nullable:    false
  format:      /dlms/corpus/[doc-type-plural]/[doc_id]-v[version].md
               (governed by Naming Convention Policy R05 and R06)
  write_authority: Version Control Agent
  immutable:   true (per version; new versions get new paths)
  constraints:
    - Path must match the actual file location in the DLMS file system
    - doc-type-plural mapping is defined in Naming Convention Policy R06

FIELD_19:
  name:        audit_ref
  type:        string
  required:    true
  nullable:    false
  format:      AUDIT-[doc_id] OR AUDIT-BOOTSTRAP-[NNNN]
               (governed by Naming Convention Policy R08)
  write_authority: Creation Orchestrator
  immutable:   true (after creation)
  constraints:
    - All audit events for this document must cite this ref
    - Audit Trail Agent uses this ref to retrieve the complete
      event history for a document

R04:

### Body Section Conventions

R05:
  rule: >
    The body of every DLMS document must begin with a ## SUMMARY section
    immediately after the closing --- of the frontmatter.
  test:     First ## heading after closing --- equals '## SUMMARY'
  checked_by: Agent Format Validator

R06:
  rule: >
    ## SUMMARY must contain exactly 2–3 sentences. It must be
    self-contained, dense, and free of narrative prose or contextual
    explanation.
  test:     Sentence count in SUMMARY body: 2 <= n <= 3
  checked_by: Template Validator; Perspective Reviewer (lens-agent-readability)

R07:
  rule: >
    The final section of every document body must be ## CHANGE_LOG.
    No body content appears after CHANGE_LOG.
  test:     Last ## heading equals '## CHANGE_LOG'
  checked_by: Agent Format Validator

R08:
  rule: >
    Every ## CHANGE_LOG entry must follow the format:
    - v[version] | [date] | [created_by] | [change summary]
    Entries are ordered newest-first. Every version has exactly one entry.
  format:   - v[MAJOR.MINOR.PATCH] | YYYY-MM-DD | [agent_id] | [summary]
  example:  - v1.0.0 | 2026-03-08 | agent:document-author | Initial approval
  test:     All CHANGE_LOG entries match the prescribed format AND
            entry count equals version history count in version-registry
  checked_by: Storage Verifier; Version Control Agent

R09:
  rule: >
    Required section headings (## level) must use UPPER_SNAKE_CASE.
    Subsection headings (### level) must use Title_Case_With_Underscores.
    Both are governed by Naming Convention Policy R10 and R11.
  test:     All ## headings match regex ^[A-Z][A-Z_]+$ AND
            all ### headings match regex ^[A-Z][a-zA-Z_]+$
  checked_by: Agent Format Validator

R10:
  rule: >
    Documents must not contain markdown features that degrade
    agent parseability: no HTML, no embedded images, no tables
    inside frontmatter, no nested code blocks within body text.
    Code blocks (triple-backtick) are permitted for structured
    examples only.
  test:     No HTML tags present. No nested code fences.
  checked_by: Agent Format Validator

R11:
  rule: >
    All cross-references to other DLMS documents in the body must use
    the doc_id format (DLMS-YYYY-NNNN), not titles or slugs.
    Titles may appear in parentheses for human readability but the
    doc_id is the authoritative reference.
  example:  "...as defined in DLMS-2026-0001 (Policy Governance Policy)..."
  test:     All document cross-references include a valid doc_id pattern
  checked_by: Dependency Index Updater; Template Validator

### Additional Fields

R12:
  rule: >
    Doc-type-specific additional fields beyond the 19 core fields
    are defined in the relevant template (TMPL-[type]-NNN) and
    are permitted in documents of that type only.
  constraints:
    - Additional fields must not use the same name as any core field
    - Additional field names use lowercase_snake_case (YAML convention)
    - Additional fields always appear after audit_ref in the frontmatter
  test:     No additional field name conflicts with core fields 1–19
  checked_by: Template Validator

## EXCEPTIONS_PROCESS
Governed by DLMS-2026-0001 (Policy Governance Policy) Tier 4 exceptions process.
Schema exceptions require an impact assessment from the Agent Format Validator
covering all documents and agent instructions affected by the deviation.

## ENFORCEMENT
  primary_agent:    Agent Format Validator
  secondary_agents: [Template Validator, Storage Verifier, Indexing Verifier]
  gate_positions:
    - Agent Format Validator runs at start of Dual-Version Production stage
    - Template Validator runs at end of Creation stage
    - Storage Verifier confirms path and field compliance at Storage stage
  audit:            Audit Trail Agent logs all schema validation events
  violation_type:   Tier 4 technical standard violation

## REVIEW_SCHEDULE
  interval_max:      6 months
  trigger_conditions:
    - New doc_type added to enum
    - New core field required across all documents
    - Breaking change to any field type or constraint
    - CI schema violation pattern detected
