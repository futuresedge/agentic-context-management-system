## SUMMARY
This policy defines all naming conventions for documents, files, folders,
identifiers, agents, and artefacts within the DLMS. The Naming Convention
Enforcer agent is bound to this policy and is authoritative for all name
validation. All Wave-1 bootstrap documents are retroactively compliant with
this policy by design.

## SCOPE
Applies to: all documents, files, folders, artefacts, identifiers, paths,
agent IDs, template IDs, tag values, and audit references within the DLMS.
Applies to: all agents that create, store, reference, or route DLMS documents.
Excludes: external system identifiers brought into the DLMS from outside
sources (these are recorded as-is in a dedicated external_ref field).

## DEFINITIONS
slug:
  A lowercase, hyphen-separated string containing only alphanumeric characters
  and hyphens. No spaces, underscores, dots, or special characters.
  Example: document-schema-policy

doc_id:
  The unique, immutable, system-assigned identifier for a DLMS document.

version string:
  A semantic version in major.minor.patch format. All three components
  are non-negative integers separated by dots. No prefixes (e.g. no 'v' prefix
  in the version field itself). The 'v' prefix appears only in file names and
  CHANGE_LOG entries.

path:
  A forward-slash-delimited string identifying the location of a file
  within the DLMS file system. Always begins with /dlms/.

section key:
  A machine-readable heading used in document body sections. Format rules
  are defined in R12 and R13.

## RULES

### Document Identifiers

R01:
  rule: >
    Every DLMS document must have a doc_id assigned by the Naming Convention
    Enforcer before the Author Agent activates. No document may be created
    without an assigned doc_id.
  format:   DLMS-YYYY-NNNN
  fields:
    DLMS:   Literal prefix. Immutable.
    YYYY:   Four-digit year of document creation (not approval).
    NNNN:   Sequential integer, zero-padded to 4 digits, unique within the year.
            Sequence resets to 0001 at the start of each calendar year.
  examples: [DLMS-2026-0001, DLMS-2026-0042, DLMS-2027-0001]
  constraints:
    - doc_id is immutable after assignment
    - doc_id is globally unique across all years and doc types
    - The sequence number is assigned by the Document Registry in
      strict creation order; no gaps, no reuse
  test:     doc_id matches regex ^DLMS-\d{4}-\d{4}$
  checked_by: Naming Convention Enforcer

R02:
  rule: >
    Template identifiers follow a distinct naming convention separate from
    doc_id. Templates are referenced by their template_id alias in all
    agent instructions. The alias is mapped to the doc_id in the
    Template Registry.
  format:   TMPL-[doc-type-slug]-[NNN]
  fields:
    TMPL:            Literal prefix.
    doc-type-slug:   Slug form of the target doc_type (e.g. policy, procedure).
    NNN:             Sequential integer, zero-padded to 3 digits, unique
                     within the doc-type.
  examples: [TMPL-policy-001, TMPL-sla-002, TMPL-template-001]
  constraints:
    - template_id alias is immutable after first approved version
    - TMPL-template-001 is the reserved alias for the meta-template (DLMS-2026-0002)
    - New template aliases are assigned by Naming Convention Enforcer
  test:     template_id matches regex ^TMPL-[a-z]+-\d{3}$ OR
            template_id IN [self, bootstrap]
  checked_by: Naming Convention Enforcer

### File Naming

R03:
  rule: >
    The agent-friendly canonical file for every document version must be
    named using the following pattern. No other file name format is valid.
  format:   [doc_id]-v[version].md
  examples:
    - DLMS-2026-0001-v0.1.0.md
    - DLMS-2026-0042-v2.1.0.md
    - DLMS-2027-0001-v1.0.0.md
  constraints:
    - The 'v' prefix is required in the file name
    - The version string follows semver (major.minor.patch)
    - File extension is always .md
    - Every version produces a new file; files are never overwritten
  test:     filename matches regex ^DLMS-\d{4}-\d{4}-v\d+\.\d+\.\d+\.md$
  checked_by: Version Control Agent; Storage Verifier

R04:
  rule: >
    Artefact files produced by agents during the lifecycle stages must
    follow a predictable naming pattern to enable reliable parsing by
    downstream agents.
  format:   [artefact-type-slug]-[doc_id].md
  examples:
    - creation-dod-DLMS-2026-0042.md
    - review-synthesis-DLMS-2026-0042.md
    - storage-verification-DLMS-2026-0042.md
    - indexing-learnings-DLMS-2026-0042.md
  constraints:
    - artefact-type-slug must match the registered artefact type for
      that stage (defined in each TMPL-[artefact]-001 template)
    - No spaces or special characters
  test:     filename matches regex ^[a-z-]+-DLMS-\d{4}-\d{4}\.md$
  checked_by: Stage Verifiers

### Folder and Path Structure

R05:
  rule: >
    All DLMS files reside under the /dlms/ root. The following canonical
    folder structure is prescriptive. No files may be stored outside
    this structure.
  structure:
    /dlms/
      corpus/
        policies/
        templates/
        procedures/
        standards/
        patterns/
        slas/
        specifications/
        references/
        reports/
        taxonomies/
      artefacts/
        creation/
        review/
        indexing/
        storage/
        distribution/
        archival/
      indexes/
      audit/
      knowledge-base/
      registry/
      config/
      ci/
      sysadmin/
  constraints:
    - Document corpus files go in /dlms/corpus/[doc-type-plural]/
    - Stage artefacts go in /dlms/artefacts/[stage]/[doc_id]/
    - Index files go in /dlms/indexes/
    - Audit trail goes in /dlms/audit/
    - Knowledge base entries go in /dlms/knowledge-base/[doc-type]/[stage].md
    - Registry files go in /dlms/registry/
    - CI reports go in /dlms/ci/
    - SysAdmin artefacts go in /dlms/sysadmin/
  test:     agent_path starts with /dlms/ AND second segment is a known folder
  checked_by: Storage Verifier; Naming Convention Enforcer

R06:
  rule: >
    The agent_path for a document must include the version number.
    Each version of a document has a unique path. No path is reused
    across versions.
  format:   /dlms/corpus/[doc-type-plural]/[doc_id]-v[version].md
  examples:
    - /dlms/corpus/policies/DLMS-2026-0001-v1.0.0.md
    - /dlms/corpus/templates/DLMS-2026-0002-v1.0.0.md
  constraints:
    - doc-type-plural is the plural slug of the doc_type
      (policy → policies, template → templates, taxonomy → taxonomies,
       procedure → procedures, standard → standards, pattern → patterns,
       sla → slas, specification → specifications, reference → references,
       report → reports)
    - Path is immutable after Storage stage completes for that version
  test:     agent_path matches the prescribed format for the doc_type
  checked_by: Version Control Agent

### Agent Identifiers

R07:
  rule: >
    All agent identifiers used in created_by, approved_by, verified_by,
    and audit event payloads must follow a prescribed format.
  formats:
    standard_agent:  agent:[agent-role-slug]
    bootstrap_team:  bootstrap:[team-slug]
    sysadmin:        sysadmin:[role-slug]
  examples:
    - agent:document-author
    - agent:review-verifier
    - agent:approval-gate
    - agent:naming-convention-enforcer
    - agent:context-curator-creation
    - bootstrap:design-team
    - sysadmin:dlm-sysadmin
  constraints:
    - agent-role-slug is lowercase hyphen-separated
    - No spaces, uppercase, or special characters in the slug
    - Bootstrap prefix is reserved exclusively for Wave-1 founding documents
    - The authoritative agent roster is maintained in /dlms/registry/agent-registry.md
  test:     agent_id matches regex ^(agent|bootstrap|sysadmin):[a-z-]+$
  checked_by: Audit Trail Agent; Agent Behaviour Analyst

### Audit References

R08:
  rule: >
    Every document must have an audit_ref assigned at creation that
    links all audit events for that document to a single retrievable key.
  formats:
    standard:  AUDIT-[doc_id]
    bootstrap: AUDIT-BOOTSTRAP-[NNNN]
  examples:
    - AUDIT-DLMS-2026-0042
    - AUDIT-BOOTSTRAP-0001
  constraints:
    - AUDIT-BOOTSTRAP-NNNN is reserved for Wave-1 documents only
    - audit_ref is immutable after creation
    - audit_ref must be unique across the entire DLMS
  test:     audit_ref matches regex ^AUDIT-(DLMS-\d{4}-\d{4}|BOOTSTRAP-\d{4})$
  checked_by: Creation Orchestrator; Audit Trail Agent

### Tag and Vocabulary Names

R09:
  rule: >
    All tag values used in the tags[] frontmatter field must be
    lowercase slugs drawn exclusively from the approved Taxonomy document.
  format:   [lowercase-hyphen-separated-slug]
  examples: [meta-governance, bootstrap, wave-1, policy, context-delivery]
  constraints:
    - No uppercase characters in tag values
    - No spaces or special characters
    - Free-text tags are forbidden
    - Tags not in the approved Taxonomy are rejected by Classification Agent
    - New tags must be proposed via the Taxonomy update process
  test:     all items in tags[] match regex ^[a-z][a-z0-9-]*$ AND
            all items in tags[] exist in approved Taxonomy
  checked_by: Classification Agent; Taxonomy Validator

### Section Keys (Document Body)

R10:
  rule: >
    Required section headings at the ## level must use UPPER_SNAKE_CASE.
    These are machine-readable keys that downstream agents parse directly.
  format:   ## UPPER_SNAKE_CASE
  examples:
    - ## SUMMARY
    - ## REQUIRED_SECTIONS
    - ## CHANGE_LOG
    - ## VALIDATION_RULES
  constraints:
    - Only letters and underscores in section keys (no digits, hyphens,
      or special characters)
    - Section keys must exactly match those defined in the template's
      REQUIRED_SECTIONS list
  test:     all ## headings in REQUIRED_SECTIONS match regex ^[A-Z][A-Z_]+$
  checked_by: Agent Format Validator; Template Validator

R11:
  rule: >
    Optional subsection headings at the ### level must use Title_Case
    with underscores as word separators.
  format:   ### Title_Case_With_Underscores
  examples:
    - ### Frontmatter_Fields
    - ### Additional_Fields
  constraints:
    - First letter of each word is capitalised
    - Words separated by underscores
    - Used only within sections established by required ## headings
  test:     all ### headings match regex ^[A-Z][a-zA-Z_]+$
  checked_by: Agent Format Validator

R12:
  rule: >
    Inline enumerated items within section bodies (rules, steps, fields)
    must use UPPER_SNAKE_CASE identifiers as keys.
  format:   KEY: value  or  KEY:\n  subkey: value
  examples:
    - R01:, R02:, V01:, V02:
    - TIER_1:, TIER_2:
    - doc_id:, doc_type:, status:
  constraints:
    - Rule identifiers use R prefix + sequential two-digit number
    - Validation rules use V prefix + sequential two-digit number
    - Field names use lowercase_snake_case (consistent with YAML convention)
  test:     Rule IDs match regex ^R\d{2}$;
            Validation rule IDs match regex ^V\d{2}$
  checked_by: Template Validator

### Version Strings

R13:
  rule: >
    All version strings must follow semantic versioning (semver).
    The 'v' prefix is used only in file names and CHANGE_LOG entries,
    never in the version frontmatter field itself.
  format:
    field_value: MAJOR.MINOR.PATCH  (e.g. 1.0.0, 0.1.0, 2.4.1)
    filename:    v[MAJOR].[MINOR].[PATCH]  (e.g. v1.0.0, v0.1.0)
    change_log:  v[MAJOR].[MINOR].[PATCH]  (e.g. v1.0.0)
  bootstrap_start: 0.1.0
  first_approved:  1.0.0
  constraints:
    - Bootstrap drafts start at 0.1.0
    - First approved version is always 1.0.0 regardless of draft version history
    - No version may be skipped (0.1.0 → 0.2.0 not 0.1.0 → 1.0.0 unless approving)
    - Pre-approval versions (0.x.x) are internal and may not be
      distributed outside the DLMS
  test:     version matches regex ^\d+\.\d+\.\d+$
  checked_by: Version Control Agent

a migration plan for all affected documents.
