## SUMMARY
This policy governs the DLMS audit trail — the immutable, append-only
record of all auditable events across every document lifecycle stage,
agent action, and system transition. Every observable event in the DLMS
must be captured, linked to its document via audit_ref, and retained
permanently. This is a Tier 2 policy directly enforcing Principle 3
(Total Auditability).

## SCOPE
Applies to: all agents that perform or witness auditable events; the
Audit Trail Agent as the sole writer to the audit trail; all DLMS
documents (every document must carry an audit_ref); all lifecycle
stages and transitions; all SysAdmin directives and their resolution;
all independence check events; all CI cycle events.

Excludes: Internal agent reasoning or deliberation that produces no
external output or state change; read-only operations where an agent
reads a document but produces no artefact and changes no state (e.g.
context package consumption by a non-DLMS agent).

Bootstrap exception: DLMS-2026-0001 through DLMS-2026-0004 carry
AUDIT-BOOTSTRAP-NNNN audit_refs. Their audit trail is retroactively
bootstrapped when the audit trail infrastructure becomes operational.
All events from bootstrap onwards are captured normally.

## DEFINITIONS

audit entry:
  A single, immutable record of one auditable event. Contains a
  minimum set of required fields defined in R05. Once written, an
  audit entry can never be modified or deleted.

audit trail:
  The complete, ordered collection of all audit entries across the
  DLMS. Stored at /dlms/audit/. Queryable but never writable except
  by the Audit Trail Agent.

audit_ref:
  The document-scoped identifier that links all audit entries for a
  specific document. Format governed by Naming Convention Policy R08.
  Assigned at document creation and immutable thereafter.

auditable event:
  Any action, state transition, agent decision, or system event that
  changes or records DLMS state. The complete list of auditable event
  types is maintained in the Event Type Registry
  (/dlms/registry/event-type-registry.md).

event_type:
  A registered, controlled vocabulary term identifying the category
  of an audit entry. All event_type values must exist in the Event
  Type Registry. Free-text event types are prohibited.

immutability:
  The property of a record that cannot be altered, overwritten, or
  deleted after it is written. Immutability in the audit trail is
  enforced structurally — no agent except the Audit Trail Agent has
  write access to /dlms/audit/, and the Audit Trail Agent is
  append-only (it has no update or delete capability).

## RULES

### Audit_Ref_Requirements

R01:
  rule: >
    Every DLMS document must carry an audit_ref field. The audit_ref
    must be assigned at the moment of document creation and must be
    non-null, correctly formatted, and globally unique.
  test: >
    audit_ref != null AND
    audit_ref matches regex
    ^AUDIT-(DLMS-\d{4}-\d{4}|BOOTSTRAP-\d{4})$ AND
    audit_ref is unique across all documents in the DLMS registry.
  checked_by: Creation Orchestrator; Naming Convention Enforcer;
              Agent Format Validator

R02:
  rule: >
    audit_ref is immutable after document creation. No agent may
    change, reassign, or nullify an audit_ref once it has been set.
  test: >
    For all document versions V of doc_id D:
    V.audit_ref == V[0].audit_ref (value is identical across all versions)
  checked_by: Version Control Agent; Storage Verifier

### Auditable_Events

R03:
  rule: >
    Every auditable event must produce exactly one audit entry,
    written by the Audit Trail Agent, before the next stage or
    action in the pipeline may proceed. No stage transition is
    valid without a corresponding audit entry.
  test: >
    For each pipeline state transition T:
    an audit entry with event_type matching T exists in /dlms/audit/
    with timestamp <= T.completion_timestamp.
  checked_by: Stage Orchestrators (gate condition);
              Audit Trail Agent; CI Verifier

R04:
  rule: >
    The following event categories are mandatory auditable events.
    Every occurrence must be captured regardless of outcome:
    document-created, status-transition, stage-started,
    stage-completed, stage-failed, verification-passed,
    verification-failed, approval-granted, approval-blocked,
    independence-check-pass, independence-check-fail,
    independence-violation, naming-validation-pass,
    naming-validation-fail, sysadmin-directive-issued,
    sysadmin-directive-resolved, ci-cycle-started,
    ci-cycle-completed, taxonomy-term-added,
    taxonomy-term-deprecated, document-superseded,
    document-archived, audit-trail-query.
  test: >
    For each event category listed above: when the corresponding
    event occurs, an audit entry is present with event_type exactly
    matching the registered name in the Event Type Registry.
  checked_by: Audit Trail Agent; Agent Behaviour Analyst (CI check)

### Audit_Entry_Structure

R05:
  rule: >
    Every audit entry must contain all of the following fields.
    No field may be null. No field may be omitted.
  required_fields:
    entry_id:      Globally unique identifier for this entry.
                   Format: AE-[audit_ref]-[sequential-integer].
    audit_ref:     The audit_ref of the document this event relates to.
    event_type:    Registered event type from the Event Type Registry.
    timestamp:     ISO 8601 timestamp with timezone offset.
    actor:         The agent or role that performed the action.
                   Format: agent:[slug] or sysadmin:[slug] or
                   bootstrap:[slug].
    doc_id:        The doc_id of the document this event relates to.
    stage:         The lifecycle stage in which the event occurred.
                   Null only for system-level events with no stage context.
    outcome:       pass, fail, or info.
    payload_ref:   Path to the full event payload artefact, or null
                   if no payload exists for this event type.
    schema_version: The version of the audit entry schema used.
  test: >
    For all entries E in /dlms/audit/:
    all nine fields are present and non-null (stage may be null
    only for system-level events per the Event Type Registry definition).
  checked_by: Audit Trail Agent (self-validation on write);
              Storage Verifier

R06:
  rule: >
    The event_type field in every audit entry must be drawn from
    the approved Event Type Registry. Free-text, informal, or
    unregistered event types are prohibited.
  test: >
    For all entries E: E.event_type IN approved Event Type Registry.
  checked_by: Audit Trail Agent; Taxonomy Validator (Event Type Registry
              is a reference document governed by this policy)

### Immutability_and_Integrity

R07:
  rule: >
    The Audit Trail Agent is the sole agent with write access to
    /dlms/audit/. No other agent may write to, modify, or delete
    any file within /dlms/audit/.
  test: >
    For all write operations to /dlms/audit/:
    actor == agent:audit-trail
  checked_by: Storage Verifier; Agent Behaviour Analyst (CI check)

R08:
  rule: >
    Audit entries are append-only. Once an audit entry is written,
    its content is immutable. No field may be updated, overwritten,
    or backfilled after the entry is written.
  test: >
    CI Cycle quality check compares audit entry checksums at each
    cycle against the prior cycle. Any checksum change for an
    existing entry is a critical integrity violation.
  checked_by: Agent Behaviour Analyst; CI Verifier;
              Storage Verifier

R09:
  rule: >
    The audit trail must be continuous. No gap in the audit trail
    is permitted between consecutive stage events for the same
    document. A gap constitutes an integrity breach.
  test: >
    For each document D: the sequence of audit entries ordered by
    timestamp forms an unbroken chain from document-created to
    the current status. Missing events between known states constitute
    a detected gap.
  checked_by: Agent Behaviour Analyst; CI Verifier

### Audit_Trail_Queryability

R10:
  rule: >
    The audit trail must be queryable by the following dimensions,
    individually and in combination: audit_ref, doc_id, actor,
    event_type, outcome, stage, and date range. The Audit Trail
    Agent must support all six query dimensions.
  test: >
    Audit Trail Agent specification (Wave 4) must declare all six
    query dimensions in its REQUIREMENTS section. CI Verifier
    validates query capability at each CI cycle.
  checked_by: Audit Trail Agent specification; CI Verifier

R11:
  rule: >
    All audit queries must themselves be logged as audit entries
    with event_type: audit-trail-query. This prevents undetected
    read access to the audit trail.
  test: >
    For all query operations against /dlms/audit/:
    a subsequent audit entry with event_type: audit-trail-query
    and actor == querying agent is written.
  checked_by: Audit Trail Agent (self-logging); Agent Behaviour Analyst

### Retention

R12:
  rule: >
    All audit trail entries must be retained permanently (RC-permanent).
    Audit entries may not be deleted, archived to cold storage, or
    otherwise made inaccessible regardless of the status of the
    document they relate to. Archived or superseded documents retain
    their full audit trail.
  test: >
    Retention Evaluator must assign RC-permanent to all audit trail
    artefacts. No audit entry may appear in any archival or deletion
    schedule.
  checked_by: Retention Evaluator; Archival Stage Verifier

## EXCEPTIONS_PROCESS
No exceptions process applies to this policy. Total auditability is
a structural invariant of the DLMS and a direct expression of
Principle 3. No per-document, per-stage, or per-agent waiver of
audit trail requirements may be granted. The bootstrap exception
declared in SCOPE is the only recognised deviation and is fixed in
time to the pre-operational bootstrap phase only.

## ENFORCEMENT
  primary_agent:    Audit Trail Agent
  gate_positions:
    - Stage transition gate: Stage Orchestrators check that the
      required audit entry exists before advancing to the next stage
    - Approval gate: Approval Gate Agent confirms a complete audit
      chain from document-created to current state before approval
    - CI cycle: Agent Behaviour Analyst checks audit trail integrity,
      entry completeness, and gap detection at every CI cycle
  audit: >
    The Audit Trail Agent logs its own writes as a self-referential
    audit event. Integrity violations detected by CI are logged as
    event_type: audit-integrity-violation with outcome: fail and
    immediately escalate to sysadmin:dlm-sysadmin.
    Paradox note: audit trail integrity violations cannot be fully
    self-audited — external CI inspection by Agent Behaviour Analyst
    is the primary integrity mechanism.
  violation_type:   Tier 2 principles violation
  escalation: >
    Any audit trail gap, immutability breach, or structural integrity
    failure is immediately escalated to sysadmin:dlm-sysadmin via
    SysAdmin Escalation Policy. These are the highest-priority
    violations in the DLMS — an untrusted audit trail invalidates
    the entire governance record.

## REVIEW_SCHEDULE
  interval_max:      12 months (Tier 2 maximum)
  trigger_conditions:
    - An audit trail integrity violation (gap, checksum mismatch,
      or unauthorised write) is detected by CI
    - A new auditable event category is identified that is not in
      the Event Type Registry
    - The Audit Trail Agent specification is updated in a way that
      changes write behaviour or query capability
    - A new lifecycle stage is added to the DLMS pipeline
    - A CI cycle report identifies systematic under-reporting of
      auditable events by any agent
