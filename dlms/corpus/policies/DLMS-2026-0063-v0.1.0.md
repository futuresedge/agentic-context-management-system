## SUMMARY
This policy governs what learning records may enter the DLMS Knowledge Base,
how they are structured within it, and who may contribute them. It defines
the KB slot schema, deduplication obligations, status transition requirements,
and contributor restrictions for the KB Agent. This is a Tier 3 Operational
Lifecycle policy.

## SCOPE
Applies to: all learning records produced per TMPL-learnings-001
(DLMS-2026-0034) awaiting KB contribution; the KB Agent; sysadmin:dlm-sysadmin
in the KB contribution and dismissal context; the Knowledge Base directory
structure at kb/.

Excludes: the creation or content quality of learning records (governed by
DLMS-2026-0034, which defines the schema, and by the producing agent);
synthesis of accumulated KB data into patterns and recommendations (governed
by Learning Synthesis Policy DLMS-2026-0064); template governance (governed
by DLMS-2026-0065); direct reads of the KB by downstream synthesis or
reporting agents (governed by DLMS-2026-0064 R08 and DLMS-2026-0016).

## DEFINITIONS

contribution event:
  A single KB write operation — either creating a new KB entry in a slot or
  merging a candidate learning record into an existing KB entry in the same
  slot. The outcome of a contribution event is one of: new-entry, merged,
  dismissed, or contribution-skipped (rejected at input gate).

KB entry:
  A structured record stored in the KB at a specific kb/{stage}/{finding_type}/
  slot path. A KB entry aggregates one or more related learning records.
  Each KB entry carries a source_records list (all learning_ids that
  contributed to it) and a match_count (number of merged records to date).

Knowledge Base (KB):
  The corpus of KB entries organised under the kb/ directory root, structured
  per kb/{stage}/{finding_type}/ slots as defined in R03. The KB is the
  primary input source for Learning Synthesis (DLMS-2026-0064).

near-duplicate:
  A candidate learning record is a near-duplicate of an existing KB entry
  when all three of the following match: source_doc_id, finding_type, and
  root_cause. Near-duplicates are merged per R05 rather than creating a
  new entry.

open learning record:
  A learning record with status: open (DLMS-2026-0034 FIELD_13) that has
  not yet been contributed to the KB or dismissed. The open learning record
  queue is the set of all such records eligible for processing by KB Agent.

## RULES

### Input_Qualification

R01:
  rule: >
    Only learning records with status: open that satisfy all eleven
    validation rules (V01–V11) in TMPL-learnings-001 (DLMS-2026-0034)
    are eligible for KB contribution. A record that fails any validation
    rule is ineligible. KB Agent must not attempt to contribute a
    non-conformant record; it must log a contribution-skipped audit event
    per R10 identifying the failing rule(s) and the learning_id.
  test: >
    For each candidate record: record.status == open AND V01 through V11
    of DLMS-2026-0034 all pass. Any record where status != open or any
    validation rule fails → contribution-skipped event; no KB write occurs.
  checked_by: KB Agent; Quality Monitor

R02:
  rule: >
    Severity does not affect eligibility for KB contribution. All four
    severity values — critical, major, minor, observation — are eligible.
    Severity affects routing priority during Learning Synthesis
    (DLMS-2026-0064 R04c) but does not gate eligibility at the
    contribution stage.
  test: >
    No KB Agent logic may filter or defer a conformant open record based
    on severity alone. Evidence of severity-based filtering is a policy
    violation.
  checked_by: KB Agent; Agent Behaviour Analyst

### KB_Structure

R03:
  rule: >
    The KB is structurally organised at kb/{stage}/{finding_type}/.
    Valid stage values (8) and valid finding_type values (7) are the
    complete enumerations defined in DLMS-2026-0034 FIELD_04 and
    FIELD_06 respectively:
    Stages: creation, review, approval, storage, distribution, archival,
            indexing, system.
    Finding_types: schema-violation, process-gap, dependency-error,
                   content-issue, taxonomy-issue, agent-behaviour,
                   process-improvement.
    This yields 56 valid slot paths. KB Agent must route each contribution
    to the exact slot matching the record's stage and finding_type values.
  test: >
    For each KB write: the target path == kb/{record.stage}/{record.finding_type}/
    AND both segment values are members of the respective enum lists
    above. Misrouted writes are rejected per R04.
  checked_by: KB Agent; Audit Trail Agent

R04:
  rule: >
    KB Agent must not create KB entries outside the 56 defined slot paths.
    A candidate record whose stage or finding_type value does not match a
    valid enum value defined in DLMS-2026-0034 FIELD_04 or FIELD_06 is a
    structural violation. KB Agent must reject it and log a
    contribution-rejected audit event with the invalid field value(s) and
    the learning_id.
  test: >
    No KB entry exists outside the kb/{valid_stage}/{valid_finding_type}/
    path structure. Any entry outside this structure is an unauthorised
    write and triggers a Tier 3 violation.
  checked_by: Audit Trail Agent; Agent Behaviour Analyst

### Deduplication

R05:
  rule: >
    Before creating a new KB entry, KB Agent must check the target slot
    for a near-duplicate (defined above). When a near-duplicate is found,
    KB Agent must merge: increment the existing entry's match_count by 1
    and append the candidate record's learning_id to the existing entry's
    source_records list. KB Agent must not create a new entry for a
    record that is a near-duplicate of an existing entry in the slot.
  test: >
    For each contribution event: IF an entry exists in the target slot
    where entry.source_doc_id == record.source_doc_id AND
    entry.finding_type == record.finding_type AND entry.root_cause ==
    record.root_cause THEN outcome == merged AND no new entry created.
  checked_by: KB Agent

### Status_Transition

R06:
  rule: >
    On a successful contribution event (outcome: new-entry or merged),
    KB Agent must atomically transition the source learning record from
    status: open to status: actioned, and record actioned_by:
    (KB Agent's agent_id) and actioned_at: (timestamp of the contribution
    event). The KB write and the learning record status update must
    both succeed or both be rolled back. A KB entry that exists without
    a corresponding status: actioned transition on its source record(s) is
    an integrity violation.
  test: >
    For each learning_id in any KB entry's source_records list: the
    original learning record has status: actioned AND actioned_at is
    non-null AND actioned_at >= the KB entry's creation or last-updated
    timestamp. Absence of actioned transition on a contributed record
    triggers an integrity-violation audit event.
  checked_by: KB Agent; Audit Trail Agent; Quality Monitor

R07:
  rule: >
    KB Agent may dismiss a learning record (status: dismissed) when it
    is a near-duplicate of an existing KB entry whose severity is equal
    to or greater than the candidate record's severity. Severity ordering
    for this rule: critical > major > minor > observation. sysadmin:dlm-sysadmin
    may dismiss any open learning record regardless of deduplication
    status. Dismissed records are retained in the learning record store;
    they must not be deleted. actioned_by and actioned_at must be set
    on dismissal, per DLMS-2026-0034 V10.
  test: >
    For any dismissed record: either (a) a near-duplicate entry exists
    in the KB with severity >= the dismissed record's severity; or (b)
    the dismissal was performed by sysadmin:dlm-sysadmin. Dismissals
    that do not satisfy either condition are unauthorised and trigger
    a policy-violation audit event.
  checked_by: KB Agent; Audit Trail Agent

### Contributor_Restriction

R08:
  rule: >
    Only KB Agent and sysadmin:dlm-sysadmin may write to the KB directory
    or update the status, actioned_by, or actioned_at fields of any
    learning record. Any other agent performing these operations is
    acting outside its context boundary per Agent Context Boundary Policy
    (DLMS-2026-0016) and produces a context-boundary-violation audit event.
  test: >
    For each KB write and each learning record status update: the
    acting agent_id is either the registered KB Agent identity or
    sysadmin:dlm-sysadmin. All other agent_ids are unauthorised and
    trigger a context-boundary-violation audit event per DLMS-2026-0015.
  checked_by: Audit Trail Agent; Agent Behaviour Analyst

### Context_Boundary

R09:
  rule: >
    KB Agent's reads list is confined to: (a) the open learning records
    queue — the set of records with status: open awaiting processing;
    and (b) the specific target slot directory (kb/{stage}/{finding_type}/)
    for deduplication checks per R05, limited to the slot matching the
    current candidate record. KB Agent must not read corpus policy
    documents, stage artefact templates, created documents, the audit
    log, other KB slots not matching the current candidate, or any other
    artefact during a contribution event.
  test: >
    All reads by KB Agent during a contribution task are confined to the
    open learning records queue and the single target slot directory.
    Any read outside this set is a context boundary violation per
    DLMS-2026-0016.
  checked_by: Audit Trail Agent; Agent Behaviour Analyst

### Audit

R10:
  rule: >
    Every KB contribution event must produce a kb-record-contributed audit
    event. The event must contain: learning_id, stage, finding_type,
    severity, outcome (new-entry | merged | dismissed | contribution-skipped),
    and — when outcome is contribution-skipped — the list of failing
    DLMS-2026-0034 validation rule IDs.
  test: >
    For each contribution attempt: a kb-record-contributed audit event
    with all required fields exists before any subsequent processing
    of other records in the same queue pass. Absence of this event is
    itself a Tier 3 audit failure per DLMS-2026-0015.
  checked_by: Audit Trail Agent; Quality Monitor

## EXCEPTIONS_PROCESS
Tier 3 exceptions are permitted on a time-limited basis with SysAdmin
approval. To request an exception to any rule in this policy: (1) The
requesting agent produces a policy-exception-request artefact addressed
to the SysAdmin directive queue, citing the rule reference, the reason
the rule cannot be satisfied, and proposed mitigating controls. (2)
sysadmin:dlm-sysadmin reviews and, if approved, issues a
policy-exception-grant directive specifying the rule, the scope, the
expiry date, and audit conditions. (3) The exception is logged as a
policy-exception audit event and is visible in the next CI cycle report.
No exception may extend beyond 90 days without renewal. No exception may
waive R08 (contributor restriction).

## ENFORCEMENT
  primary_agent:    KB Agent; Audit Trail Agent
  gate_positions:
    - Per-learning-record at contribution time: KB Agent validates R01–R05
      for each record before writing
    - Per-contribution-event: Audit Trail Agent validates R10 event
      completeness immediately after each write
    - Per-CI-cycle: Quality Monitor reviews contribution metrics and
      checks R06 integrity (all KB entries have corresponding actioned
      learning records)
  audit: >
    All kb-record-contributed events are logged per R10. Context boundary
    violations by KB Agent (R09 breach) are logged as
    context-boundary-violation events per DLMS-2026-0015. Contributor
    restriction violations (R08 breach) produce an immediate alert.
    Integrity violations (R06 rollback failures) produce an
    integrity-violation event requiring SysAdmin review.
  violation_type:   Tier 3 operational violation; R08 breaches are also
                    Tier 2 context boundary violations per DLMS-2026-0016
  escalation: >
    Context boundary violations (R08, R09 breaches) are immediately
    escalated to the SysAdmin directive queue per Policy Governance Policy
    (DLMS-2026-0001). Systematic contribution failures — same validation
    rule failing across multiple records in a single CI cycle — trigger
    a SysAdmin review request from the Quality Monitor.

## REVIEW_SCHEDULE
  interval_max:      6 months (Tier 3 maximum)
  trigger_conditions:
    - TMPL-learnings-001 (DLMS-2026-0034) is amended in a way that
      changes FIELD_04 stage values, FIELD_06 finding_type values,
      FIELD_13 status transitions, or any of V01–V11 — mandatory trigger;
      R01–R05 and R07 must be updated to reflect the revised schema.
    - Agent roster changes alter the identity or role of the KB Agent
      or the Learning Synthesizer in a way that affects R08 contributor
      restriction or independence requirements.
    - CI cycle reports consistently show contribution-skipped rates
      exceeding 10% of records in a cycle, suggesting a systematic
      conformance gap in learning record production upstream.
    - Learning Synthesis Policy (DLMS-2026-0064) is amended in a way
      that changes how synthesis consumes KB entries, requiring review
      of KB slot structure or status transition rules.
