## SUMMARY
This policy governs the retirement, de-registration, and archival of all DLMS
agent classes and their associated artefacts. Retirement is a terminal
lifecycle transition: retired agent classes cannot be reactivated, their
role_ids cannot be reassigned, and their instruction files are retained as
governance artefacts under RC-permanent. Retirement of any Tier 1–14 agent
requires SysAdmin (Tier 14) approval; Tier 15B manages its own retirements
under this policy without an external approval gate.

## SCOPE
Applies to: all DLMS agent classes across all tiers at the time of retirement;
all instruction files, skill files, and agent specification documents
associated with the retiring agent class; all entries in the TypeDB
agent_class entity, tool-access-registry, event-type-registry, and
dlms-agent-roster.md that reference the retiring agent; the Audit Trail Agent
for retirement event logging.

Excludes: instruction refinement for active agents (owned by Tier 13 CI);
suspension of a temporarily inactive agent class (not governed — an agent
class is either active or retired; no suspended state exists); tool
decommissioning within the tool-access-registry where no agent is being
retired (governed by Tier 14 SysAdmin procedures).

## DEFINITIONS

active agent class:
  An agent class with status: active in the TypeDB roster, with at least one
  entry in the tool-access-registry. An active agent class may be invoked by
  an orchestrator and may receive task dispatches through the DLMS pipeline.

dependent agent:
  An agent class whose tool-access-registry entries, instruction file READS
  section, or approved specification explicitly references the retiring agent
  class as a required input, an invocable subagent, or a named orchestrator.
  A dependent agent's operation is materially affected by the retiring agent's
  removal from the system.

impact analysis:
  A structured artefact produced by the agent-retirement-coordinator that
  enumerates: (1) all agent classes in the roster that are dependent on the
  retiring agent, (2) the specific dependency type for each (invocation
  dependency, READS dependency, or tool dependency), and (3) the proposed
  resolution for each dependency before retirement proceeds.

retirement:
  The terminal lifecycle transition that sets an agent class status to retired
  in the TypeDB roster, removes the agent's entries from the active
  tool-access-registry, and produces an agent_retired audit event. Retirement
  is permanent and irreversible under this policy.

retirement request:
  A formalised intake artefact conforming to TMPL-agent-request-001
  (DLMS-2026-0112) with request_type: retire_agent. The mandatory starting
  artefact for any retirement workflow. No retirement work may begin without
  an approved retirement request with a populated approval_artefact_id.

sysadmin approval artefact:
  A formal approval record produced by sysadmin:dlm-sysadmin, recorded in
  the audit trail, that authorises the retirement of a specific agent class.
  Required for all Tier 1–14 retirements. Contains: role_id of the retiring
  agent, issuing actor_id, timestamp, and a non-null
  sysadmin_approval_artefact_id that is referenced in the retirement request.

## RULES

### Approval_Gate

R01:
  rule: >
    Retirement of any agent class with tier integer <= 14 requires a
    sysadmin approval artefact issued by sysadmin:dlm-sysadmin before
    the retirement request may be submitted. The retirement request payload
    must contain a non-null sysadmin_approval_artefact_id that resolves to
    a valid SysAdmin approval audit event with timestamp preceding the
    retirement request submission. The agent-retirement-coordinator must
    assert this reference before calling roster.retire.
  test: >
    For every agent_retired event where the retiring agent's tier is <= 14:
    the retirement request artefact contains a non-null
    sysadmin_approval_artefact_id AND a sysadmin approval audit event with
    matching artefact id exists with timestamp preceding the agent_retired
    event. Any agent_retired event for a tier <= 14 agent without this
    reference is a policy violation requiring immediate SysAdmin escalation.
  checked_by: agent-retirement-coordinator (pre-call assertion);
              Audit Trail Agent; CI agent-behaviour-monitor

R02:
  rule: >
    Tier 15B agent classes may be retired without external SysAdmin approval.
    The retirement request must still be produced, approved internally by the
    agent-creation-orchestrator, and include a populated approval_artefact_id.
    The approving orchestrator must confirm that the impact analysis (R03) is
    complete and all dependencies are resolved before marking the request as
    approved. The agent-creation-orchestrator may not approve a Tier 15B
    retirement request that it initiated — a separate orchestrator invocation
    acting in the approval role is required.
  test: >
    For every agent_retired event where the retiring agent's tier_label is
    "15B": an approval_artefact_id is present in the retirement request AND
    an agent_request_approved audit event for this role_id exists with
    timestamp preceding the agent_retired event.
  checked_by: agent-retirement-coordinator; Audit Trail Agent

### Impact_Analysis

R03:
  rule: >
    Before calling roster.retire for any agent class, the
    agent-retirement-coordinator must produce a complete impact analysis
    artefact. The impact analysis must enumerate all dependent agents
    (as defined in this policy's DEFINITIONS), specify the dependency type
    for each, and declare the resolution for each dependency. The
    agent-creation-orchestrator must confirm the impact analysis artefact
    exists before dispatching the agent-retirement-coordinator to proceed
    with de-registration. An impact analysis with unresolved dependencies
    blocks retirement.
  test: >
    For every retirement workflow: an impact analysis artefact exists in the
    audit trail with timestamp preceding the agent_retired event AND the
    artefact's dependency resolution field is non-empty AND all listed
    dependent agents have status: resolved in the impact analysis before
    retirement proceeds.
  checked_by: agent-creation-orchestrator; agent-retirement-coordinator

R04:
  rule: >
    All dependent agents identified in the impact analysis must be fully
    resolved before the retiring agent class may be de-registered. Resolution
    means one of: (a) the dependent agent's instruction file has been updated
    to remove the dependency and re-verified per DLMS-2026-0108 R03, (b) the
    dependent agent has itself been retired under this policy, or (c) a
    SysAdmin directive explicitly states the dependency is non-operational
    and may be removed without re-verification. No partial resolution is
    accepted; a single unresolved dependency blocks retirement.
  test: >
    For every dependent agent listed in the impact analysis: a re-verification
    artefact or a retirement audit event or a SysAdmin waiver directive exists
    with timestamp preceding the agent_retired event for the primary retiring
    agent. Any dependent without one of these three resolution types blocks
    the retirement.
  checked_by: agent-retirement-coordinator; agent-creation-orchestrator

### Finality_and_Identity

R05:
  rule: >
    Retired agent class status is terminal. An agent class set to status:
    retired in the TypeDB roster may not be reactivated, reinstated, or
    transitioned to any other status. No update operation on a retired
    agent class is permitted except appending supplementary audit annotations.
    If the operational need arises for an agent filling the same function,
    a new creation request with a new role_id must be submitted under
    DLMS-2026-0108.
  test: >
    For every agent_class entity in TypeDB with agent_status: retired: no
    subsequent write transaction updates agent_status to any other value.
    Any attempt to update a retired agent's status constitutes an integrity
    violation and is blocked at the roster.write handler.
  checked_by: roster.write handler (pre-write assertion);
              Audit Trail Agent; CI data-integrity-monitor

R06:
  rule: >
    Once an agent class role_id appears in any agent_retired audit event,
    that role_id is permanently reserved and may not be assigned to any
    new agent class in any future creation request. The
    agent-request-handler must validate role_id uniqueness against both
    active and retired roster entries when processing a new creation
    request.
  test: >
    For every new agent creation request: the proposed_role_id does not
    match any role_id in the TypeDB agent_class entity regardless of
    agent_status. Matching against a retired role_id constitutes a
    uniqueness violation and the request must be rejected.
  checked_by: agent-request-handler (pre-write assertion); roster.write handler

### Archival_of_Artefacts

R07:
  rule: >
    Instruction files (.agent.md) and skill files (SKILL.md) of retired agent
    classes must not be deleted. They must be retained under RC-permanent per
    the Retention Schedule (DLMS-2026-0022). The agent-retirement-coordinator
    must move the instruction file to an archive path following the convention
    .github/agents/retired/{role_id}.agent.md and record the archive path in
    the agent_class entity's agent_retired_by field. Deletion of instruction
    or skill files of retired agents is a permanent data loss violation.
  test: >
    For every agent_retired event: the file at the instruction_path recorded
    in the agent_class entity is either (a) present at an archive path matching
    .github/agents/retired/{role_id}.agent.md OR (b) a SysAdmin directive
    explicitly waives archival for this role_id with a documented retention
    justification. Absence of the file without a waiver is a retention
    violation.
  checked_by: agent-retirement-coordinator; CI data-integrity-monitor

R08:
  rule: >
    Agent specification documents (corpus artefacts) produced during the
    creation of a retired agent class are retained in the DLMS corpus under
    their original doc_id and status: archived. They must not be deleted
    from the corpus or removed from the corpus index. The retired agent's
    spec_doc_id remains valid and searchable as a historical governance
    record.
  test: >
    For every agent class with agent_status: retired: the document at
    spec_doc_id exists in the corpus with status: archived (not deleted)
    AND its entry remains in corpus-index.md.
  checked_by: agent-retirement-coordinator; CI data-integrity-monitor

### De_Registration

R09:
  rule: >
    On confirmed retirement, the agent-registry-updater must remove all
    active tool-access-registry entries for the retiring agent class. Any
    tool whose permitted_agent_roles list included only the retiring agent
    must be either removed from the registry or reassigned to a successor
    agent class as directed by the impact analysis. Orphaned tools — tools
    with no valid permitted_agent_roles after retirement — are not permitted
    and must be resolved before retirement is finalised.
  test: >
    After every agent_retired event: no entry in the tool-access-registry
    lists the retired role_id in permitted_agent_roles AND no tool whose
    original sole permitted role was the retiring agent remains in the
    registry with an empty permitted_agent_roles field.
  checked_by: agent-registry-updater; CI agent-behaviour-monitor

R10:
  rule: >
    The agent-registry-updater must emit an agent_retired audit event as
    part of the same atomic transaction with roster.retire. The event
    payload must include: role_id, tier, tier_label, retired_by (the
    actor_id of the initiating principal), and sysadmin_approval_artefact_id
    (non-null for Tier 1–14; null for Tier 15B where internal approval
    applies). This mirrors the co-transactional audit requirement stated
    in DLMS-2026-0108 R10.
  test: >
    For every roster.retire call: an agent_retired audit event with the same
    role_id is written in the same transaction_id. Any roster.retire that
    does not produce a co-transactional audit event is a data integrity
    violation.
  checked_by: Audit Trail Agent; nexus:gateway; CI data-integrity-monitor

## EXCEPTIONS_PROCESS
Exceptions to rules in this policy require SysAdmin approval. R01 (SysAdmin
approval for Tier 1–14 retirement), R03 (impact analysis required), R04
(dependents resolved before retirement), R05 (finality of retired status),
and R06 (role_id reservation) are foundational rules that may not be waived
under any conditions. R07 and R08 (artefact retention) may be waived by a
SysAdmin directive with a documented retention justification, subject to the
constraints of DLMS-2026-0022 (Retention Schedule). No exception may exceed
90 days without renewal.

## ENFORCEMENT
  primary_agent:    agent-retirement-coordinator; agent-registry-updater;
                    agent-creation-orchestrator; Audit Trail Agent
  gate_positions:
    - Retirement Stage R1 (Request): agent-request-handler validates
      proposed_role_id not already retired (R06); agent-creation-orchestrator
      confirms SysAdmin approval artefact reference for tier <= 14 (R01)
    - Retirement Stage R2 (Impact Analysis): agent-creation-orchestrator
      confirms impact_analysis artefact is complete with no unresolved
      dependencies before dispatching to Stage R3 (R03, R04)
    - Retirement Stage R3 (De-registration): agent-retirement-coordinator
      asserts sysadmin_approval_artefact_id for tier <= 14 (R01) before
      calling roster.retire; validates no orphaned tools remain (R09)
    - Post-retirement: agent-retirement-coordinator confirms instruction file
      archived at correct path (R07); agent-registry-updater confirms
      co-transactional audit event (R10)
  audit: >
    All retirement events emit agent_retired with full payload (R10). Impact
    analysis artefacts are logged with role_id and dependency enumeration.
    R05 and R06 violations (reactivation or role_id reuse attempts) are
    immediate SysAdmin escalation. R07 retention violations are flagged in
    the next CI cycle report.
  violation_type:   Tier 15B operational violation
  escalation: >
    R01, R03, R04, R05, R06 violations are immediate SysAdmin escalation.
    R07, R08, R09, R10 violations are flagged in the CI cycle report and
    must be resolved before the retirement is considered complete.

## REVIEW_SCHEDULE
  interval_max:     6 months
  trigger_conditions:
    - A new tier designation is introduced that falls outside the current
      "tier <= 14 requires SysAdmin approval" rule scope
    - The Retention Schedule (DLMS-2026-0022) is amended in a way that
      changes the retention class applicable to instruction files or
      agent specification documents
    - Agent Creation and Lifecycle Policy (DLMS-2026-0108) is amended in
      a way that changes the retirement workflow or stage definitions
    - A systematic pattern of retirement violations is detected by
      Tier 13 CI (e.g. multiple attempted role_id reuses or orphaned tools)
