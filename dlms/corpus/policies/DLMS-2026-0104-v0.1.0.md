## SUMMARY
This policy governs the Tier 15 Nexus Infrastructure Agent team: the agents that
design, implement, test, and maintain the Nexus MCP server infrastructure. It defines
agent roles, tool assignment, the mandatory plan-build-test separation, rollback
requirements, registry obligations, and the governance of both the nexus-internal and
nexus-external MCP servers across initial build phases and ongoing maintenance.

## SCOPE
Applies to: all Tier 15 agents operating on Nexus infrastructure tasks, including MCP
  tool implementation, TypeDB schema, corpus import pipelines, registry files, and
  server configuration files.
Applies to: all infra work items — initial Nexus roadmap phases 0–11 and all ongoing
  maintenance tasks triggered by CI cycle recommendations or FO directives.
Excludes: document lifecycle pipeline work (Tiers 1–14); SysAdmin governance corpus
  updates (Tier 14); CI cycle monitoring operations (Tier 13).

## DEFINITIONS

infra_work_item:
  A bounded unit of Nexus infrastructure work assigned its own plan, DoD, execution,
  review, and verification sequence. Maps to a Nexus roadmap phase (0–11) or a
  maintenance task initiated by a SysAdmin briefing or FO directive.

nexus_stack:
  The full technical scope governed by Tier 15: TypeDB schema (nexus/src/db/schema.tql),
  MCP tool handlers (nexus/src/tools/**), both MCP servers (nexus-internal, nexus-external),
  the Tool Access Registry (dlms/registry/tool-access-registry.md), the Event Type
  Registry (dlms/registry/event-type-registry.md), seed scripts (nexus/src/seed/**),
  and related configuration files (nexus/docker-compose.yml, .vscode/mcp.json).

plan_artefact:
  The infra-plan-[phase].md file produced by the Infra Planner. Must include: approach,
  list of affected files, rollback_procedure, and test criteria. No execution agent may
  begin work before this artefact exists.

infra_dod:
  The infra-dod-[phase].md file produced by the Infra DoD Agent before execution begins.
  Defines the binary criteria the Infra Verifier checks. Must be produced by a different
  agent than the Infra Executor.

rollback_procedure:
  A documented, executable sequence of steps that restores the nexus_stack to a
  known-good state if infra implementation fails or produces regressions. Required field
  in every plan_artefact. A plan_artefact with a null or empty rollback_procedure is a
  gate failure and blocks invocation of the Infra Executor.

infra_executor:
  The sole Tier 15 agent authorised to write to nexus/src/ and modify nexus
  infrastructure files. Holds infra.writeImplementation tool. Holds no verification tool.

infra_verifier:
  The structurally independent Tier 15 agent that verifies implementation against
  infra_dod. Shares no tool with infra_executor. Produces a binary VERIFIED/FAILED
  result. Never revises or fixes — only verifies.

## RULES

### Separation_Rules

R01:
  rule:       Plan, execution, and verification of any infra_work_item must be performed
              by three structurally distinct agents: Infra Planner, Infra Executor, Infra
              Verifier. No agent may occupy more than one of these three roles in the
              same infra_work_item.
  rationale:  Enforces Principle 5 (Verification Independence) at the infrastructure layer.
  checked_by: Infra Verifier (confirms plan_artefact actor_id ≠ executor actor_id in audit
              trail before issuing VERIFIED)

R02:
  rule:       The Infra DoD Agent must write infra_dod before the Infra Executor is invoked.
              The Nexus Infrastructure Orchestrator must gate Executor invocation on existence
              of infra_dod. Absence of infra_dod is a hard gate failure — not a warning.
  rationale:  Enforces Principle 11 (Definition Precedes Execution).
  checked_by: Nexus Infrastructure Orchestrator (gate check); Infra Verifier

R02a:
  rule:       Every infra_dod must declare an `impact_class` field. The impact_class must
              be computed using the two-dimensional Impact × Uncertainty classification
              matrix defined in DLMS-2026-0107. Absence of impact_class is a hard gate
              failure — the Nexus Infrastructure Orchestrator must not invoke the Infra
              Executor or any DoD authorship pipeline step without impact_class declared.
  rationale:  Makes risk classification explicit and auditable. impact_class determines
              the DoD authorship pattern for the work item.
  checked_by: Nexus Infrastructure Orchestrator (gate check); Infra Verifier

R02b:
  rule:       For infra_work_items classified RC-high-impact: the infra_dod must be
              produced by two independent DoD agents (Infra DoD Author — Completeness
              and Infra DoD Author — Adversarial) operating in parallel, then
              consolidated by the Infra DoD Synthesizer per DLMS-2026-0107 Synthesizer
              Rules S01–S05. The Nexus Infrastructure Orchestrator must use the
              HIGH_IMPACT_PIPELINE variant defined in DLMS-2026-0105. A canonical DoD
              produced from a single draft is non-compliant.
  rationale:  Enforces PF1 (Cognitive Diversity By Design) and T6 (Resilience Through
              Structure). Single-perspective DoD on high-impact work is a structural
              single point of failure.
  checked_by: Infra Verifier (confirms both draft artefact paths exist); Nexus
              Infrastructure Orchestrator (gate check)

R02c:
  rule:       For infra_work_items classified RC-critical: the infra_dod must be produced
              by three independent DoD agents (Completeness, Adversarial, and Efficiency
              orientations) in parallel, consolidated by the Infra DoD Synthesizer
              applying S01–S06 (Security overlay mandatory if any Security overlay
              trigger is present). After the Synthesizer writes the canonical infra_dod,
              a human review gate must be satisfied — FO or delegate must explicitly
              approve the infra_dod — before the Infra Executor is invoked. Phase 2
              (MCP Core Infrastructure) is permanently RC-critical per DLMS-2026-0107.
  rationale:  RC-critical work has both high impact and high uncertainty — maximum
              cognitive diversity is proportional to risk. The human gate reflects P3
              (Structural Ethics) for work touching the DLMS trust foundation.
  checked_by: Nexus Infrastructure Orchestrator (human approval on record); Infra
              Verifier; SysAdmin Governance Agent

R03:
  rule:       The Infra Executor is the ONLY Tier 15 agent authorised to write to nexus/src/
              or to modify nexus infrastructure configuration files. No other Tier 15 agent
              may hold infra.writeImplementation or any tool scoped to write paths within
              nexus/src/ or nexus/docker-compose.yml.
  rationale:  Enforces Principle 9 (tool possession = structural authority) and minimises
              the surface area of infra mutation.
  checked_by: SysAdmin Governance Agent; Tool Access Registry (enforced at gateway)

R04:
  rule:       The Infra Verifier must not hold any tool also held by the Infra Executor.
              The intersection of the Infra Executor tool set and the Infra Verifier tool
              set must be empty. This is verified against TAR-001 before any infra_work_item
              begins.
  rationale:  Structural independence — an agent cannot verify work if it could have
              produced it. Enforces Principle 5 and Principle 9.
  checked_by: SysAdmin Governance Agent; Infra Verifier (self-checks own tool list)

### Rollback_Rules

R05:
  rule:       Every plan_artefact must contain a populated rollback_procedure section before
              the Nexus Infrastructure Orchestrator may invoke the Infra Executor. A
              plan_artefact with a null or empty rollback_procedure is a hard gate failure.
  checked_by: Nexus Infrastructure Orchestrator (gate check); Infra Verifier

R06:
  rule:       The Infra Executor must not delete or destructively overwrite any existing
              nexus infrastructure component without confirming: (a) the rollback_procedure
              covers restoration of that component, and (b) the infra_dod specifies the
              post-state of the modified component.
  checked_by: Infra Verifier (checks infra_dod coverage of all affected files)

### Registry_Rules

R07:
  rule:       New event_type values required by Tier 15 tool handlers must be added to the
              Event Type Registry (dlms/registry/event-type-registry.md) before the tool
              handler that produces them is deployed or tested. Registry-first, not code-first.
  checked_by: Infra Verifier (confirms registry entries exist before submitVerification passes)

R08:
  rule:       New tool rows required by Tier 15 agents must be added to the Tool Access
              Registry (dlms/registry/tool-access-registry.md) before the MCP gateway is
              started with those tools enabled.
  checked_by: Infra Verifier; MCP Gateway (rejects unregistered tool calls at startup)

R09:
  rule:       The Infra Executor may use the VS Code edit tool to write to nexus/src/ and
              .vscode/mcp.json — these are VS Code layer files (see platform-constraints.md
              D-005). The Infra Executor must NOT use the edit tool to write to dlms/corpus/,
              dlms/registry/, or .github/agents/. Registry file updates go through tool-mediated
              writes; governance corpus updates are Tier 14 responsibility only.
  rationale:  Enforces D-005 (MCP-first for governed artefacts) and Two-Layer Architecture.
  checked_by: Infra Verifier; SysAdmin Governance Agent

### Review_Rules

R10:
  rule:       Before the Infra Verifier is invoked, both the Infra Code Reviewer and the
              Infra Architecture Reviewer must have submitted their review artefacts. The
              Nexus Infrastructure Orchestrator must gate Verifier invocation on existence of
              both infra-code-review-[phase].md and infra-arch-review-[phase].md.
  checked_by: Nexus Infrastructure Orchestrator (gate check)

R11:
  rule:       The Infra Code Reviewer and Infra Architecture Reviewer must be invoked in
              parallel, not sequentially. Their reviews are independent and must not reference
              each other's output. Independence of review perspectives must be preserved.
  checked_by: Nexus Infrastructure Orchestrator (invocation pattern must be PARALLEL_GROUP)

### Audit_Rules

R12:
  rule:       Every infra_work_item must produce, at minimum, the following audit events in
              order: nexus_phase_started, infra_plan_created, infra_dod_created,
              infra_implementation_completed, infra_review_submitted (×2),
              infra_verified OR infra_verification_failed. A verified infra_work_item
              with any of these events absent is a compliance gap.
  checked_by: Infra Verifier; SysAdmin Activity Monitor (Tier 14)

R13:
  rule:       The Infra Executor must not access dlms/corpus/ documents directly. Context
              is delivered exclusively via infra-context-[phase].md produced by the Infra
              Context Curator. Reading corpus documents directly violates the Agent Context
              Boundary Policy (DLMS-2026-0016).
  rationale:  Enforces Principle 7 mininal context discipline.
  checked_by: Infra Verifier (checks executor READS field lists context package only)

## EXCEPTIONS_PROCESS
Tier 15 policy. Exception requests must be submitted to the DLM SysAdmin Agent (Tier 14)
with written justification and a time-limited scope. Rules R01 (three-agent separation),
R02 (DoD before execution), R02a (impact_class required), R02b (dual-DoD for RC-high-impact),
R02c (triple-DoD + human gate for RC-critical), and R04 (zero tool intersection between
Executor and Verifier) are non-waivable — no exceptions apply under any circumstance.
All other rules may receive
time-limited exceptions (maximum 14 days) with SysAdmin Governance Agent approval.
Exceptions produce an exception-grant.md artefact with: rule_id, justification,
expiry_date, approved_by. Expired exceptions revert automatically.

## ENFORCEMENT
primary_agent:    Nexus Infrastructure Orchestrator; Infra Verifier
gate_positions:
  - Pre-planning: Orchestrator confirms infra_work_item is registered before invoking
    Context Curator
  - Pre-execution: Orchestrator checks plan_artefact and infra_dod both exist;
    rollback_procedure is populated; infra_dod actor_id ≠ anticipated Executor actor_id
  - Pre-verification: Orchestrator checks both review artefacts exist before invoking
    Infra Verifier
  - Post-verification: Infra Verifier writes infra-verification-[phase].md with
    VERIFIED/FAILED, criterion-by-criterion evidence, and learnings artefact
  - Ongoing: SysAdmin Activity Monitor (Tier 14) audits tool assignment against TAR-001
    quarterly; alerts on tool_access_denied events from Tier 15 agent roles
audit:            All violations written to audit trail via Audit Trail Agent with fields:
                  rule_id, agent_id, violation_type, timestamp, resolution_status
violation_type:   Tier 15 infrastructure governance violation
escalation:       Per SysAdmin Escalation Policy (DLMS-2026-0080)

## REVIEW_SCHEDULE
interval_max:     6 months
trigger_conditions:
  - MCP SDK version change requiring structural changes to tool handler patterns
  - TypeDB version change requiring schema migration tooling changes
  - Addition of a new Tier 15 agent role not covered by existing rules
  - Any rule violation rate exceeds 10% in a rolling 30-day window
  - Post-incident review following a nexus_phase_failed event or a rollback execution
