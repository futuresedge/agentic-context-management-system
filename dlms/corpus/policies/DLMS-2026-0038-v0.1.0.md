## SUMMARY
This policy governs the versioning of all DLMS corpus documents —
the rules for incrementing version numbers, the requirement that each
new version produces a new file while the prior file is preserved,
the mandatory CHANGE_LOG section, and the authority boundary of the
Version Control Agent. This is a Tier 3 Operational Lifecycle policy.

## SCOPE
Applies to: all DLMS corpus documents and the version field in every
document's frontmatter; the Version Control Agent (the sole agent
authorised to produce new document versions); the Document Author Agent
(content changes that trigger version increments); the Audit Trail Agent
(version increment event logging); the CHANGE_LOG section present in
every DLMS document.

Excludes: version fields in stage artefacts, audit event records,
verification records, and other non-corpus artefacts produced within
the DLMS pipeline. Those artefact types are governed by their
respective templates. This policy governs corpus document versioning only.

Bootstrap exception: DLMS-2026-0001 through DLMS-2026-0013 were authored
with a single version file as part of the bootstrap process. Their version
histories are compact by design. All documents from DLMS-2026-0014 onwards
must comply fully with this policy.

## DEFINITIONS

CHANGE_LOG:
  A mandatory append-only section in every DLMS corpus document that
  records all version increments in reverse-chronological order. Each
  entry records: version, date, author identity, and a brief description
  of the change. The CHANGE_LOG is the version history of the document
  and must be preserved in all versions.

corpus document:
  A file in the DLMS corpus directories (/dlms/corpus/policies/ or
  /dlms/corpus/templates/) with a valid DLMS doc_id in its frontmatter.
  Corpus documents are the objects to which this policy's versioning
  rules apply.

current version:
  The highest-numbered version of a given doc_id by semantic version
  ordering. The current version file is the operative document for all
  agent consumption and pipeline purposes.

MAJOR increment:
  A version increment that raises the first version component (1.0.0 →
  2.0.0). Triggered exclusively by structural changes: adding or removing
  a frontmatter field, changing a section heading, or restructuring the
  document's section schema.

MINOR increment:
  A version increment that raises the second version component (0.1.0 →
  0.2.0, 1.0.0 → 1.1.0). Triggered by any substantive change to body
  content: adding, modifying, or removing rules, definitions, or
  normative statements.

PATCH increment:
  A version increment that raises the third version component (0.1.0 →
  0.1.1). Triggered only by non-semantic corrections: typo fixes,
  formatting corrections, and metadata-only changes that do not alter
  the meaning of any field or rule.

prior version file:
  The file representing a previous version of a document. Prior version
  files are immutable once superseded by a new version. They are retained
  in the corpus permanently (RC-permanent) as the document's history.

Version Control Agent:
  The agent responsible for producing new document version files.
  The Version Control Agent holds a write tool scoped to corpus
  directories and a read tool scoped to the current version of the
  target document. It does not hold approval or status-change tools.

## RULES

### Version_Format

R01:
  rule: >
    The version field must follow semantic versioning format
    MAJOR.MINOR.PATCH where each component is a non-negative integer
    with no leading zeros. The format must match the regex
    ^\d+\.\d+\.\d+$.
  test: >
    version matches regex ^\d+\.\d+\.\d+$
  checked_by: Agent Format Validator; Version Control Agent

R02:
  rule: >
    All corpus documents begin at version 0.1.0. No document may be
    created with any other initial version. The first approved version
    of any document must be 1.0.0.
  test: >
    newly created document.version == '0.1.0' AND
    first approved version == '1.0.0'
  checked_by: Agent Format Validator; Approval Gate Agent

R03:
  rule: >
    Version numbers may only increment — never decrement, reset, or
    skip. No version component may transition to a lower value in any
    subsequent version of the same document.
  test: >
    For versions V1 and V2 of the same doc_id where V2 was created
    after V1: semver(V2) > semver(V1)
  checked_by: Version Control Agent; Agent Format Validator

### Increment_Classification

R04:
  rule: >
    A MAJOR increment must be applied for any structural change to a
    document: adding or removing a frontmatter field, changing a section
    heading, or restructuring the section schema of the document's body.
    A MAJOR increment resets MINOR and PATCH to 0.
  test: >
    IF change includes any of: frontmatter field add/remove,
    section heading rename, body section add/remove:
    version increment type == MAJOR
  checked_by: Version Control Agent; Perspective Reviewer (lens-accuracy)

R05:
  rule: >
    A MINOR increment must be applied for any substantive body content
    change: adding, modifying, or removing rules, definitions, normative
    statements, scope declarations, or enforcement descriptions.
    A MINOR increment resets PATCH to 0.
  test: >
    IF change includes body content modification AND R04 does not apply:
    version increment type == MINOR
  checked_by: Version Control Agent; Perspective Reviewer (lens-accuracy)

R06:
  rule: >
    A PATCH increment must be applied only for non-semantic corrections:
    typo fixes, formatting corrections, and metadata changes that do not
    alter the meaning of any field or rule. A PATCH increment must not
    be used to introduce, modify, or remove normative content.
  test: >
    IF increment type == PATCH:
    no normative content change exists in the diff between prior and
    current version.
  checked_by: Version Control Agent; Agent Format Validator

### File_Preservation

R07:
  rule: >
    Each new version of a document must be created as a new file with
    the version number embedded in the filename per Naming Convention
    Policy DLMS-2026-0003 ({doc_id}-v{version}.md). The prior version
    file must not be modified or deleted.
  test: >
    New version file exists at correct path AND
    prior version file exists unchanged at its original path.
  checked_by: Naming Convention Enforcer; Version Control Agent

R08:
  rule: >
    Prior version files are immutable. No agent may modify a prior
    version file for any reason. A prior version file's content at
    the point it was superseded is its permanent historical record.
  test: >
    For all files F where F.version != current_version_of(F.doc_id):
    no write event exists in the audit trail for F after its supersession.
  checked_by: Audit Trail Agent; Agent Behaviour Analyst

### CHANGE_LOG_Requirement

R09:
  rule: >
    Every corpus document must contain a ## CHANGE_LOG section as the
    penultimate or final section. The CHANGE_LOG section must be
    present in all versions, including the initial 0.1.0 version.
  test: >
    '## CHANGE_LOG' heading exists in every corpus document.
  checked_by: Agent Format Validator; Template Validator

R10:
  rule: >
    The CHANGE_LOG must record every version increment in reverse
    chronological order (most recent first). Each entry must include:
    version number, date (ISO 8601 date), author identity, and a brief
    description of the change. The CHANGE_LOG is append-only — no prior
    entry may be modified or removed.
  test: >
    CHANGE_LOG contains one entry per version increment AND entries
    are in reverse chronological order AND each entry has version,
    date, author, and description fields populated.
  checked_by: Version Control Agent; Agent Format Validator

### Write_Authority

R11:
  rule: >
    Only the Version Control Agent may produce a new version file for
    an existing document. No other agent may create a file with the
    same doc_id as an existing corpus document. The Version Control
    Agent acts only on a version-increment directive issued by an
    authorized stage orchestrator.
  test: >
    For all new version files F where doc_id already exists in corpus:
    F.created_by == 'agent:version-control' AND a version-increment
    directive exists for this doc_id.
  checked_by: Audit Trail Agent; Agent Behaviour Analyst

### Audit_Requirements

R12:
  rule: >
    A version-incremented audit event must be logged for every new
    version file created. The event must include: doc_id, prior version,
    new version, increment type (MAJOR/MINOR/PATCH), version-increment
    directive reference, author, and timestamp.
  test: >
    For every new version file: a version-incremented audit event
    exists with all seven required fields populated.
  checked_by: Audit Trail Agent

## EXCEPTIONS_PROCESS
Tier 3 exceptions are permitted on a time-limited basis with SysAdmin
approval per DLMS-2026-0001. Exception requests for this policy must
cite the specific rule, the reason the rule cannot be satisfied, and
the proposed mitigating control. Exceptions are time-limited to 30 days
maximum. No exception may waive R03 (no version decrement), R07 (file
preservation), R08 (prior version immutability), or R11 (write authority).

## ENFORCEMENT
  primary_agent:    Version Control Agent; Agent Format Validator
  gate_positions:
    - Version creation: Agent Format Validator validates R01–R06 and
      R09 before accepting a new version file
    - Post-creation: Audit Trail Agent validates R12 after each version
    - CI cycle: Agent Behaviour Analyst audits R08 compliance across
      all prior version files
  audit: >
    All version increment events are logged as version-incremented events.
    All increment classification decisions are logged with increment type
    and basis. Any modification attempt on a prior version file is logged
    as a prior-version-write-attempt violation event.
  violation_type:   Tier 3 operational violation
  escalation: >
    R08 violations (prior version modification) and R11 violations
    (unauthorised version file creation) are immediately escalated to
    sysadmin:dlm-sysadmin. All other violations are captured in the
    CI cycle report for SysAdmin review.

## REVIEW_SCHEDULE
  interval_max:      6 months (Tier 3 maximum)
  trigger_conditions:
    - Semantic versioning standard (SemVer) is revised in a way that
      creates ambiguity with DLMS versioning rules
    - A new doc_type is introduced with distinct versioning requirements
    - A systematic PATCH misuse pattern (using PATCH for MINOR changes)
      is detected across multiple documents by CI
    - The Document Schema Policy (DLMS-2026-0004) is amended in a way
      that affects the version field definition
