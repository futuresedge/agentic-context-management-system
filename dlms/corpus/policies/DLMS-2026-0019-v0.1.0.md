## SUMMARY
This policy governs the lifecycle of the DLMS Taxonomy — the single
approved controlled vocabulary from which all document tag values are
drawn. It defines how terms are proposed, approved, deprecated, and
applied; the role of the Classification Agent and Taxonomy Validator;
and the process for maintaining corpus-wide tag consistency when
the taxonomy changes. This is a Tier 3 Operational Lifecycle policy.

## SCOPE
Applies to: the DLMS Taxonomy document (doc_type: taxonomy) and all
versions thereof; the Classification Agent that assigns tags to documents;
the Taxonomy Validator that checks tag compliance; the Tag Index Agent
that maintains the corpus-wide tag index; all documents that carry a
tags[] frontmatter field (i.e. all DLMS documents); any agent or SysAdmin
process that proposes a taxonomy change.

Excludes: the internal classification schemes used by non-DLMS agents
that receive context packages (those are outside DLMS governance); free-text
metadata fields in non-tag positions (governed by Metadata Standard Policy
DLMS-2026-0018); the Taxonomy template itself (governed by TMPL-taxonomy-001
DLMS-2026-0012, which defines structure; this policy defines lifecycle).

Bootstrap exception: Documents DLMS-2026-0001 through DLMS-2026-0013
were tagged before the Taxonomy document was formally approved. Their
tags are treated as compliant by declaration. All subsequent documents
must draw tags exclusively from the approved Taxonomy.

## DEFINITIONS

active term:
  A term in the Taxonomy with status: active. Only active terms may
  be applied to new documents or added to existing documents' tags[].

Classification Agent:
  The agent responsible for assigning tags[] values to documents during
  the Indexing stage. The Classification Agent reads the approved
  Taxonomy and applies active terms consistent with each document's
  content and doc_type.

controlled vocabulary:
  The complete set of active terms defined in the approved Taxonomy
  document. No tag value outside this set is valid in any DLMS document.

corpus tag index:
  The reference document maintained by Tag Index Agent at
  /dlms/registry/tag-index.md, recording for each active Taxonomy term
  the set of all doc_ids tagged with that term, across all document
  versions. Updated at every Indexing stage completion.

deprecated term:
  A term in the Taxonomy with status: deprecated. A deprecated term
  remains in the Taxonomy for historical record but must not be applied
  to new documents. Documents already carrying a deprecated term remain
  valid — they are not retroactively non-compliant — but are flagged
  for migration review.

tag migration:
  The process of updating documents that carry a deprecated or renamed
  term, replacing the old term with its replacement (or removing it if
  no replacement exists). Tag migration is a minor version update to
  each affected document.

Taxonomy Validator:
  The agent responsible for checking that all tag values in a document's
  tags[] field are active terms in the approved Taxonomy. Runs at every
  Agent Format Validation gate.

term proposal:
  A formal request to add a new term, deprecate an existing term, or
  update a term's definition. Proposals are artefacts produced by an
  authorised proposer and submitted to the SysAdmin tier for decision.

## RULES

### Taxonomy_Singleton

R01:
  rule: >
    There must be exactly one taxonomy document with status: approved
    in the DLMS at any time. The Approval Gate Agent must reject
    approval of a new taxonomy version until the prior approved version
    has been atomically transitioned to status: superseded.
  test: >
    count(documents where doc_type == 'taxonomy'
    AND status == 'approved') == 1 at all times.
    The transition from prior approved → superseded and
    new draft → approved must be atomic.
  checked_by: Approval Gate Agent; Status Transition Agent;
              Storage Verifier

R02:
  rule: >
    The approved Taxonomy document is the sole source of valid tag
    values for all DLMS documents. No tag value may be used in any
    document unless it exists in the approved Taxonomy as an active term
    at the time the tag is assigned.
  test: >
    For all documents D: for all T in D.tags[]:
    T IN approved_taxonomy.TERMS where status == 'active'
    at the time T was assigned.
  checked_by: Taxonomy Validator; Classification Agent;
              Agent Format Validator

### Tag_Assignment

R03:
  rule: >
    Tag assignment is performed by the Classification Agent during
    the Indexing stage, immediately after creation or version update.
    The Author Agent may propose initial tags as part of document
    creation, but the Classification Agent has final assignment authority.
    No other agent may write to the tags[] field post-creation except
    the Classification Agent.
  test: >
    All write events to tags[] field after creation have
    actor == agent:classification.
    Author Agent tag proposals are recorded as classification-proposal
    audit events, not as direct field writes.
  checked_by: Audit Trail Agent; Agent Behaviour Analyst

R04:
  rule: >
    Every document must carry its doc_type as a tag (per Metadata
    Standard Policy R17). Beyond the doc_type tag, the Classification
    Agent must assign all active terms that accurately describe the
    document's content, domain, and wave. Over-tagging (assigning
    terms not relevant to the document) is a classification violation.
  test: >
    doc_type IN tags[] AND
    for all T in tags[]: T is semantically applicable to document D.
    Perspective Reviewer (lens-accuracy) checks tag applicability
    at review stage.
  checked_by: Classification Agent (self-check);
              Taxonomy Validator; Perspective Reviewer (lens-accuracy)

R05:
  rule: >
    The Classification Agent must record the rationale for each
    assigned tag in its classification artefact. Tags assigned without
    a documented rationale are a classification quality violation.
  test: >
    Classification artefact produced at Indexing stage contains
    one rationale entry per assigned tag.
  checked_by: Indexing Verifier; CI Verifier

### Term_Proposal_Process

R06:
  rule: >
    Any DLMS agent or SysAdmin may propose a new term, a term
    deprecation, or a definition update by producing a term proposal
    artefact and submitting it to the SysAdmin tier via the standard
    directive queue. No agent may unilaterally add, remove, or change
    a term without SysAdmin approval.
  test: >
    All taxonomy change events in the audit trail are preceded by
    an approved SysAdmin directive event referencing the term proposal.
    Taxonomy changes without a directive reference are prohibited.
  checked_by: Audit Trail Agent; Agent Behaviour Analyst

R07:
  rule: >
    A term proposal artefact must contain: the proposed term slug,
    the proposed domain, the proposed definition, the proposing agent,
    the rationale for the change, and (for deprecations) the
    proposed replacement term or explicit declaration of no replacement.
  test: >
    All term proposal artefacts contain:
    term_slug != null AND domain != null AND definition != null AND
    proposing_agent != null AND rationale != null AND
    (IF deprecation: replacement_term OR no_replacement_declared == true)
  checked_by: SysAdmin review; Agent Format Validator

R08:
  rule: >
    New terms must not duplicate the meaning of an existing active
    term. Before approving a new term, the SysAdmin tier must confirm
    that no existing active term covers the same semantic ground.
    Synonym proliferation is a taxonomy quality failure.
  test: >
    SysAdmin directive approving a new term includes a disambiguation
    statement confirming it is semantically distinct from all active terms.
  checked_by: SysAdmin (pre-approval assessment);
              Perspective Reviewer (lens-accuracy on taxonomy versions)

### Term_Deprecation_and_Migration

R09:
  rule: >
    When a term is deprecated, it must retain status: deprecated in
    the Taxonomy permanently. Deprecated terms are never deleted.
    The deprecated_at timestamp and the replaced_by value (or explicit
    null) must be set atomically when the deprecation takes effect.
  test: >
    For all deprecated terms T:
    T remains in Taxonomy.TERMS AND T.status == 'deprecated' AND
    T.deprecated_at != null AND T.replaced_by is set or null.
  checked_by: Taxonomy Validator; Version Control Agent

R10:
  rule: >
    When a term is deprecated, the Tag Index Agent must identify
    all documents carrying that term within one CI cycle of the
    deprecation taking effect. The Tag Index Agent produces a
    migration candidate report listing all affected doc_ids.
  test: >
    Within one CI cycle of taxonomy deprecation event:
    Tag Index Agent produces migration-candidate-report artefact
    listing all doc_ids where deprecated_term IN doc.tags[].
  checked_by: Tag Index Agent; CI Verifier

R11:
  rule: >
    Tag migration for deprecated terms is performed by the
    Classification Agent under a SysAdmin-approved migration directive.
    Each migrated document receives a patch version increment and
    a CHANGE_LOG entry. Migration of all affected documents must
    complete within three CI cycles of the deprecation.
  test: >
    For all documents in migration candidate report:
    within 3 CI cycles: document version is patched AND
    deprecated_term NOT IN doc.tags[] AND
    CHANGE_LOG contains entry referencing the migration.
  checked_by: Tag Index Agent; CI Verifier; Version Control Agent

### Corpus_Tag_Index

R12:
  rule: >
    The Tag Index Agent must update the corpus tag index at the
    completion of every Indexing stage. The index must reflect the
    current approved tags[] of every approved document. Stale index
    entries are a data integrity violation.
  test: >
    After each Indexing stage completion:
    tag-index-updated audit event exists AND
    index entries for the indexed document reflect its current
    approved tags[].
  checked_by: Tag Index Agent; Indexing Verifier

R13:
  rule: >
    The corpus tag index must be queryable by the following
    dimensions: term (which documents carry this term), doc_id
    (which terms does this document carry), doc_type (which terms
    are used across a doc_type), and wave (which terms are used
    in documents from a given wave). The Tag Index Agent specification
    must declare all four query dimensions.
  test: >
    Tag Index Agent specification (Wave 4) includes all four
    query dimensions in its REQUIREMENTS section.
  checked_by: Tag Index Agent specification;
              CI Verifier

### Taxonomy_Version_Governance

R14:
  rule: >
    Taxonomy version increments follow the versioning rules defined
    in TMPL-taxonomy-001. A patch increment may not be used to add
    or deprecate terms — only to correct typos or formatting.
    Term additions are minor increments. Term removals or hierarchy
    restructuring are major increments.
  test: >
    For all taxonomy version transitions:
    increment type matches TMPL-taxonomy-001 FIELD_04 version rules AND
    patch increment contains no term additions or deprecations.
  checked_by: Version Control Agent;
              Perspective Reviewer (lens-accuracy)

R15:
  rule: >
    Every taxonomy major version increment must be accompanied by
    a migration assessment produced by the Tag Index Agent before
    the new version is approved. The assessment must state the count
    of documents affected by renamed or removed terms and the
    estimated CI cycles required for full migration.
  test: >
    IF taxonomy version transition is major (N.0.0):
    migration-assessment artefact exists AND is referenced in
    the SysAdmin approval directive AND
    assessment.affected_doc_count != null AND
    assessment.estimated_migration_cycles != null.
  checked_by: Approval Gate Agent; Tag Index Agent

## EXCEPTIONS_PROCESS
No exceptions process applies to R01 (taxonomy singleton), R02 (tags
must be active terms), or R09 (deprecated terms retained permanently).
These are structural invariants of the controlled vocabulary system.

For all other rules, a documented SysAdmin directive may grant a
time-limited exception for a specific document or migration batch.
Exceptions must specify the affected doc_ids, the rule being excepted,
the duration, and the resolution path. All exceptions are recorded as
taxonomy-policy-exception-granted audit events.

## ENFORCEMENT
  primary_agent:    Taxonomy Validator; Classification Agent;
                    Tag Index Agent
  gate_positions:
    - Agent Format Validation (all stages): Taxonomy Validator
      checks tags[] values against approved Taxonomy (R02)
    - Indexing stage: Classification Agent assigns tags under R03–R05
    - Approval gate for taxonomy documents: Approval Gate Agent
      enforces R01 singleton constraint
    - CI cycle: Tag Index Agent enforces R10, R11, R12, R15
  audit: >
    All taxonomy events are logged via Audit Trail Agent:
    taxonomy-term-added, taxonomy-term-deprecated,
    tag-assigned, tag-migration-completed,
    taxonomy-validation-pass, taxonomy-validation-fail,
    tag-index-updated, migration-candidate-report-produced,
    migration-assessment-produced.
  violation_type:   Tier 3 operational lifecycle violation
  escalation: >
    Taxonomy singleton violations (more than one approved taxonomy)
    escalate immediately to sysadmin:dlm-sysadmin — this is a
    data integrity crisis. Tag validation failures block the
    Agent Format Validation gate and return to the Author Agent
    for correction. Repeated classification violations by the
    Classification Agent escalate after three occurrences in a
    single CI period.

## REVIEW_SCHEDULE
  interval_max:      6 months (Tier 3 maximum)
  trigger_conditions:
    - A new doc_type, wave, or domain area is introduced that
      the current taxonomy does not adequately cover
    - A CI cycle migration report shows more than 20% of active
      documents carry at least one deprecated term (migration lag)
    - The Taxonomy Validator or Classification Agent specification
      is updated in a way that changes tag assignment behaviour
    - A term synonym proliferation pattern is detected (multiple
      active terms covering the same semantic ground)
    - A major version increment of the Taxonomy is approved,
      requiring policy review against the new term structure
