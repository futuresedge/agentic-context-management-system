## SUMMARY
This is the DLMS controlled vocabulary — the single approved taxonomy from
which all tag values across the DLMS corpus are drawn. It contains 44 active
terms organised across five domains: Document Types, Wave and Phase,
Governance and Lifecycle, Quality Verification and Audit, and Technical
Architecture and Operations. The Classification Agent and Taxonomy Validator
consume this document directly at every Indexing stage gate.

## SCOPE
Applies to: all DLMS documents; all tags[] frontmatter fields in the corpus;
the Classification Agent (tag assignment); the Taxonomy Validator (tag
validation); the Tag Index Agent (corpus tag index maintenance). Every valid
tag value used in any DLMS document must be drawn exclusively from the active
terms in this taxonomy.

Excludes: internal agent state identifiers, file path strings, version
strings, doc_ids, agent slugs, and any other structured identifier that
appears in non-tag fields. The taxonomy governs tag values only. Free-text
values in body content fields are not governed by this taxonomy.

Bootstrap exception: Documents DLMS-2026-0001 through DLMS-2026-0013 were
tagged before this taxonomy was formally approved. Their tags are treated as
compliant by declaration. All documents from DLMS-2026-0014 onwards must draw
tags exclusively from the active terms in the current approved version of
this document.

## GOVERNANCE

proposal_process: >
  Any DLMS agent or SysAdmin may propose a new term, deprecation, or
  definition update by producing a term-proposal artefact addressed to
  the SysAdmin directive queue. The artefact must conform to the term
  proposal schema defined in Taxonomy Policy DLMS-2026-0019 R07.
  Proposals are processed in the next available SysAdmin review cycle.
  The proposing agent records the proposal as a taxonomy-term-proposed
  audit event. No term becomes active until a SysAdmin approval
  directive is issued and the Taxonomy is updated via a new version.

approval_authority: >
  sysadmin:dlm-sysadmin is the sole authority for approving taxonomy
  changes. This reflects the corpus-wide impact of taxonomy changes —
  adding a term affects Classification Agent behaviour for all future
  documents; deprecating a term triggers a migration assessment across
  all existing documents. No agent-tier approval is sufficient for
  taxonomy changes.

deprecation_rules: >
  A term is deprecated rather than removed when it is in active use
  across existing documents. Deprecation preserves the term in the
  TERMS list with status: deprecated and a non-null deprecated_at
  timestamp. Deprecated terms must not be applied to new documents.
  Existing documents carrying a deprecated term are not retroactively
  non-compliant but are added to the migration candidate report
  produced by the Tag Index Agent per Taxonomy Policy R10. A term
  is deprecated (not removed) in all cases where existing usage exists.
  Direct removal without deprecation is permitted only for terms
  that were added in error and have never been applied to any document.

migration_process: >
  When a term is deprecated, the Tag Index Agent produces a migration
  candidate report within one CI cycle (Taxonomy Policy R10).
  The Classification Agent performs tag migration under a
  SysAdmin-approved migration directive, patching each affected document
  per Taxonomy Policy R11. Migration must complete within three CI
  cycles of the deprecation. Each migrated document receives a patch
  version increment and a CHANGE_LOG entry stating the migration.
  The Tag Index Agent confirms completion by verifying the deprecated
  term no longer appears in any document's tags[] with status: approved.

prohibited_terms: >
  The following categories of terms will never be added to this
  taxonomy regardless of proposal: (1) free-text descriptors —
  terms that could apply to any document and carry no discriminating
  information; (2) agent-internal identifiers — slugs that identify
  specific agent invocations or instances rather than document
  characteristics; (3) version strings — any term encoding a version
  number; (4) doc_id strings — terms encoding specific document
  identifiers; (5) proper nouns referring to specific documents —
  taxonomy terms must be generalisable, not document-specific;
  (6) compound terms that duplicate the combined meaning of two
  existing active terms — prefer composing existing tags over
  creating redundant compound terms.

## NOTES
All 44 terms in this initial version are drawn directly from the tags[]
fields used across corpus documents DLMS-2026-0001 through DLMS-2026-0020,
plus five anticipatory terms (archival, compliance, lifecycle, schedule,
controlled-vocabulary) required for Wave 5 documents and near-term corpus
growth.

The parent_term hierarchy in v0.1.0 is deliberately shallow — six
parent-child relationships are declared where the semantic subordination
is unambiguous: meta-governance → governance; retention → lifecycle;
versioning → lifecycle; auditability → audit; independence → verification;
multi-perspective → review; context-economy → context-boundary;
schema → metadata. All other terms are top-level within their domain.
Deeper hierarchy may be introduced in future minor versions as the
corpus grows.
