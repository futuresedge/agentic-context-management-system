## SUMMARY
This policy defines the complete, authoritative state machine for DLMS
document status transitions — the five valid states, the permitted
transitions between them, the preconditions each transition requires,
and the agents with authority to execute each transition. All other
DLMS policies that reference status transitions defer to this document
as the single source of truth. This is a Tier 3 Operational Lifecycle policy.

## SCOPE
Applies to: all DLMS documents and the status field in every document's
frontmatter; the Status Transition Agent (the sole agent authorised to
write the status field after document creation); the Approval Gate Agent
(gating draft → approved transitions); the Archival Stage Orchestrator
(gating approved → archived transitions); the Audit Trail Agent (logging
all transition events); any orchestrator or pipeline agent that reads
or acts on a document's status.

Excludes: the initial status assignment at creation (governed by Document
Creation Policy DLMS-2026-0035 R06, which mandates status: draft); status
values in artefacts other than DLMS corpus documents (stage artefacts,
audit events, and verification records have their own status fields
governed by their respective templates).

Bootstrap exception: DLMS-2026-0001 through DLMS-2026-0004 are in draft
status and were produced before the approval pipeline was operational.
Their transition to approved requires SysAdmin-initiated execution of this
policy's transition rules once the pipeline is live.

## DEFINITIONS

state machine:
  The complete, closed set of valid document statuses and the directed
  graph of permitted transitions between them. Any transition not
  explicitly listed in the state machine is invalid and must be rejected.

Status Transition Agent:
  The sole agent authorised to write the status field of a DLMS corpus
  document after creation. The Status Transition Agent acts only on a
  verified transition directive — it does not initiate transitions
  independently.

transition directive:
  A structured instruction produced by an authorised gate agent (Approval
  Gate Agent, Archival Stage Orchestrator, or SysAdmin) that authorises
  the Status Transition Agent to execute a specific transition for a
  specific doc_id. The directive must reference the precondition-met
  evidence for the transition.

transition precondition:
  The set of conditions that must be fully satisfied before a transition
  may execute. Preconditions are structural checks — they cannot be
  waived by assertion or declared satisfied without evidence.

## RULES

### State_Machine_Definition

R01:
  rule: >
    The five valid status values are: draft, under_review, approved,
    superseded, archived. No other value may appear in the status field
    of any DLMS corpus document.
  test: >
    status IN ['draft', 'under_review', 'approved', 'superseded', 'archived']
  checked_by: Agent Format Validator; Status Transition Agent

R02:
  rule: >
    The complete permitted transition graph is:
      draft         → under_review
      under_review  → draft
      under_review  → approved
      approved      → superseded
      approved      → archived
      superseded    → archived
    All other transitions are invalid. Any agent or process that
    attempts an invalid transition must be blocked and the attempt
    logged as a transition-invalid audit event.
  test: >
    For each transition event E: (E.from_status, E.to_status) IN
    permitted_transition_graph.
    If not in graph: reject AND log transition-invalid event.
  checked_by: Status Transition Agent; Audit Trail Agent

### Write_Authority

R03:
  rule: >
    The status field may only be written by: (a) the Document Author
    Agent at creation (setting the initial value of 'draft'), or
    (b) the Status Transition Agent executing an authorised transition
    directive. No other agent may write the status field under any
    circumstances.
  test: >
    For all status field write events:
    event.actor IN ['agent:document-author', 'agent:status-transition'].
    Any write by any other actor is a structural violation.
  checked_by: Audit Trail Agent; Agent Behaviour Analyst

### Transition_Preconditions

R04:
  rule: >
    The transition draft → under_review requires: (a) all 20
    frontmatter fields are non-null where required (per DLMS-2026-0018),
    (b) a completed creation DoD artefact (DLMS-2026-0024) exists for
    this doc_id, and (c) the Author has submitted a transition-request
    event. No precondition may be skipped.
  test: >
    At draft→under_review:
    Agent Format Validator validates frontmatter completeness == PASS AND
    creation-dod.status == 'complete' AND
    transition-request event exists for this doc_id.
  checked_by: Creation Orchestrator; Agent Format Validator

R05:
  rule: >
    The transition under_review → approved requires: (a) a verification
    record (DLMS-2026-0030) exists for this doc_id with status: pass,
    (b) the verification was performed by an agent independent of the
    document's author (DLMS-2026-0014 R01–R04), (c) the Approval Gate
    Agent has issued an approval-gate-pass event, and (d) a
    transition directive has been issued by the Approval Gate Agent.
    All four preconditions must be met simultaneously.
  test: >
    verification-record.status == 'pass' AND
    verification-record.verified_by != document.created_by AND
    approval-gate-pass event exists for this doc_id AND
    transition directive issued by agent:approval-gate.
  checked_by: Approval Gate Agent; Audit Trail Agent

R06:
  rule: >
    The transition under_review → draft (rejection) requires: a
    rejection directive issued by the Approval Gate Agent or a
    multi-perspective review agent, citing at minimum one specific
    failing criterion. A rejection without a cited criterion is invalid.
  test: >
    rejection directive exists with rejection_reason non-null AND
    rejection_reason references at least one specific rule or criterion.
  checked_by: Approval Gate Agent; Audit Trail Agent

R07:
  rule: >
    The transition approved → superseded requires: (a) a superseding
    document exists in approved status, (b) the superseding document's
    supersedes field references this doc_id, and (c) the Status
    Transition Agent has been issued a supersession directive
    simultaneously with the superseding document's approval. The
    superseded_by field of this document must be populated before
    the transition executes.
  test: >
    superseding_doc.status == 'approved' AND
    superseding_doc.supersedes == this.doc_id AND
    this.superseded_by == superseding_doc.doc_id AND
    supersession directive exists.
  checked_by: Status Transition Agent; Approval Gate Agent

R08:
  rule: >
    The transition approved → archived and superseded → archived are
    both exclusively initiated by the Archival Stage Orchestrator
    acting on a completed archival Definition of Done (DLMS-2026-0029).
    No other agent or role may initiate these transitions.
  test: >
    transition directive actor == 'agent:archival-stage-orchestrator' AND
    archival-dod.status == 'complete' for this doc_id.
  checked_by: Status Transition Agent; Archival Stage Orchestrator

### No_Skip_Gates

R09:
  rule: >
    No gate, flag, or configuration may bypass the precondition checks
    for any transition. There are no fast-path, emergency, or bypass
    modes for status transitions. The structural preconditions defined
    in R04–R08 are absolute.
  test: >
    No transition event exists in the audit trail where a precondition
    check was skipped or marked as bypassed.
  checked_by: Audit Trail Agent; Agent Behaviour Analyst; CI Monitor Agent

### Audit_Requirements

R10:
  rule: >
    Every status transition must be logged as a status-transition
    audit event by the Audit Trail Agent. The event must include:
    doc_id, from_status, to_status, transition agent, timestamp,
    directive reference, and precondition-met evidence references.
  test: >
    For every status field change: a status-transition audit event
    exists with all seven required fields populated.
  checked_by: Audit Trail Agent

R11:
  rule: >
    Every invalid transition attempt must be logged as a
    transition-invalid audit event including: doc_id, attempted
    from_status, attempted to_status, requesting actor, and timestamp.
    The document status must be unchanged after an invalid attempt.
  test: >
    For every invalid transition attempt: a transition-invalid event
    exists AND document.status is unchanged from before the attempt.
  checked_by: Status Transition Agent; Audit Trail Agent

## EXCEPTIONS_PROCESS
Tier 3 exceptions are permitted on a time-limited basis with SysAdmin
approval per DLMS-2026-0001. The exceptions process for this policy is
limited to precondition timing only (e.g. a verification record format
variance). The state machine itself (R01–R02) cannot be varied by exception.
Requests must be directed to the SysAdmin directive queue; approvals are
time-limited to 30 days maximum for transition-precondition exceptions.
No exception may waive R03, R09, or R10.

## ENFORCEMENT
  primary_agent:    Status Transition Agent; Approval Gate Agent
  gate_positions:
    - Pre-transition: Status Transition Agent validates preconditions
      R04–R08 before executing any transition
    - Pre-approval: Approval Gate Agent validates R05 preconditions
      as mandatory pre-approval gate condition
    - Pre-archival: Archival Stage Orchestrator validates R08
      preconditions before issuing archival transition directive
  audit: >
    All transitions are logged as status-transition events. All invalid
    attempts are logged as transition-invalid events. All precondition
    checks are logged per DLMS-2026-0015. The audit trail for any
    document's full status history is reconstructible from these events.
  violation_type:   Tier 3 operational violation (R03, R09 violations
                    are escalated as Tier 2 structural violations)
  escalation: >
    R03 violations (unauthorised status write) and R09 violations
    (bypassed gate) are immediately escalated to sysadmin:dlm-sysadmin
    as structural violations. All other violations are captured in the
    CI cycle report for SysAdmin review.

## REVIEW_SCHEDULE
  interval_max:      6 months (Tier 3 maximum)
  trigger_conditions:
    - A new lifecycle state is proposed for the DLMS document lifecycle
    - An invalid transition attempt pattern is detected by CI across
      multiple documents or agents
    - The Approval Gate Agent's verification preconditions are updated
      by an amendment to DLMS-2026-0014 or DLMS-2026-0030
    - The Archival Policy (DLMS-2026-0040) is amended in a way that
      changes archival transition preconditions
