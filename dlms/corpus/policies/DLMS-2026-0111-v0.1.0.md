## SUMMARY
This standard specifies the mandatory structure and field requirements for all
Agent Specification documents produced by Tier 15B under the Agent Creation
and Lifecycle Policy (DLMS-2026-0108). It is a structural standard that
governs what an agent specification document must contain and how its sections
must be formed, ensuring that every specification produced by the
agent-specification-author is verifiable by the agent-specification-verifier
without ambiguity.

## SCOPE
Applies to: every agent specification document produced by Tier 15B as part
of an approved agent creation workflow; all agent classes across all tiers
including Tier 15B itself.

Excludes: agent instruction files (.agent.md), which are governed by the
Agent Instruction File Template (DLMS-2026-0114); skill files (SKILL.md),
which are governed by the Skill File Governance Policy (DLMS-2026-0109);
corpus documents of other doc_types (policy, standard, template, etc.) which
are governed by their respective content templates.

## DEFINITIONS

CONTEXT_BOUNDARY:
  The mandatory tripartite section in an agent specification that declares
  exactly what the agent reads (READS), writes (WRITES), and is explicitly
  forbidden from accessing (NEVER). The CONTEXT_BOUNDARY section of an
  approved specification is the sole authoritative source for the corresponding
  agent instruction file's context boundary declaration.

GOVERNING_POLICIES:
  The mandatory section in an agent specification that lists the doc_ids of
  all DLMS corpus policy and standard documents that govern the agent's
  behaviour. At minimum includes DLMS-2026-0108 and DLMS-2026-0016.

NEVER list:
  The sub-section of CONTEXT_BOUNDARY that enumerates specific files,
  artefact types, tool namespaces, or data sources that the agent is
  structurally prohibited from accessing. A non-empty NEVER list is a
  mandatory requirement for every agent specification. "Nothing" and
  "not applicable" are not valid NEVER entries.

READS:
  The sub-section of CONTEXT_BOUNDARY that names the specific files, tool
  names, or data sources the agent may consume. Must name specific identifiers
  — never tier names, document categories, or "all policies."

speculative tool assignment:
  A tool included in an agent's TOOL_ASSIGNMENT section for which no specific
  task_step can be identified in the agent's workflow. Speculative tool
  assignment is prohibited; every tool must map to a concrete task step.

STAGE_GATES:
  The mandatory section in an agent specification that declares what
  precondition artefacts must exist before the agent begins its task and what
  output artefacts must exist when it completes, enabling gate-checking by
  the agent-creation-orchestrator.

TOOL_ASSIGNMENT:
  The mandatory section in an agent specification that lists every tool the
  agent will hold, with a task_step and justification for each. Formatted as
  a three-column table.

WRITES:
  The sub-section of CONTEXT_BOUNDARY that names exactly one output artefact
  and its location. An agent specification whose WRITES sub-section names
  more than one artefact or omits the location path fails this standard.

## NORMATIVE_REQUIREMENTS

### Identity_and_Purpose

NR01:
  conformance:  MUST
  requirement:  An agent specification document MUST contain an AGENT_IDENTITY
                section as its first body section, declaring: role_id (kebab-case
                slug), tier (integer), tier_label (string, e.g. "15B"), status
                (proposed | approved | active | retired), and request_ref (the
                approval_artefact_id of the originating creation request).
  test:         AGENT_IDENTITY section exists AND contains non-empty values for
                role_id, tier, tier_label, status, and request_ref.
  checked_by:   agent-specification-reviewer; agent-specification-verifier

NR02:
  conformance:  MUST
  requirement:  An agent specification document MUST contain a PURPOSE section
                immediately after AGENT_IDENTITY. The PURPOSE section MUST
                contain exactly one sentence that states what the agent does and
                the specific condition under which it is invoked. Compound
                sentences that describe multiple functions are not permitted;
                they indicate the agent is over-scoped.
  test:         PURPOSE section exists AND contains exactly one sentence AND
                the sentence contains a statement of function AND a statement
                of invocation condition.
  checked_by:   agent-specification-reviewer; agent-specification-verifier

### Context_Boundary

NR03:
  conformance:  MUST
  requirement:  An agent specification document MUST contain a CONTEXT_BOUNDARY
                section with three non-empty sub-sections: READS, WRITES, and
                NEVER. All three sub-sections must be present. A specification
                missing any sub-section fails this standard.
  test:         CONTEXT_BOUNDARY section exists AND READS sub-section is present
                AND WRITES sub-section is present AND NEVER sub-section is present
                AND all three are non-empty.
  checked_by:   agent-specification-reviewer; agent-specification-verifier

NR04:
  conformance:  MUST
  requirement:  The READS sub-section MUST name specific file paths, tool names,
                or named data sources. Category labels (e.g. "all policies",
                "corpus documents", "tier 4 artefacts"), tier names, and wildcard
                references are not permitted entries in READS.
  test:         Every entry in READS is a specific file path (contains / or .),
                a named tool identifier (contains . in namespace.operation format),
                or a named data source identifier. No entry in READS is solely a
                category label or tier name.
  checked_by:   agent-specification-reviewer; agent-specification-verifier

NR05:
  conformance:  MUST
  requirement:  The WRITES sub-section MUST name exactly one output artefact and
                include its storage path. A WRITES sub-section naming zero
                artefacts, more than one artefact, or an artefact without a path
                fails this standard.
  test:         WRITES sub-section contains exactly one artefact entry AND that
                entry includes a non-empty path component.
  checked_by:   agent-specification-reviewer; agent-specification-verifier

NR06:
  conformance:  MUST
  requirement:  The NEVER sub-section MUST contain at least one specific entry.
                Entries of "nothing", "not applicable", "none", or equivalent
                null assertions are not valid. Every agent has at least one
                resource it must not access; if the reviewer cannot identify one,
                the agent's scope is insufficiently narrow.
  test:         NEVER sub-section contains at least one non-empty entry that
                names a specific resource, artefact type, tool namespace, or
                data source. An empty NEVER or a NEVER containing only null
                assertions fails this standard.
  checked_by:   agent-specification-reviewer; agent-specification-verifier

### Tool_Assignment

NR07:
  conformance:  MUST
  requirement:  An agent specification document MUST contain a TOOL_ASSIGNMENT
                section formatted as a markdown table with exactly three columns:
                tool_name, task_step, and justification. Every tool the agent
                will hold must have exactly one corresponding row. No tools may
                appear in the agent's planned tool list without a row, and no
                row may exist for a tool not in the planned tool list.
  test:         TOOL_ASSIGNMENT section exists AND is formatted as a markdown
                table AND the table has exactly three columns named tool_name,
                task_step, and justification AND there is a one-to-one
                correspondence between table rows and planned tools.
  checked_by:   agent-specification-reviewer; agent-specification-verifier

NR08:
  conformance:  MUST
  requirement:  Every row in the TOOL_ASSIGNMENT table MUST have a non-empty
                task_step value that names a specific step in the agent's
                workflow. Generic task_step values such as "general use",
                "as needed", or "miscellaneous" are not permitted and constitute
                speculative tool assignment.
  test:         For every TOOL_ASSIGNMENT row: task_step is non-empty AND does
                not match the pattern /general|as needed|misc|various|all tasks/i.
  checked_by:   agent-specification-reviewer; agent-specification-verifier

NR09:
  conformance:  MUST NOT
  requirement:  An agent specification MUST NOT assign both an execution tool
                and the corresponding verification tool for the same artefact
                type. Specifically: a specification that lists any tool matching
                agentcreation.write* MUST NOT also list
                agentcreation.submitVerification. A specification listing
                agentcreation.submitVerification MUST NOT list any tool matching
                agentcreation.write*.
  test:         TOOL_ASSIGNMENT table does not contain both a tool matching
                agentcreation.write* and agentcreation.submitVerification.
  checked_by:   agent-specification-reviewer; agent-specification-verifier;
                agent-registry-updater (pre-roster.write assertion)

### Governance_and_Gates

NR10:
  conformance:  MUST
  requirement:  An agent specification document MUST contain a GOVERNING_POLICIES
                section listing the doc_ids of all DLMS corpus policy and standard
                documents that govern the agent's behaviour.
  test:         GOVERNING_POLICIES section exists AND contains at least one
                doc_id entry in DLMS-YYYY-NNNN format.
  checked_by:   agent-specification-reviewer; agent-specification-verifier

NR11:
  conformance:  MUST
  requirement:  The GOVERNING_POLICIES section MUST include at minimum
                DLMS-2026-0108 (Agent Creation and Lifecycle Policy) and
                DLMS-2026-0016 (Agent Context Boundary Policy). These two
                documents govern all agent classes in the DLMS and cannot be
                omitted from any agent specification.
  test:         GOVERNING_POLICIES section contains DLMS-2026-0108 AND
                DLMS-2026-0016 as entries.
  checked_by:   agent-specification-reviewer; agent-specification-verifier

NR12:
  conformance:  MUST
  requirement:  An agent specification document MUST contain a STAGE_GATES
                section declaring: (1) PRECONDITIONS — the artefacts that must
                exist before the agent begins its task, and (2) POSTCONDITIONS
                — the artefacts the agent must have produced when it completes.
                Both sub-sections must be non-empty.
  test:         STAGE_GATES section exists AND PRECONDITIONS sub-section is
                non-empty AND POSTCONDITIONS sub-section is non-empty.
  checked_by:   agent-specification-reviewer; agent-specification-verifier

NR13:
  conformance:  SHOULD
  requirement:  An agent specification document SHOULD contain a KNOWN_CONSTRAINTS
                section documenting edge cases, escalation paths, and operational
                limits that the agent-instruction-author must be aware of when
                translating the specification into an instruction file.
  rationale:    KNOWN_CONSTRAINTS reduces the risk of the agent-instruction-author
                making assumptions that deviate from the specification author's
                intent. Its absence is permitted only when the specification
                author has confirmed the agent has no known edge cases.
  test:         KNOWN_CONSTRAINTS section is present OR specification author has
                recorded "No known constraints" with a rationale for its absence.
  checked_by:   agent-specification-reviewer

NR14:
  conformance:  MUST
  requirement:  An agent specification document MUST contain a CHANGE_LOG section
                as its final section, recording version, date, author, and change
                summary for every version.
  test:         CHANGE_LOG section exists AND is the last section in the document
                AND contains at least one entry for version 0.1.0.
  checked_by:   agent-specification-reviewer; agent-specification-verifier

## RATIONALE
Agent specifications are the authoritative source for agent instruction files.
If a specification is structurally ambiguous — missing a CONTEXT_BOUNDARY,
omitting tools from TOOL_ASSIGNMENT, or listing only category labels in READS —
the resulting instruction file will inherit that ambiguity and may violate P7,
P9, or P3 in ways that are not detectable until the agent is deployed. This
standard makes every aspect of an agent specification independently verifiable
before the instruction file is authored, preventing defects from propagating
downstream into the deployed agent.

The prohibition on category labels in READS (NR04) directly enacts P9 (Narrow
Context, Wide Knowledge). The NEVER non-empty requirement (NR06) operationalises
the foundational insight that every context boundary must be explicitly closed:
if an agent can reach a resource and it is not in NEVER, it will eventually
access it. The verifiable one-to-one TOOL_ASSIGNMENT requirement (NR07, NR08)
enacts P7 by preventing context inflation through over-permissioned tool sets
and enforces P3 by making the structural independence check (NR09) mechanical
rather than interpretive.

## REVIEW_SCHEDULE
  interval_max:     6 months
  trigger_conditions:
    - Agent Creation and Lifecycle Policy (DLMS-2026-0108) is amended in a
      way that introduces new mandatory fields or sections for agent
      specifications
    - Agent Context Boundary Policy (DLMS-2026-0016) is amended in a way
      that changes the definition of what constitutes a valid READS entry
    - A systematic pattern of specification failures at the same NR is
      detected by Tier 13 CI, indicating the requirement needs clarification
    - A new agent platform format is adopted that requires additional mandatory
      specification fields not covered by this standard's current requirements
