## SUMMARY
This policy governs the full seven-stage creation and retirement lifecycle for
all DLMS agent classes across all tiers, and is the founding governance
document for Tier 15B (Agent Creation & Lifecycle). It enforces P3 (no
self-certification) across specification, review, and verification stages;
P7 (context economy) in instruction file authoring; and P9 (explicit context
boundaries) as a mandatory element of every agent specification. It applies
recursively to Tier 15B agents themselves and supersedes the informal working
document `dlms/dlms-agent-spec-policy-and-templates.md`.

## SCOPE
Applies to: all DLMS agent class creation, update, deployment, and retirement
workflows regardless of tier; all agent specification documents, agent
instruction files (.agent.md), and skill files (SKILL.md) produced or
maintained by Tier 15B; all request intake artefacts whether initiated by
SysAdmin (Tier 14) or by a Tier 13 CI cycle recommendation; the agent_class
entity in the TypeDB roster database; the tool-access-registry and
event-type-registry at the point of new agent registration.

Excludes: instruction refinement for existing deployed agents (owned by
Tier 13 through the CI improvement cycle); Tier 6 Human-Friendly Production
agent design (deferred); MCP server infrastructure configuration (governed
by Tier 15 Nexus); prompt files (.prompt.md) and workspace instruction files
(.instructions.md) that are not agent definition files.

## DEFINITIONS

agent class:
  A named, versioned definition of an AI participant's role, context boundary,
  tool assignment, and instruction file. The canonical description of what an
  agent is permitted to do and not do. Distinguished from an agent instance,
  which is a specific running invocation of a class.

agent creation request:
  A formalised intake artefact produced by the agent-request-handler conforming
  to TMPL-agent-request-001 (DLMS-2026-0112). The mandatory starting artefact
  for any agent creation or retirement workflow. Work may not begin without an
  approved request artefact with a populated approval_artefact_id.

agent instruction file:
  The operational configuration file that governs a specific agent's runtime
  behaviour. For DLMS agents, this is a .agent.md file (VS Code Copilot format)
  or equivalent platform format. The instruction file is derived directly from
  an approved agent specification and must not diverge from it.

agent specification:
  A formal document produced by the agent-specification-author that defines an
  agent class per DLMS-2026-0111 (Agent Specification Standard). Contains the
  agent's identity, purpose, context boundary (READS/WRITES/NEVER), tool
  assignment table with per-tool justification, governing policies, and stage
  gates. The specification is the authoritative and sole source for the
  instruction file.

context boundary:
  The tripartite declaration within an agent specification and instruction file
  that names what the agent reads (may consume), writes (may produce), and is
  never permitted to access. Defined via READS / WRITES / NEVER sections.
  Required in every agent specification per Principle 9.

retirement:
  The terminal lifecycle transition that sets an agent class status to retired,
  de-registers it from active tool-access-registry entries, and records the
  transition in the audit trail. Retired agent classes may not be reactivated
  under the same role_id; a new creation request with a new role_id is required.

skill file:
  A SKILL.md file containing supplementary content — rubrics, checklists,
  format specifications — that an agent loads on demand when a task requires it.
  Skill files are never loaded at agent startup. They are referenced
  conditionally from the instruction file; their body is loaded only when the
  triggering condition is met.

stage gate:
  A mandatory checkpoint in the agent creation lifecycle at which a required
  artefact must exist and pass independent verification before the workflow
  may advance. The seven stage gates are governed by DoD template
  DLMS-2026-0115.

structural authority:
  An agent's capability is defined entirely by its declared tools list.
  An agent cannot take an action unless it holds the corresponding tool.
  Runtime permission assertions are not structural authority and must not
  substitute for correct tool assignment at specification time.

## RULES

### Request_and_Approval

R01:
  rule: >
    No agent creation or retirement workflow may commence until a formalised
    agent creation request artefact exists and has been approved. The request
    artefact must conform to TMPL-agent-request-001 (DLMS-2026-0112) and must
    be produced by the agent-request-handler using the agentcreation.writeRequest
    tool. The approved request artefact's approval_artefact_id field must be
    populated before any subsequent stage artefact may be produced.
  test: >
    For every agent creation workflow: a request artefact of type
    agent_creation_request with status approved and a non-null
    approval_artefact_id exists in the audit trail — recorded as an
    agent_request_approved event — before any agent_spec_created,
    agent_instruction_created, or agent_deployed event is appended for
    the same role_id.
  checked_by: agent-creation-orchestrator; agent-specification-verifier

R02:
  rule: >
    All agent creation and retirement requests require explicit human approval
    before work begins. Tier 13 CI agents may produce a recommendation or
    flag a gap as evidence_of_need in the request artefact; they may not
    approve requests. The actor_id recorded in the agent_request_approved
    audit event must match the pattern sysadmin:* or a registered human
    principal — never an agent actor_id pattern (agent:*, agentcreation:*,
    ci:*, infra:*).
  test: >
    For every agent_request_approved event: the event's actor_id matches
    sysadmin:* or human:*. An approval event with actor_id matching
    agent:*, agentcreation:*, ci:*, or infra:* constitutes a policy
    violation and must be flagged to SysAdmin immediately.
  checked_by: agent-request-handler; Audit Trail Agent

### Independence

R03:
  rule: >
    The agent-specification-author, agent-specification-reviewer, and
    agent-specification-verifier must be distinct agent identities throughout
    the lifecycle of a single agent creation workflow. The agent that authors
    a specification may not review it. The agent that reviews a specification
    may not verify the resulting instruction file. The agent that authors an
    instruction file may not verify it. These prohibitions apply without
    exception regardless of tier, urgency classification, or SysAdmin directive.
  test: >
    For any completed agent creation workflow: the actor_id in the
    agent_spec_created event, the actor_id in the agentcreation.submitReview
    audit event, and the actor_id in the agent_spec_verified event are three
    distinct values. Any two matching values constitute a P3 independence
    violation and must be escalated to SysAdmin immediately.
  checked_by: agent-specification-verifier; Audit Trail Agent;
              CI agent-behaviour-monitor

R06:
  rule: >
    No agent class may hold both an execution tool and the corresponding
    verification tool for the same artefact type it produces. An agent holding
    any agentcreation.write* tool must not also hold
    agentcreation.submitVerification. An agent holding
    agentcreation.submitVerification must not hold any agentcreation.write*
    tool. This prohibition applies to all tiers including Tier 15B and is
    enforced at registration time before roster.write is called.
  test: >
    For every agent class entry in the tool-access-registry: IF the agent
    holds any tool matching agentcreation.write*, it does not also hold
    agentcreation.submitVerification. IF the agent holds
    agentcreation.submitVerification, it holds no tool matching
    agentcreation.write*. Any co-occurrence is a structural independence
    violation blocked at roster.write.
  checked_by: agent-registry-updater (pre-call assertion);
              CI agent-behaviour-monitor

### Specification_Requirements

R04:
  rule: >
    Every agent specification document must contain a CONTEXT_BOUNDARY section
    with three non-empty sub-sections: READS, WRITES, and NEVER. READS must
    name specific files or tool names — never category labels, tier names, or
    "all documents." WRITES must name exactly one output artefact and its path.
    NEVER must enumerate at least one file, artefact type, or resource the
    agent is explicitly forbidden from accessing. An agent specification without
    a complete, specific, and non-empty CONTEXT_BOUNDARY section fails
    specification review and verification.
  test: >
    For every agent specification document: CONTEXT_BOUNDARY section is present
    AND the READS sub-section is non-empty and names specific resources AND
    the WRITES sub-section names exactly one artefact with a path AND the NEVER
    sub-section contains at least one entry. Absence of any sub-section, or
    READS entries containing only category labels, constitutes a specification
    failure.
  checked_by: agent-specification-reviewer; agent-specification-verifier

R05:
  rule: >
    Every agent specification document must contain a TOOL_ASSIGNMENT section
    structured as a table with three columns: tool_name, task_step, and
    justification. Every tool in the agent's intended tool list must have a
    corresponding row. No tool may appear in a specification without a declared
    task_step and a justification. Speculative tool assignment — any tool for
    which no specific task_step can be identified — is prohibited and
    constitutes a specification failure.
  test: >
    For every agent specification: the TOOL_ASSIGNMENT table is present AND
    every row has non-empty values for tool_name, task_step, and justification
    AND every tool in the agent's planned tool list has exactly one
    corresponding row AND no row exists without a non-empty task_step entry.
  checked_by: agent-specification-reviewer; agent-specification-verifier

### Instruction_File_Requirements

R08:
  rule: >
    Agent instruction file body content must not exceed 400 tokens. This limit
    applies to the body only, excluding YAML frontmatter. Content exceeding
    this limit must be moved to a referenced SKILL.md file and loaded via
    progressive disclosure triggered by the specific task condition that
    requires it. The 400-token limit is a hard constraint; no exception
    mechanism may waive it.
  test: >
    token_count(instruction_file_body, excluding_frontmatter) <= 400. Any
    instruction file whose body exceeds 400 tokens fails verification and
    must be refactored before the corresponding agent class may be deployed.
  checked_by: agent-specification-verifier; Template Validator

R09:
  rule: >
    Every agent instruction file must declare user-invocable: false in its
    frontmatter unless direct human invocation is explicitly required by the
    agent's approved specification and justified in the TOOL_ASSIGNMENT section.
    The deprecated infer field must not be used in any new instruction file.
    All Tier 15B agent classes are pipeline subagents and must declare
    user-invocable: false.
  test: >
    For every agent instruction file: the frontmatter contains a user-invocable
    field AND (user-invocable == false OR user-invocable == true with a
    corresponding justification entry in the specification's TOOL_ASSIGNMENT
    section) AND the infer field is absent.
  checked_by: agent-specification-verifier; Template Validator

### Retirement_Requirements

R07:
  rule: >
    Retirement of any Tier 1 through Tier 14 agent class requires a
    sysadmin_approval_artefact_id in the retirement request payload. This
    reference must resolve to a valid SysAdmin approval artefact issued by
    sysadmin:dlm-sysadmin and recorded in the audit trail before the
    retirement request is submitted. The agent-retirement-coordinator must
    assert this reference before calling roster.retire for any agent class
    with tier integer <= 14. Tier 15B agent classes may be retired under
    this policy without an external approval, subject to the impact analysis
    requirement in DLMS-2026-0110.
  test: >
    For every agent_retired event where the retiring agent's tier is <= 14:
    the retirement request payload contains a non-null
    sysadmin_approval_artefact_id AND a corresponding SysAdmin approval
    audit event exists with timestamp preceding the agent_retired event. An
    agent_retired event for a tier <= 14 agent without this reference is a
    policy violation requiring immediate SysAdmin escalation.
  checked_by: agent-retirement-coordinator (pre-call assertion);
              Audit Trail Agent; CI agent-behaviour-monitor

### Audit_Requirements

R10:
  rule: >
    The agent-registry-updater must emit an audit event for every call to
    roster.write and roster.retire. The audit event must be written in the
    same database transaction as the roster mutation: if either the roster
    write or the audit event append fails, both must roll back atomically.
    The audit event for roster.write must be of type agent_deployed. The
    audit event for roster.retire must be of type agent_retired. Both events
    must include role_id, tier, tier_label, and actor_id in the payload.
  test: >
    For every agent_deployed event: a corresponding roster.write mutation
    exists with the same role_id and the audit event and roster write share
    the same transaction_id. For every agent_retired event: the same
    co-transaction constraint applies to roster.retire. Any roster mutation
    without a co-transactional audit event constitutes a data integrity
    violation.
  checked_by: Audit Trail Agent; nexus:gateway (transaction handling);
              CI data-integrity-monitor

## EXCEPTIONS_PROCESS
Exceptions to rules in this policy require SysAdmin approval. To request an
exception: (1) The requesting principal produces a policy-exception-request
artefact addressed to the SysAdmin directive queue, citing the rule reference,
the operational reason the rule cannot be satisfied, and proposed mitigating
controls. (2) sysadmin:dlm-sysadmin reviews and, if approved, issues a
policy-exception-grant specifying the rule, scope, expiry date (maximum 90
days), and audit conditions. (3) The exception is logged as a
policy-exception audit event visible in the next CI cycle report.

The following rules are foundational and not subject to exception under any
conditions: R01 (approved request required before work begins), R02 (human
approval gate — no agent may approve), R03 (independence of author, reviewer,
and verifier), R06 (no execution and verification co-holding), R07 (SysAdmin
approval required for Tier 1–14 retirement). These rules are directly derived
from P1, P2, and P3 and cannot be waived without undermining the structural
integrity of the DLMS.

## ENFORCEMENT
  primary_agent:    agent-creation-orchestrator; agent-specification-verifier;
                    agent-retirement-coordinator; Audit Trail Agent
  gate_positions:
    - Stage 1 (Request): agent-request-handler validates that no workflow
      artefacts are produced before approval_artefact_id is populated;
      agent-creation-orchestrator blocks advancement without a confirmed
      agent_request_approved event
    - Stage 2 (Problem Analysis): agent-creation-orchestrator confirms
      approved request artefact before dispatching agent-problem-analyst
    - Stage 3 (Specification Review): agent-specification-reviewer enforces
      R04 and R05 before review passes; agent-creation-orchestrator will not
      dispatch Stage 4 without a passed review
    - Stage 4 (Instruction): agent-instruction-author may not proceed without
      a passed specification review artefact
    - Stage 5 (Verification): agent-specification-verifier enforces R03
      (actor_id distinctness), R04, R05, R08, and R09 against the instruction
      file before submitting the verification artefact
    - Stage 6 (Registration): agent-registry-updater enforces R06 (tool
      co-holding check) and R10 (co-transactional audit) via roster.write;
      blocked on a passed verification artefact
    - Retirement (Stage R3): agent-retirement-coordinator enforces R07 before
      calling roster.retire; blocked on sysadmin_approval_artefact_id
      for tier <= 14
  audit: >
    All stage transitions emit audit events per the event-type-registry
    (actor pattern for Tier 15B: agentcreation:*). Independence checks
    (R03, R06) results are logged. Approval events (R02) include the
    approving actor_id. Policy violations are escalated to
    sysadmin:dlm-sysadmin and flagged in the next Tier 13 CI cycle report.
  violation_type:   Tier 15B operational violation
  escalation: >
    R01, R02, R03, R06, and R07 violations are immediate SysAdmin escalation.
    R04, R05, R08, R09, and R10 violations are flagged in the CI cycle report
    and must be resolved before the affected agent class may be deployed or
    retired.

## REVIEW_SCHEDULE
  interval_max:     6 months
  trigger_conditions:
    - A new tier is added to the DLMS agent roster requiring agent class
      definitions beyond Tier 15B's current scope
    - A structural change to the TypeDB agent_class schema affects fields
      governed by this policy's rules
    - The tool-access-registry is extended with a new tool namespace requiring
      corresponding lifecycle governance
    - The Agent Specification Standard (DLMS-2026-0111) is amended in a way
      that affects mandatory specification fields referenced by R04 or R05
    - A systematic creation or retirement failure pattern is detected by
      Tier 13 CI across multiple agent class deployments
