## SUMMARY
This policy governs capability-based access control for all DLMS corpus
documents, mapping each confidentiality classification level to the permitted
agent operations and structural constraints that enforce them. Access authority
derives exclusively from an agent's held tool capabilities and the document's
access manifest — never from runtime declarations, role titles, or agent
assertions. This is a Tier 3 Agent Behaviour policy.

## SCOPE
Applies to: all DLMS agents that read, write, submit, or execute operations
against DLMS corpus documents; the Access Gatekeeper agent; the Audit Trail
Agent; all DLMS documents with a confidentiality classification (C0 through
C3) as defined in Confidentiality Classification Policy (DLMS-2026-0045).

Excludes: access control over non-corpus artefacts such as audit event
records, system logs, and CI reports — those are governed by Audit Trail
Policy (DLMS-2026-0015) and CI Cycle Policy (Wave 13). Excludes the
definition of classification levels and the criteria for assigning them,
which are defined in DLMS-2026-0045.

## DEFINITIONS

access manifest:
  A structured artefact that lists the agent classes and identities
  explicitly permitted to read and write a document at classification level
  C2 or C3. Access manifests are required for all C2 and C3 documents from
  the moment of creation. Access manifest artefacts must be produced using
  TMPL-access-manifest-001 (DLMS-2026-0052).

Access Gatekeeper:
  The agent responsible for evaluating all document access requests before
  permitting any read or write operation. The Access Gatekeeper evaluates
  the document's classification field and the requesting agent's tool
  possession and manifest status. It does not read document body content.

capability-based access:
  An access control model in which an agent's authority to perform an
  operation derives exclusively from its current tool possession and its
  status in the applicable access manifest. An agent that does not hold
  the required tool or manifest entry cannot access the document, regardless
  of any runtime instruction, role title, or agent declaration.

classification level:
  One of four confidentiality levels assigned to a DLMS document per
  Confidentiality Classification Policy (DLMS-2026-0045): C0 (public),
  C1 (internal), C2 (restricted), C3 (confidential). Each level maps to a
  distinct set of access permissions defined in this policy.

need-to-know:
  The operational principle that access to C2 documents is restricted to
  agent classes whose stage function requires the document. Need-to-know is
  operationalised through the access manifest: only agents listed in the
  manifest satisfy the Access Gatekeeper's C2 access check.

## RULES

### Capability_Based_Access

R01:
  rule: >
    All access to DLMS corpus documents is governed by capability-based
    access control. An agent's authority to read, write, or execute
    operations against a document derives exclusively from: (a) the
    agent's currently held tools, and (b) the document's access manifest
    where required. No runtime declaration, role title, or agent assertion
    may grant access authority that is not structurally held.
  test: >
    All document access operations pass through the Access Gatekeeper.
    No read or write proceeds without a preceding access-granted event
    for the requesting agent and target doc_id. Attempts to bypass the
    Access Gatekeeper produce access-violation audit events.
  checked_by: Access Gatekeeper; Audit Trail Agent

R02:
  rule: >
    An agent must not access a document whose classification level exceeds
    the permissions defined in R03–R07 for its tool set and manifest status.
    Classification level is read from the document frontmatter
    confidentiality_class field. If confidentiality_class is null, absent,
    or carries an unrecognised value, the document is treated as C1
    (internal) and a classification-unknown audit event is logged.
  test: >
    For each access attempt: Access Gatekeeper reads confidentiality_class
    AND evaluates against requesting agent tool set and manifest entry.
    Null or absent classification → treat as C1 AND log
    classification-unknown event. Unrecognised value → treat as C1 AND
    log classification-unknown event.
  checked_by: Access Gatekeeper; Audit Trail Agent

### Classification_Permission_Map

R03:
  rule: >
    C0 (public) documents: all registered DLMS agents may read. Write
    authority is governed by stage assignment only, not by classification.
    C0 documents are eligible for external distribution per distribution-
    stage policies. No access manifest is required for C0 documents.
  test: >
    For any registered DLMS agent requesting read access to a C0 document:
    access-granted event is produced without manifest check. Write access
    is evaluated against stage assignment rules only.
  checked_by: Access Gatekeeper

R04:
  rule: >
    C1 (internal) documents: all registered DLMS agents may read. Write
    authority is governed by stage assignment only, not by classification.
    C1 documents must not be included in any external distribution plan.
    No access manifest is required for C1 documents.
  test: >
    For any registered DLMS agent requesting read access to a C1 document:
    access-granted event is produced without manifest check. Attempts to
    include C1 documents in an external distribution plan are blocked by
    the Distribution Orchestrator.
  checked_by: Access Gatekeeper; Distribution Orchestrator

R05:
  rule: >
    C2 (restricted) documents: only agent classes explicitly listed in the
    document's access manifest may read. An agent not listed in the access
    manifest receives access-denied regardless of its tool possession. Write
    authority requires a manifest entry for write operations and stage
    assignment. An access manifest must exist for every C2 document at
    creation; its absence is a configuration error escalated immediately to
    sysadmin:dlm-sysadmin.
  test: >
    For any agent requesting read access to a C2 document: Access Gatekeeper
    reads access manifest AND confirms the requesting agent_class or
    agent_id is listed with access_type covering the requested operation.
    Access manifest absent → access-denied for all agents except
    sysadmin:dlm-sysadmin AND access-manifest-missing audit event produced.
  checked_by: Access Gatekeeper; Audit Trail Agent

R06:
  rule: >
    C3 (confidential) documents: only sysadmin:dlm-sysadmin and agents
    explicitly named in a SysAdmin-issued access directive may read. An
    access manifest must exist and must contain a SysAdmin-signed explicit
    entry for each permitted agent. Write operations to C3 documents require
    a SysAdmin directive specifying the authoring agent and scope. No agent
    may self-authorise access to a C3 document under any conditions.
  test: >
    For any agent other than sysadmin:dlm-sysadmin requesting access to a
    C3 document: Access Gatekeeper confirms agent_id appears in access
    manifest under a SysAdmin-signed entry. Absent entry → access-denied.
    Self-authorisation attempt → access-denied AND access-violation event.
  checked_by: Access Gatekeeper; Audit Trail Agent

R07:
  rule: >
    An access manifest must be produced and registered for every C2 and C3
    document before the document enters the review stage. Access manifests
    must be produced using TMPL-access-manifest-001 (DLMS-2026-0052). For C3
    documents, the manifest requires a SysAdmin-signed attestation block per
    DLMS-2026-0052 V03.
  test: >
    For all C2 and C3 documents: an access manifest conforming to
    TMPL-access-manifest-001 (DLMS-2026-0052) is registered in the
    document's audit trail before the first review-session-opened event
    for that doc_id.
  checked_by: Review Stage Orchestrator; Audit Trail Agent

### Access_Denial_Handling

R08:
  rule: >
    Every access denial must produce an access-denied audit event logged by
    the Audit Trail Agent. The event must include: requesting_agent_id,
    doc_id, classification_level, attempted_operation, and timestamp. No
    access denial may be silent.
  test: >
    For each access denial by Access Gatekeeper: audit event type
    access-denied exists with all five required fields populated.
  checked_by: Audit Trail Agent

R09:
  rule: >
    An agent that receives an access-denied response must invoke its
    raise_uncertainty capability immediately, referencing the access-denied
    audit event. The agent must not attempt to work around the denial by
    substituting another document, requesting a different path, or
    inferring document content from other sources.
  test: >
    For each access-denied event: within the same agent execution session,
    a raise_uncertainty event is produced referencing the access-denied
    event_id. Absence of raise_uncertainty after access-denied constitutes
    a context boundary violation per DLMS-2026-0016.
  checked_by: Audit Trail Agent; Agent Behaviour Analyst

R10:
  rule: >
    If the Access Gatekeeper is unavailable or non-responsive, the
    requesting agent must treat the non-response as access-denied, invoke
    raise_uncertainty, and halt execution. The requesting agent must not
    proceed under an assumption of implicit access.
  test: >
    For each document access attempt where Access Gatekeeper response is
    absent or timeout: raise_uncertainty event produced AND agent execution
    halted. No document access proceeds without an explicit access-granted
    event.
  checked_by: Agent Behaviour Analyst; Audit Trail Agent

### SysAdmin_Access

R11:
  rule: >
    sysadmin:dlm-sysadmin retains read access to all documents at all
    classification levels (C0 through C3) for audit, governance, and
    emergency response purposes. SysAdmin read access to C2 and C3
    documents must produce an access-granted audit event with: agent_id,
    doc_id, classification_level, and justification_ref. SysAdmin write
    access to approved documents is governed by Change Management Policy
    (Wave 13).
  test: >
    For sysadmin:dlm-sysadmin access to C2 and C3 documents: access-granted
    event exists with justification_ref populated. C0 and C1 SysAdmin reads
    are not required to produce access-granted events.
  checked_by: Audit Trail Agent

### Context_Boundary

R12:
  rule: >
    The Access Gatekeeper agent must operate within a strict context boundary
    per Agent Context Boundary Policy (DLMS-2026-0016). Its reads list must
    contain only: the target document's frontmatter (specifically the
    confidentiality_class and doc_id fields) and the target document's
    access manifest. The Access Gatekeeper must never read document body
    content and must not use document content to influence its access
    decision.
  test: >
    All reads by Access Gatekeeper during an access evaluation are confined
    to: target document frontmatter AND access manifest for the target
    doc_id. Any read of document body content by Access Gatekeeper is a
    context boundary violation per DLMS-2026-0016.
  checked_by: Audit Trail Agent; Agent Behaviour Analyst

### Audit_Requirements

R13:
  rule: >
    Audit logging requirements by classification level: (a) C2 and C3
    documents — access-granted events are required for all read and write
    operations, including SysAdmin access, with requesting_agent_id, doc_id,
    classification_level, operation, and timestamp; (b) C0 and C1 documents
    — access-granted events are not produced for read operations (proportional
    logging per principle PF4); (c) all classification levels — access-denied
    events are required for all denied access attempts with all five required
    fields.
  test: >
    For C2 and C3 reads and writes: access-granted event exists with five
    required fields. For C0 and C1 reads: no access-granted event produced.
    For all denials: access-denied event exists with five required fields.
  checked_by: Audit Trail Agent

## EXCEPTIONS_PROCESS
Tier 3 exceptions are permitted on a time-limited basis with SysAdmin
approval. To request an exception to any rule in this policy: (1) The
requesting agent produces a policy-exception-request artefact addressed
to the SysAdmin directive queue, citing the rule reference, the reason
the rule cannot be satisfied, and the proposed mitigating controls.
(2) sysadmin:dlm-sysadmin reviews and, if approved, issues a
policy-exception-grant directive specifying the rule, scope, expiry date,
and audit conditions. (3) The exception is logged as a policy-exception
audit event and is visible in the next CI cycle report. No exception may
extend beyond 90 days without renewal. No exception may waive R01, R06,
R08, or R10. The capability-based access model (R01) and C3 access
controls (R06) are non-negotiable structural constraints.

## ENFORCEMENT
  primary_agent:    Access Gatekeeper; Audit Trail Agent
  gate_positions:
    - All document read and write operations: Access Gatekeeper intercepts
      all requests before any operation executes
    - C2 and C3 document creation: Review Stage Orchestrator confirms access
      manifest exists before the review stage opens (R07)
    - Distribution stage: Distribution Orchestrator validates classification
      before including any document in an external distribution plan (R04)
  audit: >
    All access-granted events (C2/C3) and all access-denied events are
    logged per R13. Access Gatekeeper context boundary compliance is logged
    per DLMS-2026-0015. access-manifest-missing events are escalated
    immediately. access-violation events trigger a SysAdmin alert.
  violation_type:   Tier 3 operational violation
  escalation: >
    Self-authorisation attempts (R06 violations), access-violation events,
    and access-manifest-missing conditions are immediately escalated to
    sysadmin:dlm-sysadmin. Context boundary violations by Access Gatekeeper
    (R12) are immediately escalated. Failure to raise_uncertainty after
    access-denied (R09) is flagged in the next CI cycle report.

      misconfigured access manifests or incorrect agent tool assignments
