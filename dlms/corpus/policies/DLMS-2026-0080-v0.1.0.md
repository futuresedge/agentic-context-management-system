## SUMMARY
This Tier 2 policy defines the conditions that mandate escalation to
sysadmin:dlm-sysadmin, the notification and response windows that apply
to each escalation, and the cycle completion gate that prevents any CI
cycle from closing while an unacknowledged escalation remains open.
Human oversight at defined escalation points is a non-negotiable control;
no exception to this requirement is permitted.

## SCOPE

Applies to:
- All escalation triggers arising from the CI cycle, including those
  defined in CI Cycle Policy (DLMS-2026-0076), SLA Breach Response
  Policy (DLMS-2026-0078), and Change Management Policy
  (DLMS-2026-0079, Wave 13)
- Agent:ci-cycle-orchestrator, agent:sla-manager,
  agent:dlm-sysadmin-agent, agent:anomaly-detector, and any other
  agent designated in the escalation_ref field of a governed policy
- sysadmin:dlm-sysadmin in all acknowledgement and direction-setting
  roles
- All escalation artefacts (audit entries, notifications, and any
  SysAdmin briefing SAB- produced per DLMS-2026-0073)

Excludes:
- Internal agent-to-agent coordination that does not involve
  sysadmin:dlm-sysadmin
- Escalations defined within a single stage process that are resolved
  without triggering any condition listed in R01 (those are governed
  by the relevant stage SLA policy)

## DEFINITIONS

escalation trigger:
  Any discrete condition that this policy defines as mandating
  notification to sysadmin:dlm-sysadmin. The full list of triggers is
  enumerated in R01. An escalation trigger is not a preference or a
  guideline — meeting any trigger condition creates a mandatory
  obligation for the escalating agent.

escalation event:
  An audit entry created at the point an escalation trigger fires,
  recording: the trigger condition, the CI cycle_id, the triggering
  agent, and the timestamp. An escalation event is the formal record
  that an escalation obligation exists.

notification:
  The act of dispatching an escalation artefact (structured message or
  SAB-) to sysadmin:dlm-sysadmin. Notification is the mechanism by
  which the escalation event is communicated; it is distinct from
  acknowledgement.

acknowledgement:
  A recorded response by sysadmin:dlm-sysadmin to a notification,
  citing the escalation event reference and either (a) accepting the
  escalation for resolution, or (b) issuing a direction for the
  triggering agent to act upon. Acknowledgement closes the escalation
  obligation when paired with a resolution audit entry.

unacknowledged escalation:
  An escalation event for which no acknowledgement has been recorded
  within the applicable response window. An unacknowledged escalation
  is a blocking condition for cycle completion (R06).

## RULES

### Escalation Triggers

R01:
  rule: >
    An escalation to sysadmin:dlm-sysadmin is mandatory when any ONE of
    the following conditions is met:
    (a) The CI Cycle Synthesis artefact (CIS-) carries
        escalation_carried_forward == true (per DLMS-2026-0076 R06).
    (b) The Improvement Recommendations artefact (IMP-) contains one or
        more recommendations with priority: immediate (per
        DLMS-2026-0072).
    (c) Any anomaly report (AR-) produced during the current CI cycle
        records an anomaly with severity: critical (per
        DLMS-2026-0068).
    (d) A critical-tier SLA breach is triggered under SLA Breach Response
        Policy (DLMS-2026-0078 R06).
    (e) An unauthorised change is detected during the change window as
        defined in Change Management Policy (DLMS-2026-0079 R04,
        Wave 13).
    (f) The CI cycle is declared a cycle breach event (DLMS-2026-0076
        R07): no CD- issued within 2 days of an SBR- with
        escalation_carried_forward == true.
    Meeting any single trigger condition is sufficient to mandate
    escalation. Multiple simultaneous triggers are batched into a single
    notification but each trigger must be individually enumerated.
  test: >
    IF ANY of conditions (a)-(f) is true:
      escalation_event created AND
      notification dispatched within 30 min of trigger detection
  checked_by: agent:ci-cycle-orchestrator; Audit Trail Agent

### Notification Timing

R02:
  rule: >
    The escalating agent must dispatch a notification to
    sysadmin:dlm-sysadmin within 30 minutes of detecting the escalation
    trigger. If a SysAdmin briefing (SAB-) artefact is required by
    DLMS-2026-0073 for the current cycle (time_sensitivity: immediate
    or next-cycle), the SAB- must accompany the notification. If the
    trigger is condition (a), (c), (d), or (f) in R01, the SAB- is
    mandatory regardless of time_sensitivity.
  test: >
    notification.dispatched_at - trigger_detected_at <= 30 min AND
    IF trigger in [a, c, d, f]: SAB- attached to notification
  checked_by: agent:ci-cycle-orchestrator; Audit Trail Agent

### Acknowledgement Windows

R03:
  rule: >
    sysadmin:dlm-sysadmin must acknowledge the escalation notification
    within 4 hours of dispatch. Acknowledgement must be a structured
    event citing the escalation_event.id, the cycle_id, and either
    (a) "accepting — resolution in progress" or (b) a specific direction
    to the triggering agent. An acknowledgement that lacks a citation of
    escalation_event.id is not considered valid.
  test: >
    acknowledgement.recorded_at - notification.dispatched_at <= 4h AND
    acknowledgement.escalation_event_ref == escalation_event.id AND
    acknowledgement.cycle_id == current_cycle.cycle_id AND
    acknowledgement.response_type IN ["accepting", "direction-issued"]
  checked_by: Audit Trail Agent; agent:ci-cycle-orchestrator

R04:
  rule: >
    If sysadmin:dlm-sysadmin has not acknowledged within 4 hours of
    notification dispatch, the escalating agent must re-dispatch the
    notification. Re-dispatch must occur every 2 hours thereafter until
    acknowledgement is received. Each re-dispatch is logged as a new
    audit event citing the original escalation_event.id and the
    prior notification reference. The 4-hour initial window and 2-hour
    re-dispatch cycle apply indefinitely; no agent may assume that
    silence constitutes acknowledgement.
  test: >
    IF now - notification.dispatched_at > 4h AND no acknowledgement:
      redispatch.dispatched_at - (last_dispatch.dispatched_at) <= 2h AND
      redispatch.escalation_event_ref == escalation_event.id AND
      redispatch logged as audit event
  checked_by: Audit Trail Agent; agent:ci-cycle-orchestrator

### Audit Trail

R05:
  rule: >
    All escalation events, notifications, re-dispatches, and
    acknowledgements must be recorded in the audit trail per Audit
    Trail Policy (DLMS-2026-0015). Each entry must include: the
    escalation_event.id, the trigger condition identifier from R01 (a)–(f),
    the cycle_id, the acting agent or human identifier, and the timestamp.
    No escalation lifecycle action is considered to have occurred if it
    lacks a corresponding audit entry. This rule cannot be excepted.
  test: >
    FOR each action in [escalation event, notification, redispatch, acknowledgement]:
      audit_entry.escalation_event_ref non-null AND
      audit_entry.trigger_condition IN [a, b, c, d, e, f] AND
      audit_entry.cycle_id non-null AND
      audit_entry.actor non-null AND
      audit_entry.timestamp non-null
  checked_by: Audit Trail Agent

### Cycle Completion Gate

R06:
  rule: >
    A CI cycle must not be marked complete while any unacknowledged
    escalation from that cycle remains open. Agent:ci-cycle-orchestrator
    must check for open unacknowledged escalations as the final gate
    before recording cycle completion. If an open escalation exists, the
    cycle_completion record is blocked until all escalations for that
    cycle carry a valid acknowledgement. This rule cannot be excepted.
  test: >
    FOR each cycle:
      cycle.completion_recorded_at non-null IMPLIES
      ALL escalation_events FOR cycle.cycle_id:
        escalation.acknowledgement.recorded_at non-null AND
        escalation.acknowledgement IS valid per R03
  checked_by: agent:ci-cycle-orchestrator; Audit Trail Agent

### Escalation Resolution

R07:
  rule: >
    An escalation is not considered resolved, and must remain open, until
    sysadmin:dlm-sysadmin has issued a CD- for the triggering cycle that
    addresses the underlying trigger condition. For trigger conditions (b)
    and (c) — immediate-priority recommendations or critical anomalies —
    the CD- must include either a remediation item or an explicit
    no-action rationale for each triggering item. Resolution is recorded
    as an audit event citing the escalation_event.id, the CD-
    artefact_id, and the cycle_id. A resolved escalation cannot be
    re-opened for the same trigger condition in the same cycle.
  test: >
    escalation.resolved_at non-null IMPLIES
      CD-.artefact_id referenced in resolution_audit.cd_ref AND
      FOR trigger in [b, c]: CD- contains remediation_item or no_action_rationale
        FOR each triggering IMP-/AR- entry AND
      resolution_audit.escalation_event_ref == escalation_event.id
  checked_by: agent:ci-cycle-orchestrator; Audit Trail Agent

### Severity Self-Assessment Prohibition

R08:
  rule: >
    No escalating agent may evaluate or adjust the severity or priority
    of the condition that triggered an escalation. Only sysadmin:dlm-sysadmin
    may change the severity classification of a trigger condition already
    recorded in an escalation event. An agent must escalate based on the
    severity or priority value produced by the originating artefact
    (AR-, IMP-, or breach event); the escalating agent must not apply
    its own judgement to downgrade or suppress the trigger. This rule
    cannot be excepted (Tier 2 per DLMS-2026-0014).
  test: >
    escalation_event.trigger_severity ==
      source_artefact.severity OR source_artefact.priority
    AND escalation_event.trigger_severity modified_by sysadmin:dlm-sysadmin
      ONLY
  checked_by: Audit Trail Agent; Verification agents

## EXCEPTIONS_PROCESS

This policy is Tier 2. All rules are either Tier 2 constraints (cannot
be excepted under any circumstance) or Tier 3 constraints (excitable
with sysadmin:dlm-sysadmin approval). The minimum exception threshold
for all rules in this document is Tier 3 — sysadmin:dlm-sysadmin
approval prior to exception.

The following cannot be excepted under any circumstance:
- R01 (escalation triggers are mandatory)
- R05 (audit trail — Tier 2 per DLMS-2026-0015)
- R06 (cycle completion gate — Tier 2 human oversight requirement)
- R08 (severity self-assessment prohibition — Tier 2 per DLMS-2026-0014)

For any other rule in this policy where a one-off exception is sought:
1. Exception request submitted to sysadmin:dlm-sysadmin before the
   obligation arises.
2. Exception recorded as an audit event with rule reference, cycle_id,
   rationale, and compensating control.
3. Exception applies to a single cycle instance only.

## ENFORCEMENT

primary_agent:    agent:ci-cycle-orchestrator
secondary_agent:  agent:sla-manager; agent:dlm-sysadmin-agent;
                  agent:anomaly-detector
gate_positions:
  - 30-minute notification window after trigger detection (R02)
  - 4-hour initial acknowledgement window (R03)
  - 2-hour re-dispatch cycle if unacknowledged (R04)
  - Cycle completion gate (R06)
violation_type:   Any missed notification or re-dispatch window — audit
                  event recorded immediately; cycle completion blocked.
                  Any agent that suppresses an escalation trigger is a
                  critical integrity failure — escalate to
                  sysadmin:dlm-sysadmin independently of the suppressing
                  agent.
escalation_ref:   This is the terminal escalation policy for the DLMS.
                  There is no higher automated escalation path.
                  sysadmin:dlm-sysadmin is the human authority.
