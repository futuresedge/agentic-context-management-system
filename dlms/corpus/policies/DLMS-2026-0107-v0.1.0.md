## SUMMARY
This policy codifies a two-dimensional work classification model (Impact × Uncertainty)
that determines the required number and cognitive orientation of Definition of Done
authors for any DLMS work item. It mandates multi-perspective DoD authorship for
high-stakes and novel work in response to confirmed violations of PF1 (Cognitive
Diversity By Design) and T6 (Resilience Through Structure) in the single-author DoD
model. Currently operationalised in Tier 15 (Nexus Infrastructure); applicable to all
tiers.

## SCOPE
Applies to: all DLMS tiers — any agent or pipeline producing a Definition of Done
  artefact. Currently operationalised in Tier 15; other tiers adopt as their DoD agent
  patterns are next revised.
Excludes: DoD template definitions (governed by DLMS-2026-0041 and TMPL-* documents);
  the classification taxonomy does not change what a criterion contains, only how
  many independent agents author it.

## DEFINITIONS

impact_class:
  The classification level assigned to a work item based on its position in the
  Impact × Uncertainty matrix. One of: RC-standard, RC-high-impact, RC-critical.
  Must be declared in the work item's context or plan artefact before the DoD
  authorship step begins.

blast_radius:
  The number of agents, tools, and downstream pipeline stages whose correct operation
  directly depends on the work item being correct. High blast radius increases the
  Impact dimension score.

feature_novelty:
  A binary flag indicating that this type of work has no prior DLMS example, reference
  implementation, or learnings corpus entry. High novelty increases the Uncertainty
  dimension score. Decreases as the learnings corpus and SKILL.md coverage grow.

pattern_coverage:
  A flag indicating that at least one directly applicable SKILL.md or TMPL-* template
  exists for this work type. Absent pattern coverage increases the Uncertainty dimension
  score. Improves automatically as SKILL.md files are authored.

first_time_execution:
  A flag indicating the specific phase or task type has never been executed successfully
  in the live system, regardless of whether a pattern exists. Increases Uncertainty.
  Cleared after the first verified execution.

external_interface_change:
  A flag indicating the work item modifies a function signature, tool API, or artefact
  schema that downstream agents depend on. Increases both Uncertainty (unknown ripple
  effects) and Impact (downstream breakage if incorrect).

completeness_orientation:
  A cognitive orientation for DoD authorship. The author asks: "What must be true for
  this work to be correct and complete?" Produces comprehensive criteria covering
  functional correctness, non-functional requirements, audit trail, and rollback
  readiness.

adversarial_orientation:
  A cognitive orientation for DoD authorship. The author asks: "What failure modes
  would a naive DoD permit to pass?" Produces stress-tested criteria that split
  ambiguous conditions into directional tests, identify bidirectional failure checks,
  and surface silent-pass failure modes (where incorrect behaviour produces no
  observable error).

efficiency_orientation:
  A cognitive orientation for DoD authorship. The author asks: "Is this DoD minimum
  sufficient? Are any criteria redundant, overlapping, or unverifiable in principle?"
  Counterbalances the adversarial orientation's natural tendency to expand criteria.
  Applied at RC-critical level. Aligns with the minimal-context discipline in
  context-engineering-approach.md.

security_orientation:
  A conditional DoD authorship overlay triggered when a work item touches an
  access-control boundary. Asks: "What attack surface does this work create or expand?"
  Applied through a Security overlay step in the Synthesizer stage, not as a parallel
  DoD author. Activation conditions defined in SECURITY_OVERLAY_TRIGGERS below.

dod_synthesizer:
  The agent role that consolidates multiple parallel DoD drafts into a single canonical
  DoD artefact. Applies the Synthesizer rules defined in this document. Must not be
  the same agent as any of the DoD authors for the same work item (T5).

outcome_focused:
  A property of DoD criteria meaning each criterion specifies a required system state
  or observable behaviour, not the implementation approach used to achieve it. Preserves
  the executing agent's architectural freedom. Criteria that specify "must use method X"
  rather than "must produce result Y" fail this property.

## CLASSIFICATION_MODEL

### Dimensions

| Dimension | Factors | Scoring |
|---|---|---|
| **Impact** | Blast radius (agent + tool + stage dependents); reversibility (rollback without data loss?); security boundary (touches access control, audit trail, or trust chain?); cross-cutting (spans multiple tiers or both infra layers?) | High if ≥ 2 factors apply, OR security boundary is touched |
| **Uncertainty** | Feature novelty (no prior DLMS example); pattern coverage (no applicable SKILL.md or TMPL-*); first_time_execution (phase/task never succeeded in live system); external_interface_change (signature or schema change with downstream dependents) | High if ≥ 2 factors apply, OR feature_novelty AND no pattern_coverage simultaneously |

### Classification Matrix

| | Low Uncertainty | High Uncertainty |
|---|---|---|
| **Low Impact** | `RC-standard` | `RC-high-impact` |
| **High Impact** | `RC-high-impact` | `RC-critical` |

A security boundary touch (access control, audit atomicity, trust chain) upgrades to
`RC-critical` regardless of the matrix position.

### Auto-Classifications — Tier 15

The following Tier 15 work items are permanently `RC-critical` regardless of matrix
evaluation. Their Impact and Uncertainty are both structurally high and cannot decrease
through pattern accumulation:

| Work item | Rationale |
|---|---|
| Any change to `nexus/src/tools/shared/gateway.ts` | OCAP model enforcement; all tool access depends on it |
| Any change to `nexus/src/tools/shared/gate.ts` | Stage gate integrity; all pipeline sequencing depends on it |
| Any change to `nexus/src/tools/shared/audit.ts` | Audit trail atomicity; compliance chain integrity |
| Any change to `dlms/registry/tool-access-registry.md` (TAR-001) | Defines all agent permissions; blast radius = all agents |
| Any change to TypeDB schema (`nexus/src/db/`) | All TypeDB queries and artefact storage depend on schema correctness |
| Nexus Phase 2 (MCP Core Infrastructure) | Implements gateway.ts + audit.ts simultaneously |

All other Tier 15 phases start as `RC-high-impact` unless they touch the above files,
at which point they upgrade to `RC-critical`.

### Classification Is Mutable

A work item's `impact_class` may be downgraded on repeat execution once:
1. The Uncertainty dimension decreases (a SKILL.md now exists, pattern_coverage is true,
   first_time_execution flag has been cleared by a prior verified run)
2. The Impact dimension has not increased

Re-evaluation must be performed by the same agent role that produced the original
classification (Infra Planner for Tier 15). The `impact_class` in the new artefact
supersedes the previous one and must be traceable to its inputs.

## DOD_AUTHORSHIP_RULES

### Authorship Pattern by impact_class

| impact_class | Parallel DoD Authors | Synthesizer Required? | Human Gate? |
|---|---|---|---|
| `RC-standard` | 1 × Completeness | No — single author produces canonical DoD directly | No |
| `RC-high-impact` | 2 × (Completeness + Adversarial) | Yes — efficiency-pruning mandate | No |
| `RC-critical` | 3 × (Completeness + Adversarial + Efficiency) | Yes — with Security overlay if triggered | Yes — FO or delegate must approve synthesised DoD before Executor activates |

### Author Independence Constraint

All parallel DoD authors must:
- Receive the same inputs (plan artefact + context artefact paths only)
- Not read each other's draft DoD artefacts before submitting
- Not communicate outside their designated input channel
- Write to separate draft artefact paths (draft-completeness, draft-adversarial, draft-efficiency)

The Synthesizer is the only agent permitted to read all draft artefacts.

### Synthesizer Rules

The DoD Synthesizer must apply the following rules in order when producing the canonical DoD:

**S01 — Extract:** Include every criterion from all draft DoD artefacts as a candidate set.

**S02 — Conflict resolution:** When two criteria address the same condition with different
  threshold or framing:
  - Prefer the adversarial framing over the completeness framing.
  - Prefer the more precise formulation over the more general.
  - Document the discarded alternative in a `synthesis_notes` field.

**S03 — Non-waivable survival:** All criteria flagged `non_waivable: true` in any draft
  survive synthesis unchanged. They cannot be pruned and cannot be weakened during
  conflict resolution.

**S04 — Redundancy pruning:** If two criteria are logically equivalent in meaning and
  scope (i.e., passing one guarantees passing the other), retain only the more precisely
  formulated criterion. Record the redundancy in `synthesis_notes`.

**S05 — Outcome focus:** Each criterion in the canonical DoD must be outcome-focused.
  Criteria specifying implementation approach rather than system state must be rewritten
  to target the observable result. This preserves executor architectural freedom.
  Criteria that cannot be rewritten outcome-focused and cannot be removed (because they
  are non-waivable) must be flagged with `implementation_prescriptive: true` in the DoD
  for FO awareness.

**S06 — Security overlay (conditional):** If the work item triggers the Security overlay,
  the Synthesizer must additionally review all criteria through the security_orientation
  lens — adding any missing criteria covering: access control boundary changes,
  authentication surface, audit atomicity in the presence of failures, and
  denial-of-service resistance for the specific modified component.

### Security Overlay Triggers

The Security overlay is applied by the Synthesizer whenever any of the following are true:

| Trigger | File or component |
|---|---|
| Work item modifies gateway.ts | `nexus/src/tools/shared/gateway.ts` |
| Work item modifies gate.ts | `nexus/src/tools/shared/gate.ts` |
| Work item modifies audit.ts | `nexus/src/tools/shared/audit.ts` |
| Work item modifies TAR-001 | `dlms/registry/tool-access-registry.md` |
| Work item introduces or changes agent authentication/identity handling | Any |
| Work item changes tool permission validation logic | Any `nexus/src/` file |

## RULES

HC01:
  rule:       Every DoD-producing step (whether by a single agent or parallel authors)
              must begin by declaring the work item's `impact_class`. The impact_class
              must be recorded in the DoD artefact's frontmatter or header block before
              any criteria are authored.
  rationale:  Makes classification explicit and auditable. Prevents agents from skipping
              classification silently.
  checked_by: Infra Verifier (checks impact_class field exists in infra_dod); DoD Custodian
              (Tier 2) in the document lifecycle pipeline

HC02:
  rule:       impact_class must be derived from the two-dimensional classification matrix
              (Impact × Uncertainty) defined in this document. Auto-classification rules
              take precedence over matrix evaluation. An agent may not assert impact_class
              without evaluating all four Impact factors and all four Uncertainty factors.
  rationale:  Prevents underclassification through arbitrary or convenience-based
              classification.
  checked_by: Infra Verifier; DoD Custodian

HC03:
  rule:       RC-standard work items use a single DoD author operating with the
              completeness_orientation. No Synthesizer required. The author writes the
              canonical DoD directly.
  checked_by: Infra Verifier (confirms impact_class is RC-standard before accepting single
              author)

HC04:
  rule:       RC-high-impact work items must use two parallel DoD authors (Completeness
              and Adversarial orientations). Authors must not read each other's drafts
              before submitting. The Synthesizer produces the canonical DoD from both
              drafts. The Synthesizer must apply Synthesizer Rules S01–S05 (and S06 if
              Security overlay is triggered). A canonical DoD produced from a single
              draft is non-compliant.
  rationale:  Enforces PF1 (Cognitive Diversity By Design) and T6 (Resilience Through
              Structure). Single-perspective DoD on high-impact work is a structural
              single point of failure.
  checked_by: Infra Verifier (checks both draft artefact paths exist and are distinct);
              Nexus Infrastructure Orchestrator (gate check)

HC05:
  rule:       RC-critical work items must use three parallel DoD authors (Completeness,
              Adversarial, and Efficiency orientations). Authors must not read each
              other's drafts before submitting. The Synthesizer produces the canonical
              DoD from all three drafts, applying S01–S06. If the work item triggers the
              Security overlay, S06 is mandatory. After the canonical DoD is produced,
              a human review gate must be satisfied before the executing agent is invoked.
  rationale:  RC-critical work has both high impact and high uncertainty — maximum cognitive
              diversity is proportional. The Efficiency author counterbalances adversarial
              expansion, preventing DoD bloat on the most complex tasks. The human gate
              reflects P3 (Structural Ethics) and T7 (Verification Is Distributable).
  checked_by: Nexus Infrastructure Orchestrator (gate check — human approval must be on
              record); Infra Verifier

HC06:
  rule:       The DoD Synthesizer must not be the same agent instance that authored any
              of the draft DoDs for the same work item. Synthesizer identity is structural,
              not declarative — the agent role must differ from all DoD author roles.
  rationale:  Enforces T5 (No Actor Judges Own Work).
  checked_by: Infra Verifier (checks synthesizer actor_id ≠ any draft author actor_id in
              audit trail)

HC07:
  rule:       DoD criteria must be outcome-focused (property defined in DEFINITIONS).
              The Synthesizer must reclassify criteria that specify implementation approach
              rather than observable result. Any implementation-prescriptive criteria that
              cannot be rewritten and are non-waivable must be flagged `implementation_prescriptive: true`.
  rationale:  Maintains executor architectural freedom. A DoD should never constrain how
              a result is achieved, only whether the result is correct.
  checked_by: Infra Verifier; DoD Custodian

HC08:
  rule:       impact_class is not static. When a work item type has been successfully
              executed (verified) in the live system before, the executing team must
              re-evaluate Uncertainty factors. If pattern_coverage is now true (SKILL.md
              exists) and first_time_execution flag is cleared, the Uncertainty dimension
              may decrease, potentially reclassifying the work item to a lower RC level.
              The re-evaluated impact_class replaces the prior one in the new artefact.
  rationale:  Prevents permanent over-classification as the DLMS matures. Excellence in
              governance should reduce procedural burden for well-understood work, not
              increase it.
  checked_by: Infra Planner (self-evaluated); Infra Verifier (confirms re-evaluation is
              traceable)

HC09:
  rule:       When the Security overlay is triggered (S06 conditions), the trigger must
              be recorded in the infra_dod artefact header as `security_overlay: true`
              alongside the trigger condition that activated it. A security-boundary work
              item with `security_overlay: false` or absent is a hard gate failure.
  checked_by: Infra Verifier; SysAdmin Governance Agent

## ENFORCEMENT
primary_agent:    Infra Verifier (Tier 15); DoD Custodian (Tier 2 — for document lifecycle
                  tiers when they adopt this policy)
gate_positions:
  - Pre-DoD: DoD-producing agent checks impact_class against classification matrix; records
    impact_class in artefact
  - Pre-execution: Orchestrator gate checks impact_class field exists AND correct authorship
    pattern was used for the declared level
  - Pre-Executor (RC-critical): Orchestrator checks human approval record exists for the
    synthesised DoD before invoking Executor
  - Post-verification: Infra Verifier checks actor_id independence between Synthesizer and
    all draft DoD authors; checks all non-waivable criteria present in canonical DoD
audit:            Violations written to audit trail with fields: rule_id, agent_id,
                  violation_type, timestamp, resolution_status. HC04/HC05 violations
                  (under-classification of high-stakes work) are priority:critical.
violation_type:   high-stakes-classification-violation
escalation:       Per SysAdmin Escalation Policy (DLMS-2026-0080)
