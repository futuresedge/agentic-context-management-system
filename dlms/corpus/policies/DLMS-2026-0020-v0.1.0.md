## SUMMARY
This policy governs the declaration, validation, and maintenance of
dependencies between DLMS documents. Every dependency relationship a
document has with another must be explicitly declared in the frontmatter
dependencies[] field using an approved relationship type. The Dependency
Index Agent maintains the corpus-wide dependency graph and enforces
its integrity at every Indexing stage. This is a Tier 3 Operational
Lifecycle policy.

## SCOPE
Applies to: all DLMS documents that declare dependencies in their
frontmatter dependencies[] field (i.e. all documents); the Dependency
Index Agent that maintains the corpus-wide dependency graph; the
Indexing Verifier that checks dependency declarations at the Indexing
stage gate; the Approval Gate Agent insofar as it checks dependency
validity before granting approval; any agent that consumes the
dependency graph for context curation, impact analysis, or
change propagation.

Excludes: implicit relationships between documents that are not
formally declared (these are not tracked by this policy — the DLMS
has no concept of undeclared relationships); relationships between
DLMS documents and external systems or non-DLMS artefacts (these
are captured in specification DEPENDENCIES sections as operational
notes, not as governed dependency declarations); the Taxonomy document's
self-referential tag constraint (governed by Taxonomy Policy
DLMS-2026-0019).

Bootstrap exception: Documents DLMS-2026-0001 through DLMS-2026-0013
contain forward references in their dependencies[] fields — they reference
documents that did not exist at the time of their creation. This is a
permitted bootstrap exception. All documents from DLMS-2026-0014 onwards
must not declare forward references.

## DEFINITIONS

dependency:
  A formally declared, directional relationship between a source
  document (the declaring document) and a target document (the
  referenced document). Dependencies are declared in the source
  document's frontmatter dependencies[] field.

dependency graph:
  The corpus-wide directed graph of all dependency relationships,
  maintained by the Dependency Index Agent at
  /dlms/registry/dependency-index.md. Nodes are doc_ids; edges
  are dependency relationships with rel type labels.

Dependency Index Agent:
  The agent responsible for maintaining the dependency graph.
  At every Indexing stage, the Dependency Index Agent validates
  the declaring document's dependencies[], updates the graph,
  and checks for violations including cycles and dangling references.

dependency relationship type (rel):
  The declared nature of the relationship between source and target.
  Four types are approved: implements, references, supersedes,
  is-governed-by. Each type carries a specific semantic meaning
  defined in DEFINITIONS below.

implements:
  The source document operationalises, enforces, or gives effect to
  the target document. Example: a procedure implements a policy;
  a standard implements a policy. The target governs the source's
  domain; the source provides the operational detail.

references:
  The source document cites, uses data from, or is informed by
  the target document, but does not implement or enforce it.
  A looser coupling than implements. Example: a policy references
  a standard that provides relevant technical context.

supersedes:
  The source document replaces the target document. The target
  must simultaneously have its superseded_by field set to the
  source doc_id. This is the only bidirectional relationship type
  — it requires an atomic paired update.

is-governed-by:
  The rules, constraints, or authority of the target document
  apply to the source document. Example: all documents declare
  is-governed-by DLMS-2026-0001 (Policy Governance Policy).
  This is the most common dependency type in the corpus.

dangling reference:
  A dependency declaration whose target doc_id does not exist
  in the DLMS registry. Dangling references are always violations
  except in Wave-1 bootstrap documents.

dependency cycle:
  A condition in the dependency graph where document A depends on
  document B which (directly or transitively) depends on document A.
  Cycles are structural violations — they indicate a logical
  circularity in the governance hierarchy.

impact set:
  The set of all documents that directly or transitively depend on
  a given document D. When D changes, all documents in its impact
  set may be affected. The impact set is derived from the dependency
  graph by the Dependency Index Agent.

## RULES

### Declaration_Requirements

R01:
  rule: >
    Every DLMS document must declare all dependencies in its
    frontmatter dependencies[] field at the time of creation.
    A document that depends on another document but does not
    declare that dependency is non-compliant regardless of whether
    the dependency is obvious or implied by context.
  test: >
    For all documents D: every document E that D's rules, schema,
    or content formally rely upon is present in D.dependencies[].
    Perspective Reviewer (lens-operability) checks this at review stage.
  checked_by: Dependency Index Updater; Indexing Verifier;
              Perspective Reviewer (lens-operability)

R02:
  rule: >
    Every document must declare is-governed-by DLMS-2026-0001
    (Policy Governance Policy) as its minimum dependency.
    No document may have an empty dependencies[] array.
  test: >
    For all documents D:
    len(D.dependencies) >= 1 AND
    D.dependencies contains doc_id == 'DLMS-2026-0001'
    AND rel == 'is-governed-by'.
  checked_by: Agent Format Validator; Dependency Index Updater

R03:
  rule: >
    Each dependency entry must use exactly one rel value from the
    approved set: implements, references, supersedes, is-governed-by.
    The rel value must accurately reflect the nature of the
    relationship. Misclassified rel values are a dependency
    quality violation.
  test: >
    For all D in dependencies[]:
    D.rel IN [implements, references, supersedes, is-governed-by] AND
    D has exactly two keys (doc_id and rel).
  checked_by: Agent Format Validator; Perspective Reviewer (lens-accuracy)

R04:
  rule: >
    A document may declare at most one dependency entry per target
    doc_id. If a source document has multiple relationship types with
    the same target, the most specific rel type takes precedence.
    Duplicate doc_id entries in dependencies[] are prohibited.
  test: >
    For all documents D:
    len(set(dependencies[*].doc_id)) == len(dependencies[]).
    (No two entries share the same doc_id.)
  checked_by: Agent Format Validator; Dependency Index Updater

### Target_Document_Validity

R05:
  rule: >
    All doc_ids declared in dependencies[] must exist in the DLMS
    registry at the time the document is created or updated.
    Forward references — declaring a dependency on a document that
    does not yet exist — are prohibited except in Wave-1 bootstrap
    documents (DLMS-2026-0001 through DLMS-2026-0004).
  test: >
    For all D in dependencies[]:
    D.doc_id IN DLMS registry at time of declaration OR
    declaring document is in the Wave-1 bootstrap exemption set.
  checked_by: Dependency Index Updater; Indexing Verifier

R06:
  rule: >
    Dependencies declared with rel: implements or rel: is-governed-by
    must target documents with status: approved. A document may not
    implement or be governed by a draft or under_review document.
    Dependencies with rel: references or rel: supersedes may target
    documents at any status.
  test: >
    For all D in dependencies[] where D.rel IN [implements, is-governed-by]:
    referenced document has status == 'approved'.
  checked_by: Dependency Index Updater; Approval Gate Agent

### Cycle_Prevention

R07:
  rule: >
    The dependency graph must be acyclic at all times. The Dependency
    Index Agent must perform a cycle detection check on the full graph
    whenever a new dependency declaration is processed. A cycle
    detected after a declaration is added is a critical integrity
    violation — the offending declaration must be rejected and
    the graph must be rolled back.
  test: >
    After each Dependency Index Agent update:
    topological sort of dependency graph succeeds (no cycles detected).
    If cycle detected: declaration is rejected, rollback occurs, and
    dependency-cycle-detected audit event is logged with outcome: fail.
  checked_by: Dependency Index Updater; Storage Verifier;
              Audit Trail Agent

R08:
  rule: >
    The is-governed-by relationship is always directed downward in
    the governance hierarchy — a lower-tier document declares
    is-governed-by toward a higher-tier document. A higher-tier
    document may not declare is-governed-by toward a lower-tier
    document. This rule is a structural guard against hierarchy
    inversions that would create logical cycles.
  test: >
    For all D in dependencies[] where D.rel == 'is-governed-by':
    tier(declaring document) >= tier(referenced document) OR
    declaring document is not a policy (non-policy documents
    may declare is-governed-by toward any tier).
  checked_by: Dependency Index Updater;
              Perspective Reviewer (lens-accuracy)

### Supersedes_Consistency

R09:
  rule: >
    When a document declares supersedes: [doc_id] in its frontmatter
    and a corresponding rel: supersedes dependency entry, the
    referenced document's superseded_by field must be set to the
    declaring document's doc_id atomically. The two writes are a
    single transaction. A supersedes declaration without the
    corresponding superseded_by update is a consistency violation.
  test: >
    IF supersedes != null:
    dependencies contains doc_id == supersedes value AND
    rel == 'supersedes' AND
    referenced_doc.superseded_by == this.doc_id AND
    both writes share the same transaction_id in the audit trail.
  checked_by: Version Control Agent; Dependency Index Updater;
              Storage Verifier

R10:
  rule: >
    A document may declare at most one supersedes relationship.
    A document may not supersede more than one prior document.
    Consolidating multiple prior documents into one successor
    requires a SysAdmin directive explicitly authorising the
    multi-supersession.
  test: >
    count(D in dependencies[] where D.rel == 'supersedes') <= 1 OR
    SysAdmin directive authorising multi-supersession exists in
    the audit trail.
  checked_by: Dependency Index Updater; Agent Format Validator

### Dependency_Index_Maintenance

R11:
  rule: >
    The Dependency Index Agent must update the corpus-wide dependency
    graph at the completion of every Indexing stage. The graph must
    reflect the current approved dependencies[] of all approved
    documents. Stale graph entries are a data integrity violation.
  test: >
    After each Indexing stage completion:
    dependency-index-updated audit event exists AND
    graph entries for the indexed document reflect its current
    approved dependencies[].
  checked_by: Dependency Index Updater; Indexing Verifier

R12:
  rule: >
    The dependency graph must be queryable by the following
    dimensions: by source doc_id (what does this document depend on),
    by target doc_id (what documents depend on this document — its
    impact set), by rel type (all implements relationships, etc.),
    and by tier (all dependencies crossing tier boundaries).
    The Dependency Index Agent specification must declare all four
    query dimensions.
  test: >
    Dependency Index Agent specification (Wave 4) includes all four
    query dimensions in its REQUIREMENTS section.
  checked_by: Dependency Index Agent specification; CI Verifier

### Impact_Assessment

R13:
  rule: >
    When a document D is updated (new version), superseded, or
    archived, the Dependency Index Agent must produce an impact
    assessment listing all documents in D's impact set — all
    documents that directly or transitively depend on D. The
    impact assessment must be produced before the status transition
    is finalised.
  test: >
    For all status transitions of document D:
    impact-assessment artefact is produced by Dependency Index Agent
    AND artefact is referenced in the transition's audit event
    before the transition is recorded as complete.
  checked_by: Status Transition Agent; Dependency Index Updater;
              Audit Trail Agent

R14:
  rule: >
    When the impact assessment for a superseded or archived document
    identifies documents with rel: implements or rel: is-governed-by
    pointing to the retiring document, those dependent documents must
    be flagged for mandatory review. The Dependency Index Agent
    produces a dependency-review-required notification for each
    affected document. Review must be completed within two CI cycles.
  test: >
    For all documents E in impact set of retiring document D
    where E.dependencies contains D.doc_id AND
    rel IN [implements, is-governed-by]:
    dependency-review-required audit event exists for E AND
    E enters under_review status within 2 CI cycles.
  checked_by: Dependency Index Updater; CI Verifier;
              Review Orchestrator

### Cross-Document_Consistency

R15:
  rule: >
    All doc_ids referenced in a document's body content (not
    frontmatter) — such as rule checked_by fields, RELATED_PATTERNS
    entries, or COMPLIANCE_CHECK references — must also appear in
    the frontmatter dependencies[] with an appropriate rel type.
    Body references that are not declared in dependencies[] are
    undeclared dependencies and are a validation failure.
  test: >
    For all doc_id references appearing in document body:
    referenced doc_id IN D.dependencies[*].doc_id.
    Perspective Reviewer (lens-operability) and Template Validator
    check this at review stage.
  checked_by: Dependency Index Updater; Template Validator;
              Perspective Reviewer (lens-operability)

R16:
  rule: >
    The spec DEPENDENCIES section (in specification documents)
    and the frontmatter dependencies[] field must be consistent.
    Every DLMS doc_id appearing in a specification's DEPENDENCIES
    section must appear in its frontmatter dependencies[] with a
    consistent rel type. Discrepancies are a consistency violation.
  test: >
    For all specification documents S:
    for all D in S.DEPENDENCIES where D.doc_id_or_name matches
    regex ^DLMS-\d{4}-\d{4}$:
    D.doc_id_or_name IN S.frontmatter.dependencies[*].doc_id AND
    rel types are consistent.
  checked_by: Template Validator; Perspective Reviewer (lens-accuracy)

## EXCEPTIONS_PROCESS
No exceptions process applies to R07 (cycle prohibition) or R09
(supersedes atomicity). These are structural integrity invariants —
a cyclic dependency graph or an inconsistent supersession pair
represent data corruption, not policy edge cases.

For all other rules, a documented SysAdmin directive may grant a
time-limited exception for a specific document. Common legitimate
exceptions include R06 (implementing a not-yet-approved document
during an active authoring sprint, with a commitment to resolve
before the implementing document is itself approved). All exceptions
are recorded as dependency-policy-exception-granted audit events
and must be resolved before the declaring document reaches
status: approved.

## ENFORCEMENT
  primary_agent:    Dependency Index Updater; Indexing Verifier
  gate_positions:
    - Creation stage: Agent Format Validator validates R02–R04
      on initial dependencies[] declaration
    - Indexing stage: Dependency Index Updater validates R05–R06,
      R07 (cycle check), R11, R15 on every index pass
    - Status transition: Dependency Index Updater enforces R09
      (supersedes atomicity) and R13 (impact assessment) at
      every status transition event
    - Approval gate: Approval Gate Agent checks R06 (implements and
      is-governed-by targets are approved) before granting approval
    - CI cycle: CI Verifier checks R14 (dependency review completion)
      for all flagged documents
  audit: >
    All dependency events are logged via Audit Trail Agent:
    dependency-declared, dependency-validated, dependency-index-updated,
    dependency-cycle-detected, dangling-reference-detected,
    supersedes-pair-updated, impact-assessment-produced,
    dependency-review-required, dependency-review-completed,
    dependency-policy-exception-granted.
    Cycle detection and dangling reference events have outcome: fail
    and block the relevant gate.
  violation_type:   Tier 3 operational lifecycle violation
  escalation: >
    Dependency cycles and supersedes atomicity failures escalate
    immediately to sysadmin:dlm-sysadmin — these are graph integrity
    crises. Dangling references block the Indexing stage gate and
    return to the Author Agent for correction. Dependency review
    overruns (not completed within 2 CI cycles per R14) escalate
    to sysadmin:dlm-sysadmin after the second missed cycle.

## REVIEW_SCHEDULE
  interval_max:      6 months (Tier 3 maximum)
  trigger_conditions:
    - A new rel type is proposed for the dependency schema, requiring
      a policy update to define its semantics and constraints
    - The dependency graph reaches a scale where cycle detection
      performance becomes a pipeline bottleneck (requires architectural
      review of the Dependency Index Agent)
    - A CI cycle identifies a systematic pattern of undeclared
      body references (R15 violations) across multiple documents,
      suggesting the authoring process needs guidance
    - A new doc_type is introduced whose dependency patterns are
      not adequately covered by the four approved rel types
    - Impact assessment overruns are detected in more than 10% of
      status transitions in a single CI period
