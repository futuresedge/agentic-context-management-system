## SUMMARY
This policy governs the mandatory Definition of Done (DoD) stage-gate system
that controls all DLMS document lifecycle transitions. No document may advance
from one lifecycle stage to the next without a verified DoD record produced by
an agent structurally independent of the stage executor. This is a Tier 3
Agent Behaviour policy.

## SCOPE
Applies to: all DLMS lifecycle stage orchestrators; all stage executor agents;
all stage verifier agents; the Audit Trail Agent for DoD event logging; all
DLMS documents regardless of doc_type at the following six stage gates:
creation, review, approval, storage, distribution, and archival.

Excludes: internal workflow steps within a single stage that do not constitute
a stage gate transition. Only the gate transition event — where a document
moves from one lifecycle stage to the next — triggers the DoD requirement.
Work-in-progress validation checks performed within a stage are governed by
each stage's operating procedure, not by this policy.

## DEFINITIONS

Definition of Done record:
  A structured completion artefact produced at the conclusion of a lifecycle
  stage gate, conforming to the template specified for that stage. The DoD
  record is the machine-verifiable evidence that a document satisfies all
  preconditions for stage advancement. It is a first-class DLMS artefact and
  is subject to independent verification before it may be acted upon.

DoD producer:
  The stage orchestrator agent responsible for generating the completed DoD
  record for its stage gate. The DoD producer has held the work product
  throughout the stage and must not also hold the verify tool for the DoD
  record it produces.

DoD template:
  One of six stage-specific templates (DLMS-2026-0024 through DLMS-2026-0029)
  that defines the checklist schema, mandatory item identifiers, and verdict
  structure for a specific stage gate. Each DoD template governs one stage
  only and may not be used at any other stage gate.

DoD verifier:
  A stage verifier agent — structurally independent from the DoD producer —
  that evaluates the completed DoD record against the applicable DoD template
  and renders a pass or fail verdict. The DoD verifier never evaluates work it
  participated in producing.

mandatory checklist item:
  Any item in a DoD record's checklist designated as required: true in the
  applicable DoD template. A single fail verdict on any mandatory checklist
  item produces a DoD-fail outcome regardless of the verdict on all other items.

stage advancement:
  The state change by which a document exits one lifecycle stage and becomes
  eligible to enter the next. Stage advancement is controlled by the stage
  gate. Without a preceding dod-passed audit event, stage advancement is
  structurally blocked.

## RULES

### DoD_Scope

R01:
  rule: >
    A Definition of Done record is a required artefact at each of the six
    DLMS stage gates. The six mandatory stage gates are: creation, review,
    approval, storage, distribution, and archival. No stage gate is optional.
    No stage gate may be skipped or bypassed by directive, exception, or
    agent judgement.
  test: >
    For every document stage-advancement event: a DoD record exists with
    status: verified AND a dod-passed audit event referencing the same
    doc_id and stage precedes the stage-advancement event. Any
    stage-advancement event without a preceding dod-passed event constitutes
    a policy violation.
  checked_by: Stage Orchestrator; Audit Trail Agent

R02:
  rule: >
    Each stage gate is governed exclusively by its designated DoD template.
    The binding is: creation gate → DLMS-2026-0024; review gate →
    DLMS-2026-0025; approval gate → DLMS-2026-0026; storage gate →
    DLMS-2026-0027; distribution gate → DLMS-2026-0028; archival gate →
    DLMS-2026-0029. No stage may use a DoD template designated for a
    different stage.
  test: >
    For each DoD record: the record's template_ref field matches the
    designated template for the declared stage. A mismatched template
    reference produces a dod-failed audit event and blocks advancement.
  checked_by: DoD Verifier; Audit Trail Agent

### Stage_Gate_Independence

R03:
  rule: >
    The agent that produces the DoD record for a given stage gate must not
    be the same agent that verifies it. The DoD producer and DoD verifier
    must be distinct agent identities as defined in Verification
    Independence Policy (DLMS-2026-0014 R01–R06). This requirement applies
    at every stage gate without exception.
  test: >
    For each DoD record: producer_agent_id ≠ verifier_agent_id as recorded
    in the DoD record and associated audit events. Matching identities
    constitute an independence violation.
  checked_by: DoD Verifier; Audit Trail Agent; Approval Gate Agent

R04:
  rule: >
    The DoD verifier must hold a read tool for the document class under
    evaluation and a verify tool for the relevant stage gate. The DoD
    verifier must not hold a write tool for the document being evaluated,
    a submit tool for the same stage gate, or any execution tool that
    constitutes participation in the stage's work product.
  test: >
    DoD verifier's declared tool set contains: read:[document-class] AND
    verify:[stage-gate]. DoD verifier's tool set does not contain:
    write:[doc] OR submit:[stage-gate] OR any execution tool for that stage.
  checked_by: Stage Orchestrator; Agent Format Validator

### Stage_Gate_Binding

R05:
  rule: >
    The creation stage gate requires a DoD record produced using
    DLMS-2026-0024. The Creation Orchestrator is the DoD producer. The
    Stage Verifier in the creation-verifier role is the DoD verifier. A
    document that fails the creation DoD must not be submitted to the
    review stage; its status must not be set to under_review.
  test: >
    document.status == 'under_review' → dod-passed event exists for
    stage: creation, referencing this doc_id, with timestamp preceding
    the status-transitioned event.
  checked_by: Creation Orchestrator; Status Transition Agent

R06:
  rule: >
    The review stage gate requires a DoD record produced using
    DLMS-2026-0025. The Review Synthesizer is the DoD producer. The
    Stage Verifier in the review-verifier role is the DoD verifier. A
    document that fails the review DoD must not be submitted to the
    approval gate.
  test: >
    Document entering approval gate → dod-passed event exists for
    stage: review, referencing this doc_id, with timestamp preceding
    the approval-gate-opened event.
  checked_by: Review Synthesizer; Approval Gate Agent

R07:
  rule: >
    The approval stage gate requires a DoD record produced using
    DLMS-2026-0026. The Approval Gate Agent is the DoD producer. The
    Stage Verifier in the approval-verifier role is the DoD verifier.
    The approval DoD must be verified before the Status Transition Agent
    sets status to approved. The approval DoD is distinct from the
    approval decision itself — both must occur.
  test: >
    status-transitioned event to approved → dod-passed event for
    stage: approval exists with timestamp preceding the
    status-transitioned event timestamp.
  checked_by: Approval Gate Agent; Status Transition Agent

R08:
  rule: >
    The storage stage gate requires a DoD record produced using
    DLMS-2026-0027. The Storage Agent is the DoD producer. The Stage
    Verifier in the storage-verifier role is the DoD verifier. A
    document that fails the storage DoD must not advance to the
    distribution stage.
  test: >
    Distribution stage opened → dod-passed event for stage: storage
    exists with timestamp preceding the distribution-stage-opened event.
  checked_by: Storage Agent; Distribution Orchestrator

R09:
  rule: >
    The distribution stage gate requires a DoD record produced using
    DLMS-2026-0028. The Distribution Orchestrator is the DoD producer.
    The Stage Verifier in the distribution-verifier role is the DoD
    verifier. A document that fails the distribution DoD must not enter
    archival evaluation.
  test: >
    Archival eligibility check event → dod-passed event for stage:
    distribution exists for this doc_id with timestamp preceding the
    archival-eligibility-check event.
  checked_by: Distribution Orchestrator; Archival Stage Orchestrator

R10:
  rule: >
    The archival stage gate requires a DoD record produced using
    DLMS-2026-0029. The Archival Stage Orchestrator is the DoD producer.
    The Stage Verifier in the archival-verifier role is the DoD verifier.
    A document that fails the archival DoD must not transition to
    archived status.
  test: >
    status-transitioned to archived → dod-passed event for stage:
    archival exists with timestamp preceding the status-transitioned
    event timestamp.
  checked_by: Archival Stage Orchestrator; Status Transition Agent

### Failure_Handling

R11:
  rule: >
    A single fail verdict on any mandatory checklist item in a DoD record
    produces a DoD-fail outcome for the entire record. The DoD-fail outcome
    unconditionally blocks stage advancement. No majority pass logic,
    weighted scoring, or exception mechanism may override a fail on a
    mandatory checklist item.
  test: >
    For any DoD record: IF any mandatory_item.verdict == fail THEN
    DoD record overall_verdict == fail AND no stage-advancement event
    is produced for this doc_id until a new DoD record is produced and
    verified with all mandatory items passing.
  checked_by: DoD Verifier; Stage Orchestrator

R12:
  rule: >
    A DoD-fail outcome must produce a dod-failed audit event and a
    return-to-stage directive addressed to the originating stage
    orchestrator. The return-to-stage directive must cite the failing
    mandatory checklist item identifier(s). The Stage Orchestrator must
    not advance the document; it must address the failing conditions and
    initiate a new DoD cycle.
  test: >
    On any DoD-fail: audit event type dod-failed exists with doc_id,
    stage, and failing_items[] populated AND a return-to-stage directive
    is dispatched before any further stage-advancement action on this
    doc_id.
  checked_by: Audit Trail Agent; Stage Orchestrator

### Context_Boundary

R13:
  rule: >
    The DoD Verifier agent must operate within a strict context boundary
    per Agent Context Boundary Policy (DLMS-2026-0016). Its reads list
    must contain only: the document under evaluation AND the applicable
    stage DoD template. The DoD Verifier must not read other documents'
    DoD records, prior version DoD records for the same document, or
    any agent deliberation artefacts from the stage being verified.
  test: >
    All reads by a DoD Verifier agent during a verification task are
    confined to: the target doc_id's current version file AND the
    designated stage DoD template. Any read outside this set is a
    context boundary violation per DLMS-2026-0016.
  checked_by: Audit Trail Agent; Agent Behaviour Analyst

### Audit_Requirements

R14:
  rule: >
    A dod-passed audit event must be logged by the Audit Trail Agent for
    every DoD record that passes verification. The event must include:
    doc_id, stage, dod_template_ref, producer_agent_id, verifier_agent_id,
    and timestamp. The dod-passed event is the authoritative precondition
    receipt for stage advancement.
  test: >
    For every verified DoD record with outcome: pass — an audit event of
    type dod-passed exists with all six required fields populated before
    any stage-advancement event for the same doc_id and stage.
  checked_by: Audit Trail Agent

R15:
  rule: >
    A dod-failed audit event must be logged for every DoD record that
    fails verification. The event must include: doc_id, stage,
    failing_items[], producer_agent_id, verifier_agent_id, and timestamp.
    dod-failed events are permanent audit trail records and may not be
    deleted or suppressed.
  test: >
    For every DoD record with any mandatory_item.verdict == fail: audit
    event of type dod-failed exists with all six required fields populated,
    including a non-empty failing_items array.
  checked_by: Audit Trail Agent

## EXCEPTIONS_PROCESS
Tier 3 exceptions are permitted on a time-limited basis with SysAdmin
approval. To request an exception to any rule in this policy: (1) The
requesting agent produces a policy-exception-request artefact addressed
to the SysAdmin directive queue, citing the rule reference, the reason
the rule cannot be satisfied, and the proposed mitigating controls.
(2) sysadmin:dlm-sysadmin reviews and, if approved, issues a
policy-exception-grant directive specifying the rule, scope, expiry date,
and audit conditions. (3) The exception is logged as a policy-exception
audit event and is visible in the next CI cycle report. No exception may
extend beyond 90 days without renewal. No exception may waive R01, R03,
or R11. The six mandatory stage gates (R01) and the independence
requirement (R03) are foundational to this policy and are not subject
to exception under any conditions.

## ENFORCEMENT
  primary_agent:    Stage Orchestrators (creation, review, approval, storage,
                    distribution, archival); Audit Trail Agent
  gate_positions:
    - All six stage gates: Stage Verifier validates DoD completeness and
      independence before any stage-advancement event is produced
    - Status Transition Agent: validates a preceding dod-passed event for
      the relevant stage before executing any status transition that
      constitutes stage advancement
    - Approval Gate Agent: validates Approval DoD independently before
      approval is granted
  audit: >
    All DoD outcomes are logged as dod-passed or dod-failed events with
    the six required fields. All context boundary checks by DoD Verifier
    agents are logged per DLMS-2026-0015. Return-to-stage directives are
    logged with the ruling checklist item reference(s).
  violation_type:   Tier 3 operational violation
  escalation: >
    Stage advancement without a preceding dod-passed event is an immediate
    SysAdmin escalation. Independence violations (R03) are immediately
    escalated to sysadmin:dlm-sysadmin. Context boundary violations by
    DoD Verifier agents are flagged in the next CI cycle report.

## REVIEW_SCHEDULE
  interval_max:      6 months (Tier 3 maximum)
  trigger_conditions:
    - A new stage gate is introduced to the DLMS lifecycle
    - A DoD template (DLMS-2026-0024 through DLMS-2026-0029) is amended
      in a way that affects the mandatory checklist item set or the
      template binding declared in R02
    - Verification Independence Policy (DLMS-2026-0014) is amended in
      a way that affects the independence definition applied in R03
    - A systematic DoD failure pattern is detected by CI across multiple
      documents or concentrated at a single stage gate
