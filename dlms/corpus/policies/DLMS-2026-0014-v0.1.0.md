## SUMMARY
This policy governs verification independence across all DLMS lifecycle
stages and document authorship. No agent that creates, authors, or
contributes to producing an artefact may also verify or approve that same
artefact. This is a Tier 2 policy directly enforcing Principle 5
(Structural Verification Independence).

## SCOPE
Applies to: all DLMS agents that produce, verify, or approve documents
or stage artefacts; all document frontmatter fields that record agent
identity (created_by, verified_by, approved_by); all DLMS procedure
STEPS where a verification step follows a production step; all stage
orchestrators that route artefacts for verification.

Excludes: Read-only agents (e.g. Classification Agent reading a document
to assign tags does not constitute production and does not trigger
independence requirements); agents that consume artefacts for indexing
or distribution without modifying or producing them.

Bootstrap exception: DLMS-2026-0001 through DLMS-2026-0004 were
produced by bootstrap:design-team and have null approved_by and
verified_by. These documents are exempt from independence enforcement
and must be formally reviewed and approved under this policy when the
approval pipeline is operational.

## DEFINITIONS

actor:
  The agent or role recorded as performing a specific action in a
  procedure step, frontmatter field, or audit event.

contributing agent:
  Any agent that produces, transforms, drafts, or substantively
  modifies an artefact during a stage. Being in the execution path
  of a stage makes an agent a contributing agent for that stage's output.

independence:
  The property of an actor being structurally distinct from any other
  actor that produced or contributed to the artefact being evaluated.
  Independence is determined by agent identity (agent ID), not by
  agent type or role class. Two invocations of the same agent role
  are not independent.

production step:
  Any step in a DLMS procedure whose primary output is an artefact
  that a subsequent verification step will check.

verification step:
  Any step in a DLMS procedure whose purpose is to confirm that a
  production step's output is correct, complete, or compliant.

## RULES

### Document_Authorship_Independence

R01:
  rule: >
    The agent recorded in created_by must differ from the agent
    recorded in verified_by. No agent may verify a document it created.
  test: >
    created_by != verified_by
    (where both fields are non-null)
  checked_by: Approval Gate Agent; Agent Format Validator

R02:
  rule: >
    The agent recorded in verified_by must differ from the agent
    recorded in approved_by. No agent may approve a document it verified.
  test: >
    verified_by != approved_by
    (where both fields are non-null)
  checked_by: Approval Gate Agent

R03:
  rule: >
    The agent recorded in created_by must differ from the agent
    recorded in approved_by. No agent may approve a document it created.
  test: >
    created_by != approved_by
    (where both fields are non-null)
  checked_by: Approval Gate Agent

R04:
  rule: >
    All three identity fields (created_by, verified_by, approved_by)
    must be pairwise distinct when all three are non-null. No single
    agent may hold more than one of these roles on the same document.
  test: >
    created_by != verified_by AND
    verified_by != approved_by AND
    created_by != approved_by
  checked_by: Approval Gate Agent (pre-approval gate check)

### Stage_Artefact_Independence

R05:
  rule: >
    No Stage Verifier agent may verify a stage artefact that it
    contributed to producing during that same stage execution.
    The Stage Orchestrator must assign verification to an agent
    that was not in the production execution path.
  test: >
    For each stage completion event:
    agent_id of Stage Verifier NOT IN set of contributing_agents
    recorded in the stage's audit trail.
  checked_by: Stage Orchestrator (assignment gate);
              Audit Trail Agent (post-stage check)

R06:
  rule: >
    Independence is determined by agent identity, not agent type.
    Two separate invocations of the same agent role do not satisfy
    the independence requirement. Different agent IDs are required.
  test: >
    The agent IDs compared must be distinct endpoint identifiers,
    not role class names. Role-level deduplication is insufficient.
  checked_by: Audit Trail Agent; Agent Behaviour Analyst

### Procedure_Step_Independence

R07:
  rule: >
    In all DLMS procedures, the actor of a verification step must
    differ from the actor of the production step whose output it verifies.
    This applies to adjacent and non-adjacent step pairs where the
    relationship is verification.
  test: >
    For all step pairs (S_producer, S_verifier) where S_verifier
    verifies the output of S_producer:
    S_producer.actor != S_verifier.actor
  checked_by: Template Validator (at procedure authoring);
              Perspective Reviewer (lens-accuracy)

R08:
  rule: >
    Procedures authored in the DLMS must declare the actor for every
    step. Steps with actor: null or actor: any are invalid.
    Ambiguous actor assignment is prohibited.
  test: >
    For all steps S in any procedure: S.actor != null AND
    S.actor matches regex ^(agent|sysadmin|bootstrap):[a-z-]+$
  checked_by: Template Validator; Agent Format Validator

### Approval_Gate_Enforcement

R09:
  rule: >
    The Approval Gate Agent must perform an independence check as
    a mandatory pre-approval condition. If any independence violation
    is detected in the document's frontmatter or stage history,
    approval is blocked and the violation is logged.
  test: >
    Approval Gate Agent independence_check == PASS before
    status transition to approved is permitted.
    A failed check produces an audit event of type: independence-violation.
  checked_by: Approval Gate Agent; Audit Trail Agent

R10:
  rule: >
    A document whose independence check has failed may not be
    re-submitted for approval until the violation is resolved
    and a new verification pass is completed by an independent agent.
  test: >
    If audit trail contains event type: independence-violation for
    this doc_id AND no subsequent event type: independence-resolved
    exists, approval is blocked.
  checked_by: Approval Gate Agent

## EXCEPTIONS_PROCESS
No exceptions process applies to this policy. Verification independence
is a structural invariant of the DLMS — it cannot be waived on a
per-document basis. The bootstrap exception declared in SCOPE is the
only recognised deviation and is fixed in time to Wave-1 documents only.

## ENFORCEMENT
  primary_agent:    Approval Gate Agent
  gate_positions:
    - Pre-approval check: Approval Gate Agent validates R01–R04 and R09
      before any status transition to approved
    - Stage assignment: Stage Orchestrator enforces R05 when assigning
      verification tasks
    - Procedure authoring: Template Validator enforces R07–R08 when
      a procedure document is validated
  audit: >
    All independence checks are logged by Audit Trail Agent with
    event types: independence-check-pass, independence-check-fail,
    independence-violation, independence-resolved.
    Every approval event references the independence-check-pass
    event in its payload.
  violation_type:   Tier 2 principles violation
  escalation: >
    Independence violations are immediately escalated to
    sysadmin:dlm-sysadmin via SysAdmin Escalation Policy.
    No lower-tier resolution path exists for Tier 2 violations.

## REVIEW_SCHEDULE
  interval_max:      12 months (Tier 2 maximum)
  trigger_conditions:
    - A new agent role is introduced that participates in both
      production and verification paths in the same stage
    - An independence violation pattern is detected by Agent
      Behaviour Analyst across multiple documents
    - A CI cycle report identifies a systematic bypass of the
      independence check gate
    - A structural change to the lifecycle pipeline adds or removes
      a verification step
