## SUMMARY
This policy governs all preconditions, structural requirements, and agent
constraints for creating a new document in the DLMS corpus. No document
may enter the DLMS outside the creation process defined here. This is a
Tier 3 Operational Lifecycle policy.

## SCOPE
Applies to: all agents and roles that initiate document creation; the
Creation Orchestrator; the Document Author Agent; the Agent Format Validator
at the creation gate; all DLMS documents regardless of doc_type; the
Naming Convention Enforcer for doc_id reservation; the Audit Trail Agent
for creation event logging.

Excludes: the four Wave-1 bootstrap documents (DLMS-2026-0001 through
DLMS-2026-0004), which were created before this policy existed and are
exempt by declaration. All subsequent documents must comply fully.

Bootstrap exception: No new bootstrap exception may be declared
unilaterally by any agent. Bootstrap exceptions require SysAdmin
approval and must be recorded in this policy's SCOPE by formal amendment.

## DEFINITIONS

creation gate:
  The validation checkpoint at which the Agent Format Validator confirms
  all preconditions are met before the Document Author Agent begins
  writing content. No authoring commences before the creation gate passes.

doc_id reservation:
  The act of the Naming Convention Enforcer assigning the next sequential
  doc_id for a given calendar year and recording it in the DLMS registry
  as in-use. Reservation is atomic — no two documents may hold the same
  doc_id at any point, including during concurrent creation operations.

Document Author Agent:
  The agent responsible for producing a document's frontmatter and body
  content. The Document Author Agent holds a write tool scoped to the
  target corpus directory only. It does not hold tools to read other
  corpus documents, write to registry files, or modify existing documents.

minimum viable document:
  A document that has passed the creation gate: all 20 frontmatter fields
  are populated, the file is correctly named per DLMS-2026-0003, all
  body sections required by the applicable template are present, and the
  creation audit event has been logged.

template assignment:
  The binding of a document to a specific template doc_id and version at
  creation time, recorded in the template_id and template_ver fields.
  Once set, template assignment is immutable for the lifetime of the
  document. A doc_type change would require a new document.

## RULES

### Precondition_Gate

R01:
  rule: >
    A doc_id must be reserved from the DLMS registry by the Naming
    Convention Enforcer before the Document Author Agent activates.
    No document may be authored without a pre-assigned doc_id. The
    doc_id format must comply with DLMS-2026-0003. Reservation
    is recorded as a doc_id-reserved audit event.
  test: >
    At creation gate: DLMS registry contains an in-use entry for
    the doc_id with status: reserved AND reserved_at is non-null AND
    a doc_id-reserved audit event exists for this doc_id.
  checked_by: Naming Convention Enforcer; Creation Orchestrator

R02:
  rule: >
    An approved template must exist for the document's doc_type before
    authoring begins. The applicable template is the most recent approved
    version of the doc_type's designated TMPL-* document. No document
    may be authored against a draft or superseded template.
  test: >
    Template T exists where T.template_id == applicable_tmpl_id AND
    T.status == 'approved'. If no approved template exists for the
    doc_type, creation is blocked.
  checked_by: Creation Orchestrator; Agent Format Validator

R03:
  rule: >
    The target file path must conform to the directory assignment rules
    in Naming Convention Policy (DLMS-2026-0003). The file must not
    already exist at that path. If a file with the target path exists,
    creation is blocked and escalated.
  test: >
    file_path matches naming convention AND
    NOT exists(file_path in corpus)
  checked_by: Naming Convention Enforcer; Creation Orchestrator

R04:
  rule: >
    A creation Definition of Done (DoD) instance must be initialised
    using TMPL-dod-creation-001 (DLMS-2026-0024) before the Document
    Author Agent activates. The DoD is the contract against which the
    creation stage output will be verified.
  test: >
    A DoD artefact conforming to DLMS-2026-0024 exists for this
    doc_id with status: open before author activation timestamp.
  checked_by: Creation Orchestrator; Stage Verifier

### Frontmatter_Completeness

R05:
  rule: >
    All 20 core frontmatter fields must be populated in canonical order
    before a document is submitted as a minimum viable document. No field
    may be absent. Fields that are validly null (approved_at, approved_by,
    verified_by, supersedes, superseded_by) must be written as null —
    not omitted.
  test: >
    Agent Format Validator confirms: count of frontmatter fields >= 20 AND
    all 20 fields present AND canonical order matches R01 of
    DLMS-2026-0018 AND no field is absent.
  checked_by: Agent Format Validator

R06:
  rule: >
    The status field must be set to 'draft' at creation. No document
    may be created with any other status value. The Status Transition
    Agent owns all subsequent status changes.
  test: >
    status == 'draft' in all newly created documents.
  checked_by: Agent Format Validator; Status Transition Agent

R07:
  rule: >
    The version field must be set to '0.1.0' at creation. No document
    may be created with any other version value.
  test: >
    version == '0.1.0' in all newly created documents.
  checked_by: Agent Format Validator; Version Control Agent

R08:
  rule: >
    The template_id and template_ver fields must reference the approved
    template used to author this document. For non-bootstrap documents,
    template_id must match the applicable TMPL-* alias for the doc_type.
    template_ver must match the version of that template at creation time.
  test: >
    template_id matches applicable_tmpl_id AND
    template_ver == version_of(template_id).at_creation_time
  checked_by: Agent Format Validator; Naming Convention Enforcer

### Context_Boundary

R09:
  rule: >
    The Document Author Agent must operate within the context boundary
    declared in its approved specification (DLMS-2026-0016 R01–R02).
    Its reads list must contain only: the applicable template document
    and the Naming Convention Policy (DLMS-2026-0003). It must not
    read other corpus documents during authoring.
  test: >
    All reads by Document Author Agent during a creation task are
    confined to: template_id document AND DLMS-2026-0003.
    Any read outside this set is a context boundary violation.
  checked_by: Audit Trail Agent; Agent Behaviour Analyst

R10:
  rule: >
    The Document Author Agent must write exactly one file per creation
    task: the new document at its reserved path. No other write
    operations are permitted during a creation task.
  test: >
    count(writes by Document Author Agent in creation task) == 1 AND
    write target == reserved_path for this doc_id.
  checked_by: Audit Trail Agent

### Audit_Requirements

R11:
  rule: >
    A creation-complete audit event must be logged by the Audit Trail
    Agent upon successful creation gate passage. The event must include:
    doc_id, doc_type, file_path, template_id, created_by, created_at,
    and a reference to the DoD artefact.
  test: >
    An audit event of type: creation-complete exists for this doc_id
    with all six required fields populated AND logged before the
    document enters review.
  checked_by: Audit Trail Agent; Stage Verifier

R12:
  rule: >
    If the creation gate fails (any R01–R08 check fails), a
    creation-blocked audit event must be logged specifying the
    failing rule reference and blocking reason. Creation must
    not proceed past a failed gate.
  test: >
    IF any precondition check returns FAIL:
    audit event type: creation-blocked exists with rule_ref and
    reason populated AND Document Author Agent is not activated.
  checked_by: Creation Orchestrator; Audit Trail Agent

## EXCEPTIONS_PROCESS
Tier 3 exceptions are permitted on a time-limited basis with SysAdmin
approval. To request an exception to any rule in this policy:
(1) The requesting agent produces a policy-exception-request artefact
addressed to the SysAdmin directive queue, citing the rule reference,
the reason the rule cannot be satisfied, and the proposed mitigating
controls. (2) sysadmin:dlm-sysadmin reviews and, if approved, issues a
policy-exception-grant directive specifying the rule, scope, expiry date,
and audit conditions. (3) The exception is logged as a policy-exception
audit event and is visible in the next CI cycle report. No exception may
extend beyond 90 days without renewal. No exception may waive R01 or R11.

## ENFORCEMENT
  primary_agent:    Creation Orchestrator; Agent Format Validator
  gate_positions:
    - Creation gate: Agent Format Validator validates R01–R08 before
      Document Author Agent activates
    - Post-creation: Audit Trail Agent validates R11 after creation completes
    - Stage Verifier: validates DoD completion criteria at stage closure
  audit: >
    All creation gate outcomes are logged as creation-complete or
    creation-blocked events. Creation gate pass events reference the
    doc_id, template_id, and DoD artefact. All context boundary
    checks are logged per DLMS-2026-0015.
  violation_type:   Tier 3 operational violation
  escalation: >
    Violations of R01, R03, R10, or R12 are immediately escalated to
    sysadmin:dlm-sysadmin per SysAdmin Escalation Policy. All other
    violations are flagged in the next CI cycle report for SysAdmin
    review within the CI resolution window.

## REVIEW_SCHEDULE
  interval_max:      6 months (Tier 3 maximum)
  trigger_conditions:
    - A new doc_type is introduced requiring a creation rule variant
    - A systematic creation gate failure pattern is detected by CI
    - The Document Schema Policy (DLMS-2026-0004) is amended in a way
      that affects frontmatter completeness requirements
    - The Naming Convention Policy (DLMS-2026-0003) is amended in a
      way that affects doc_id reservation or file path rules
