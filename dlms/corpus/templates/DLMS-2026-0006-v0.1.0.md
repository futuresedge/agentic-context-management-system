## SUMMARY
This template defines the canonical structure for all standard documents in
the DLMS corpus. Standards specify technical, structural, or behavioural
requirements using RFC 2119 conformance language (MUST, SHOULD, MAY). They
are distinct from policies in that they specify what a thing must be, not
what an actor must do.

## REQUIRED_SECTIONS

SUMMARY:
  heading:     ## SUMMARY
  required:    true
  position:    1
  description: >
    A dense, factual statement of what this standard specifies,
    its standard_type, and the artefacts or agents it governs.
  constraints:
    - Exactly 2–3 sentences
    - Must identify the standard type and subject domain

SCOPE:
  heading:     ## SCOPE
  required:    true
  position:    2
  description: >
    What this standard applies to and what it explicitly excludes.
  constraints:
    - At least one 'Applies to:' statement
    - At least one 'Excludes:' statement
    - If no exclusions: "Excludes: nothing within the DLMS"

DEFINITIONS:
  heading:     ## DEFINITIONS
  required:    true
  position:    3
  description: >
    Definitions of terms used in NORMATIVE_REQUIREMENTS that carry
    specific meaning within this standard's domain. Alphabetical.
  constraints:
    - Only terms used in this standard's requirements are defined
    - Must not contradict definitions in approved policies or standards
    - If no domain-specific terms: state "No domain-specific definitions."

NORMATIVE_REQUIREMENTS:
  heading:     ## NORMATIVE_REQUIREMENTS
  required:    true
  position:    4
  description: >
    The enumerated requirements that constitute this standard.
    Each requirement uses RFC 2119 conformance language and is
    independently verifiable.
  conformance_keywords:
    MUST:      Absolute requirement. Non-compliance = standard violation.
    MUST_NOT:  Absolute prohibition. Non-compliance = standard violation.
    SHOULD:    Recommended. Deviation requires documented rationale.
    SHOULD_NOT: Not recommended. Adoption requires documented rationale.
    MAY:       Optional. Permitted but not required.
  requirement_schema:
    id:
      type:     string
      format:   NR prefix + two-digit sequential number (NR01, NR02, …)
      required: true
    conformance:
      type:     enum
      values:   [MUST, MUST_NOT, SHOULD, SHOULD_NOT, MAY]
      required: true
    requirement:
      type:     string
      required: true
      description: >
        A declarative statement using exactly one conformance keyword.
        Present tense. Specifies what a thing must be, have, or satisfy.
    rationale:
      type:     string
      required: false
      description: >
        Brief explanation of why this requirement exists.
        Mandatory for all SHOULD and SHOULD_NOT requirements.
    test:
      type:     string
      required: true
      description: How compliance is verified. Agent-parseable.
    checked_by:
      type:     string
      required: true
  constraints:
    - Minimum 1 requirement; no maximum
    - IDs are sequential with no gaps from NR01
    - MUST and MUST_NOT requirements have no exceptions process
    - SHOULD and SHOULD_NOT deviations must be documented
    - Requirements may be grouped under ### subheadings for readability

RATIONALE:
  heading:     ## RATIONALE
  required:    true
  position:    5
  description: >
    The design reasoning behind this standard as a whole. Explains
    why these requirements are the right solution, what alternatives
    were considered, and what problem is being solved.
  constraints:
    - Not normative — nothing in RATIONALE constitutes a requirement
    - 1–5 paragraphs; dense and direct
    - Must reference the policy or system principle this standard serves

COMPLIANCE_CHECK:
  heading:     ## COMPLIANCE_CHECK
  required:    true
  position:    6
  description: >
    A structured summary of all MUST and MUST_NOT requirements with
    their checking agent and gate position in the pipeline. Provides
    a single-glance conformance checklist for verifier agents.
  format: >
    For each MUST/MUST_NOT requirement:
    [NR_id] | [conformance] | [test summary] | [checked_by] | [gate_position]
  constraints:
    - Only MUST and MUST_NOT requirements appear here
    - SHOULD and SHOULD_NOT requirements are tracked separately
      by the Quality Monitor against documented deviations
    - Gate position refers to the DLMS lifecycle stage at which
      the check occurs

REVIEW_SCHEDULE:
  heading:     ## REVIEW_SCHEDULE
  required:    true
  position:    7
  description: Maximum review interval and unscheduled review triggers.
  required_fields:
    interval_max:      6 months maximum (Tier 4 standard)
    trigger_conditions: Minimum 2 conditions including at least one CI condition.

CHANGE_LOG:
  heading:     ## CHANGE_LOG
  required:    true
  position:    last
  format:      "- v[version] | [YYYY-MM-DD] | [agent_id] | [change summary]"
  constraints:
    - Newest version first
    - One entry per version; immutable once written

## OPTIONAL_SECTIONS

NOTES:
  heading:     ## NOTES
  description: Non-normative commentary or design rationale.
  when_to_include: When design decisions benefit from explanation.
  position:    After CHANGE_LOG

MIGRATION_GUIDANCE:
  heading:     ## MIGRATION_GUIDANCE
  description: >
    Instructions for updating artefacts that conform to an older
    version of this standard when a major version is released.
  when_to_include: Major version increments only.
  position:    After CHANGE_LOG, before NOTES if both present

## VALIDATION_RULES

V01:
  rule:     All eight REQUIRED_SECTIONS must be present in prescribed order.
  test:     >
    Sections SUMMARY, SCOPE, DEFINITIONS, NORMATIVE_REQUIREMENTS, RATIONALE,
    COMPLIANCE_CHECK, REVIEW_SCHEDULE, CHANGE_LOG all present and in sequence.
  checked_by: Template Validator

V02:
  rule:     doc_type must be 'standard'. standard_type must be present
            with a value from the approved enum.
  test:     >
    doc_type == 'standard' AND standard_type IN
    [technical, structural, behavioural]
  checked_by: Template Validator; Agent Format Validator

V03:
  rule:     retention_class must be RC-permanent for all standard documents.
  test:     retention_class == 'RC-permanent'
  checked_by: Indexing Verifier

V04:
  rule:     NORMATIVE_REQUIREMENTS must contain at least one requirement.
            Every requirement must have id, conformance, requirement,
            test, and checked_by. SHOULD and SHOULD_NOT requirements
            must have a non-null rationale.
  test:     >
    len(NORMATIVE_REQUIREMENTS entries) >= 1 AND
    for all NR: NR.id != null AND NR.conformance != null AND
    NR.requirement != null AND NR.test != null AND
    NR.checked_by != null AND
    IF NR.conformance IN [SHOULD, SHOULD_NOT] THEN NR.rationale != null
  checked_by: Template Validator

V05:
  rule:     Each requirement must use exactly one conformance keyword
            (MUST, MUST_NOT, SHOULD, SHOULD_NOT, or MAY). Requirement
            IDs must be sequential from NR01 with no gaps.
  test:     >
    For all NR: NR.conformance IN [MUST, MUST_NOT, SHOULD, SHOULD_NOT, MAY]
    AND NR.requirement contains exactly one conformance keyword AND
    IDs form a contiguous sequence from NR01.
  checked_by: Template Validator

V06:
  rule:     COMPLIANCE_CHECK must contain an entry for every MUST and
            MUST_NOT requirement in NORMATIVE_REQUIREMENTS.
  test:     >
    count(COMPLIANCE_CHECK entries) ==
    count(NR where conformance IN [MUST, MUST_NOT])
  checked_by: Template Validator

V07:
  rule:     dependencies[] must include is-governed-by DLMS-2026-0001.
            If implements_policy is non-null, it must appear in
            dependencies[] with rel: implements.
  test:     >
    dependencies contains doc_id == DLMS-2026-0001 AND
    rel == is-governed-by AND
    IF implements_policy != null THEN
    dependencies contains doc_id == implements_policy AND
    rel == implements
  checked_by: Dependency Index Updater; Indexing Verifier

V08:
  rule:     CHANGE_LOG must have one entry per version, newest first,
            in the prescribed format.
  test:     >
    len(CHANGE_LOG entries) == len(version history) AND
    CHANGE_LOG[0].version == current version AND
    all entries match prescribed format.
  checked_by: Storage Verifier; Version Control Agent
