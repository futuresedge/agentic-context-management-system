## SUMMARY
This template defines the canonical structure for all procedure documents
in the DLMS corpus. Procedures describe how to perform a specific operational
task — they implement policies and standards by providing the step-by-step
execution path, decision logic, and expected outputs that agents and operators
follow to achieve a defined outcome.

trigger:
  name:        trigger
  type:        string
  required:    true
  nullable:    false
  position:    immediately after audit_ref
  description: >
    The event, condition, or agent action that initiates this procedure.
    Written as a declarative statement.
  examples:
    - "DLM SysAdmin Agent issues a change directive for a policy document."
    - "CI Cycle Policy schedule fires and CI Orchestrator activates."
    - "A new document enters the Creation stage."
  constraints:
    - Single trigger per procedure; if multiple triggers exist,
      author separate procedures or use a dispatcher procedure pattern

    and for initiating updates when the procedure becomes stale.
  constraints:

## REQUIRED_SECTIONS

SUMMARY:
  heading:     ## SUMMARY
  required:    true
  position:    1
  description: >
    A dense, factual statement of what this procedure accomplishes,
    what triggers it, and what its primary output is.
  constraints:
    - Exactly 2–3 sentences
    - Must name the trigger and the primary output

SCOPE:
  heading:     ## SCOPE
  required:    true
  position:    2
  description: >
    What this procedure applies to and what it explicitly excludes.
    Identifies the actor(s) responsible for execution.
  constraints:
    - At least one 'Applies to:' statement
    - At least one 'Excludes:' statement
    - At least one 'Executed by:' statement naming the agent or role

PREREQUISITES:
  heading:     ## PREREQUISITES
  required:    true
  position:    3
  description: >
    The conditions that must be true before this procedure begins.
    Each prerequisite is a binary check — either satisfied or not.
  prerequisite_schema:
    id:
      type:     string
      format:   P prefix + two-digit number (P01, P02, …)
      required: true
    condition:
      type:     string
      required: true
      description: >
        A verifiable state that must exist. Written as:
        "[artefact or condition] must [exist / have status X / be approved]."
    checked_by:
      type:     string
      required: true
  constraints:
    - Minimum 1 prerequisite
    - If a prerequisite is not met, the procedure does not begin —
      the gate condition is held and the trigger event is queued
    - Prerequisites are checked by the Stage Orchestrator or
      the procedure_owner agent before Step 1 executes

STEPS:
  heading:     ## STEPS
  required:    true
  position:    4
  description: >
    The ordered sequence of actions that constitute this procedure.
    Each step is atomic — it represents a single, completable action
    by a single agent or role. Steps are numbered sequentially.
  step_schema:
    id:
      type:     string
      format:   S prefix + two-digit number (S01, S02, …)
      required: true
    actor:
      type:     string
      required: true
      format:   agent:[slug] or sysadmin:[slug]
      description: The single agent or role that performs this step.
    action:
      type:     string
      required: true
      description: >
        What the actor does. One sentence, active voice, present tense.
        Begins with a verb. Specifies the input read and the output written.
    reads:
      type:     array of strings
      required: true
      description: File paths or artefact references consumed in this step.
    writes:
      type:     array of strings
      required: true
      description: File paths or artefact references produced in this step.
    on_failure:
      type:     string
      required: true
      description: >
        What happens if this step fails. Options:
        retry — step is retried (specify max_retries).
        escalate — procedure halts; procedure_owner is notified.
        branch — execution moves to a named DECISION_POINT.
  constraints:
    - Minimum 2 steps
    - Step IDs are sequential with no gaps from S01
    - No step may have the same actor as the immediately preceding
      verification step (Verification Independence Policy)
    - Every step that produces a verification artefact must
      have an actor that differs from the step being verified

DECISION_POINTS:
  heading:     ## DECISION_POINTS
  required:    true
  position:    5
  description: >
    Named branch conditions that alter the execution path. Referenced
    in STEPS via the on_failure or on_condition fields.
  decision_schema:
    id:
      type:     string
      format:   D prefix + two-digit number (D01, D02, …)
      required: true
    condition:
      type:     string
      required: true
      description: The binary condition evaluated at this point.
    if_true:
      type:     string
      required: true
      description: The step ID to execute if the condition is true.
    if_false:
      type:     string
      required: true
      description: The step ID to execute or action to take if false.
  constraints:
    - If no decision points exist, state: "No decision points.
      This procedure is linear."
    - All step on_failure: branch references must resolve to a
      valid Decision Point ID

OUTPUTS:
  heading:     ## OUTPUTS
  required:    true
  position:    6
  description: >
    The complete list of artefacts produced by this procedure upon
    successful completion. Provides a definitive checklist for
    the procedure_owner and downstream consumers.
  output_schema:
    artefact:   string — the file name or artefact type produced
    written_by: string — the step ID that produces it
    path:       string — the storage path
    consumed_by: string — the agent or step that reads this output
  constraints:
    - Every artefact written in STEPS must appear here
    - No output may be listed that is not produced in a STEPS entry

ERROR_CONDITIONS:
  heading:     ## ERROR_CONDITIONS
  required:    true
  position:    7
  description: >
    Known failure modes for this procedure, their likely causes,
    and the resolution path for each.
  error_schema:
    id:
      type:     string
      format:   E prefix + two-digit number (E01, E02, …)
      required: true
    condition:
      type:     string
      required: true
      description: The observable failure state.
    likely_cause:
      type:     string
      required: true
    resolution:
      type:     string
      required: true
      description: >
        Steps to resolve. References STEPS IDs, DECISION_POINTS IDs,
        or escalation to procedure_owner.
  constraints:
    - Minimum 1 error condition
    - Every on_failure: escalate in STEPS must have a corresponding
      ERROR_CONDITION entry

REVIEW_SCHEDULE:
  heading:     ## REVIEW_SCHEDULE
  required:    true
  position:    8
  description: Maximum review interval and unscheduled review triggers.
  required_fields:
    interval_max:       6 months maximum (Tier 4 document)
    trigger_conditions: Minimum 2 conditions; at least one CI-related.

CHANGE_LOG:
  heading:     ## CHANGE_LOG
  required:    true
  position:    last
  format:      "- v[version] | [YYYY-MM-DD] | [agent_id] | [change summary]"
  constraints:
    - Newest version first; one entry per version; immutable once written

## OPTIONAL_SECTIONS

NOTES:
  heading:     ## NOTES
  description: Non-normative guidance, rationale, or design context.
  when_to_include: >
    When design decisions or historical context aid maintainers
    or agents consuming this procedure.
  position:    After CHANGE_LOG

EXAMPLES:
  heading:     ## EXAMPLES
  description: >
    One or more worked examples showing the procedure applied to
    a realistic scenario. Illustrates DECISION_POINTS and
    non-linear paths.
  when_to_include: >
    When the procedure has multiple branching paths or the
    sequence of steps is non-obvious.
  position:    After NOTES if present, otherwise after CHANGE_LOG

## VALIDATION_RULES

V01:
  rule:     All nine REQUIRED_SECTIONS must be present in prescribed order.
  test:     >
    Sections SUMMARY, SCOPE, PREREQUISITES, STEPS, DECISION_POINTS,
    OUTPUTS, ERROR_CONDITIONS, REVIEW_SCHEDULE, CHANGE_LOG all present
    and in that sequence.
  checked_by: Template Validator

V02:
  rule:     doc_type must be 'procedure'. trigger, procedure_owner, and
            implements_policy must all be present and non-null.
  test:     >
    doc_type == 'procedure' AND trigger != null AND
    procedure_owner != null AND implements_policy != []
  checked_by: Template Validator; Agent Format Validator

V03:
  rule:     retention_class must be RC-permanent for all procedure documents.
  test:     retention_class == 'RC-permanent'
  checked_by: Indexing Verifier

V04:
  rule:     PREREQUISITES must contain at least one entry. Each entry
            must have id, condition, and checked_by.
  test:     >
    len(PREREQUISITES) >= 1 AND for all P:
    P.id != null AND P.condition != null AND P.checked_by != null
  checked_by: Template Validator

V05:
  rule:     STEPS must contain at least two entries. Each step must
            specify actor, action, reads, writes, and on_failure.
            Step IDs must be sequential from S01.
  test:     >
    len(STEPS) >= 2 AND for all S:
    S.actor != null AND S.action != null AND
    S.reads != null AND S.writes != null AND
    S.on_failure != null AND
    IDs form a contiguous sequence from S01.
  checked_by: Template Validator

V06:
  rule:     No verification step may share an actor with the step it
            verifies (Verification Independence Policy).
  test:     >
    For all step pairs (S_n, S_n+1) where S_n+1 is a verification step:
    S_n.actor != S_n+1.actor
  checked_by: Perspective Reviewer (lens-accuracy); Template Validator

V07:
  rule:     Every artefact written in STEPS must appear in OUTPUTS.
            Every artefact in OUTPUTS must be produced in a STEPS entry.
  test:     >
    set(STEPS[*].writes) == set(OUTPUTS[*].artefact)
  checked_by: Template Validator

V08:
  rule:     Every on_failure: branch reference in STEPS must resolve
            to a valid DECISION_POINTS id. Every on_failure: escalate
            must have a corresponding ERROR_CONDITIONS entry.
  test:     >
    For all S where S.on_failure starts with 'branch':
    referenced D.id exists in DECISION_POINTS AND
    For all S where S.on_failure == 'escalate':
    a corresponding E entry exists in ERROR_CONDITIONS.
  checked_by: Template Validator

V09:
  rule:     implements_policy[] must be non-empty. All listed doc_ids
            must appear in dependencies[] with rel: implements AND
            have status: approved.
  test:     >
    len(implements_policy) >= 1 AND
    for all p in implements_policy:
    p IN dependencies[*].doc_id where rel == implements AND
    referenced doc has status: approved.
  checked_by: Dependency Index Updater; Indexing Verifier

V10:
  rule:     CHANGE_LOG must have one entry per version, newest first,
            in the prescribed format.
  test:     >
    len(CHANGE_LOG entries) == len(version history) AND
    CHANGE_LOG[0].version == current version AND
    all entries match prescribed format.
  checked_by: Storage Verifier; Version Control Agent
