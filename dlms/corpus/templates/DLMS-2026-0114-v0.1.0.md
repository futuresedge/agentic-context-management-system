## SUMMARY
This template defines the mandatory structure, token budget, and encoding
discipline for all .agent.md instruction files and their companion SKILL.md
progressive disclosure files, as authored by the agent-instruction-author
from an approved agent specification (DLMS-2026-0113). An instruction file
that does not conform to this template will fail the instruction_file_authored
gate in the DoD: Agent Creation Stage (DLMS-2026-0115).

## TARGET_DOC_TYPE
agent-instruction-file

## PURPOSE
Agent instruction files encode a verified agent specification (DLMS-2026-0113)
into the format that the VS Code Copilot agent runtime can load and execute.
There are two file types governed by this template: the primary .agent.md file
and the optional companion SKILL.md. Both are translated — not designed —
from the approved specification; the instruction-file author must not invent
new context, tools, or behaviours beyond what the specification authorises.

## FORMAT_A — AGENT_INSTRUCTION_FILE (.agent.md)

The .agent.md file is the primary runtime instruction file. It is stored at
`.github/agents/{role_id}.agent.md` relative to the workspace root.

### Frontmatter_Fields

```yaml
---
name: {Human-readable agent name — Title Case with spaces; matches agent roster entry}
description: "{Single sentence: exact function AND invocation condition. Must match the PURPOSE section of the approved specification verbatim or with only minimal grammatical adjustment for the command format.}"
tools: [{comma-separated list of tool identifiers — must exactly match
         TOOL_ASSIGNMENT in the approved specification}]
model: {Claude Sonnet 4.6 | Claude Haiku 4.5}
       # sonnet: orchestrators, synthesis agents, review agents
       # haiku: narrow executor agents — single-file transform, format
       #        validation, metric capture
user-invocable: false
       # Default for all Tier 15B subagents. Set true only for agents
       # explicitly designed for direct user invocation per the specification.
disable-model-invocation: false
       # Set true only for agents that must not be invocable by other agents.
       # Rare. Requires explicit justification in the approved specification.
---
```

### Body_Structure

The instruction file body must be structured as follows. Deviation from this
structure — including reordering sections, adding un-approved content, or
omitting mandatory sections — constitutes a template violation.

**Constraint: Body is capped at 400 tokens.** Any content that would exceed
400 tokens must be extracted to a SKILL.md companion file (see FORMAT_B).
Token count is measured from the first character after the YAML front matter
closing `---` to the final character of the file.

**Encoding discipline: linter-style, not prose.** Agent instruction files
use structured declarative syntax — field: value, MUST/NEVER lists, and
indented sub-keys. Prose role descriptions ("You are a...", "Your job is...",
"As an agent, you will...") are prohibited. Instructions optimise for
machine readability under context pressure, not for human-readable narrative.

```markdown
READS:   {exact/path/to/input.ext}
         {second resource — file path or tool namespace, if applicable}
WRITES:  {exact/path/to/output.ext}
NEVER:   {specific resource this agent must not access}; {add more as needed}

## GATE_CONDITIONS
# All must be TRUE before this agent begins any work.
- {precondition from STAGE_GATES/PRECONDITIONS in the approved specification}

## OUTPUT_FORMAT
# Precise schema for the output artefact. Field: type/constraints for each.
result:        PASS | FAIL | BLOCKED
agent_id:      {this agent's role_id}
doc_id:        {document or workflow being processed}
input_path:    {path received from orchestrator}
output_path:   {path declared in WRITES above}
{additional fields as declared in the approved specification}
timestamp:     ISO-8601

## RULES
MUST:
  - {Positive obligation drawn directly from the approved specification}
  - {Add one MUST per critical behavioural requirement; minimum 1}
NEVER:
  - {Hard prohibition drawn from CONTEXT_BOUNDARY/NEVER in the specification}
  - read any file not listed in READS above
  - mark result as PASS if any required OUTPUT_FORMAT field is null
  - {Add further constraints from the specification's KNOWN_CONSTRAINTS}

## SKILL_REFS
# Skills loaded on demand only. Not pre-loaded at agent startup.
# Required ONLY if the agent has companion SKILL.md files.
skills:
  - name:         {skill-name}
    path:         .github/skills/{skill-name}/SKILL.md
    load_when:    "{Exact, specific condition — not 'if relevant'}"
    pinned_version: {version string matching the SKILL.md header}
```

### Body_Ordering_Rules

ORDERING_RULE_01:
  rule:    READS/WRITES/NEVER context declaration must be the first content
           block in the body — before any ## section heading. It is the agent's
           declared boundary and must be the first thing evaluated.
  test:    Body line 1 matches /^READS:/ after the frontmatter closing ---

ORDERING_RULE_02:
  rule:    ## RULES (containing MUST and NEVER sub-lists) must be the last
           section before ## SKILL_REFS (if present) or the end of the file.
           No substantive content may follow ## RULES. Boundaries go at
           the bottom; they are not decoration.
  test:    ## RULES is the penultimate or final section; no ## heading that
           contains normative instructions appears after ## RULES

ORDERING_RULE_03:
  rule:    ## GATE_CONDITIONS must immediately follow the context declaration.
           The agent must check gate conditions before executing any step.
  test:    ## GATE_CONDITIONS is the first ## section heading in the body

ORDERING_RULE_04:
  rule:    ## SKILL_REFS, if present, must be the final section.
  test:    If ## SKILL_REFS is present, it is the last ## heading in the file

### Prohibited_Patterns

PROHIBITED_01:
  pattern:   "You are a..."
  reason:    Prose role description. Replace with READS/WRITES/NEVER + RULES.

PROHIBITED_02:
  pattern:   "Your role is..." | "Your job is..." | "As an agent, you..."
  reason:    Prose role description. Same prohibition as PROHIBITED_01.

PROHIBITED_03:
  pattern:   "If relevant, load SKILL.md"
  reason:    Non-specific skill load condition. SKILL_REFS load_when must be
             an exact, evaluable condition — not a vague relevance judgment.

PROHIBITED_04:
  pattern:   Tools declared in frontmatter.tools that have no corresponding
             MUST or step in OUTPUT_FORMAT or RULES
  reason:    Speculative tool assignment. Every declared tool must map to a
             specific step. This check cross-references against the
             TOOL_ASSIGNMENT table in the approved specification.

PROHIBITED_05:
  pattern:   Category references in READS (e.g. "all corpus policies",
             "any tier 4 document", "relevant context files")
  reason:    Category labels violate the Named-Resource Rule. READS must
             name specific files, tool identifiers, or data source names.

## FORMAT_B — SKILL_FILE (SKILL.md)

SKILL.md companion files provide progressive disclosure content that the
primary .agent.md loads on demand. They are stored co-located with their
primary instruction file:
  - Primary:  `.github/agents/{role_id}.agent.md`
  - Skill:    `.github/agents/skills/{role_id}/{skill-name}.SKILL.md`
            — or, for shared skills:
              `.github/skills/{skill-name}/SKILL.md`

### Skill_Frontmatter

```yaml
---
name:         {skill-name}
version:      {semver — must be pinned in the referencing SKILL_REFS entry}
description:  "{Single sentence: exactly what this skill file contains and when it should be loaded. This sentence ALONE is always present in the agent's context — the body is loaded only when the load_when condition is met.}"
applies_to:   [{role_id of the primary agent}]
context_tokens: {approximate token count of this file's body}
---
```

### Skill_Body_Rules

SKILL_RULE_01:
  rule:    Skill file body contains only content that the primary agent
           cannot include within its 400-token body budget, and only
           content that is specific to the task this skill supports.
           General DLMS context, policy text, and tier definitions are
           not appropriate skill file content — they are governance context
           and must not be replicated inside agent files.
  test:    No skill file body contains verbatim text from a DLMS corpus
           policy or standard document

SKILL_RULE_02:
  rule:    Skill file body must not exceed 800 tokens. A skill file
           exceeding 800 tokens provides a signal that the agent is
           over-scoped or that the skill content is not properly focused.
           If content cannot fit in 800 tokens, split into two skill files
           with distinct, specific load_when conditions.
  test:    token_count(skill_body) <= 800

SKILL_RULE_03:
  rule:    Skill files are owned by the agent whose role_id appears in
           applies_to. No skill file may be shared across agents in
           different roles without an explicit applies_to entry for each
           consuming agent and a registered dependency in the consuming
           agent's specification (DLMS-2026-0109 R07).
  test:    Skill file is co-located with the primary agent file OR
           listed in tool-access-registry as a shared skill with all
           consuming agents listed in applies_to

SKILL_RULE_04:
  rule:    Skill file body must begin with a ## PURPOSE section stating in
           one sentence what the skill covers and when it applies.
           Without a ## PURPOSE, the agent cannot evaluate the load_when
           condition reliably.
  test:    First line of skill body is ## PURPOSE AND PURPOSE contains
           one sentence

## TOKEN_BUDGET_ENFORCEMENT

The 400-token body budget for .agent.md files is enforced at gate GATE-05
(instruction_file_authored) in the DoD: Agent Creation Stage (DLMS-2026-0115).
Token counting follows the same tokeniser as the declared model:
  - Claude Haiku 4.5 / Claude Sonnet 4.6 → Anthropic token counting
  - Token count is measured from the body start (first character after the
    closing `---` of frontmatter) to the end of the file
  - Comments (lines beginning with #) COUNT toward the token budget
  - A 10% tolerance window (440 tokens) is permitted for first-draft
    submissions; instructions reviewers must flag any body between 400–440
    tokens with a budget warning, and any body exceeding 440 tokens must
    be returned for refactoring before passing the gate

## VALIDATION_RULES

V01: File is located at .github/agents/{role_id}.agent.md
V02: Frontmatter contains name, description, tools, model, user-invocable. description is an inline single-line string — YAML block scalars (> or |) are prohibited on this field and will cause the runtime to silently drop the value.
V03: tools list exactly matches TOOL_ASSIGNMENT in the approved specification.
V04: model is Claude Haiku 4.5 or Claude Sonnet 4.6.
V05: user-invocable is false unless the specification explicitly states otherwise.
V06: Body begins with READS: as first content after frontmatter.
V07: Body contains WRITES: and NEVER: in the context declaration block.
V08: ## GATE_CONDITIONS is the first ## section.
V09: ## RULES is the penultimate or final ## section.
V10: Body token count is <= 440 tokens (400 target, 440 hard ceiling).
V11: No prohibited patterns (PROHIBITED_01 through PROHIBITED_05) are present.
V12: Every declared tool in tools[] appears in at least one MUST rule or
     OUTPUT_FORMAT field with a specific task step.
V13: SKILL_REFS entries, if present, each have path, load_when, and
     pinned_version fields per DLMS-2026-0109 R04.
V14: Companion SKILL.md files, if present, have a frontmatter with name,
     version, description, applies_to, and context_tokens fields.
V15: Companion SKILL.md body begins with ## PURPOSE as first ## section.
V16: Companion SKILL.md body does not exceed 800 tokens.
