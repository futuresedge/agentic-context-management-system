## SUMMARY
This template defines the mandatory section structure and field format for
all agent specification documents produced by Tier 15B's
agent-specification-author. It is the concrete authoring template that
implements the structural requirements of the Agent Specification Standard
(DLMS-2026-0111). Every agent specification must conform to this template
before it can be reviewed by the agent-specification-reviewer.

## TARGET_DOC_TYPE
agent-specification

## PURPOSE
The agent specification is the authoritative design record for a new or
updated agent class. It bridges the approved agent request (DLMS-2026-0112)
and the agent instruction file (.agent.md) by documenting in precise,
verifiable terms: who the agent is, what it does, what it may access, what
tools it holds, and which policies govern it. The specification is authored
before the instruction file — not after.

## REQUIRED_SECTIONS

The template body below uses {placeholder} for values the
agent-specification-author must supply. All sections marked REQUIRED must
be present and non-empty. Sections marked OPTIONAL may be omitted only when
the specification author has confirmed they do not apply, with a rationale
recorded in the CHANGE_LOG.

## SECTION_CONSTRAINTS

The following constraints supplement DLMS-2026-0111 and are enforced by the
agent-specification-reviewer and agent-specification-verifier:

AGENT_IDENTITY:
  - role_id must be unique across all active and retired agent_class entities
  - status must be "proposed" at initial draft; transitions governed by
    agent-creation-orchestrator
  - request_ref must contain a valid approval_artefact_id that resolves to
    an agent request with status: approved or in_progress

PURPOSE:
  - Exactly one sentence — sentence count is machine-verifiable
  - Must not begin with "This agent" — state the function directly
  - Both the function and the invocation condition must be inferable from
    the sentence without reading any other section

CONTEXT_BOUNDARY/READS:
  - Maximum 5 entries — if more than 5 are required, the agent is over-scoped
  - Each entry must be a specific file path (contains / or .), a named tool
    operation (namespace.operation format), or a named data source identifier
  - Category labels ("all policies", "corpus documents", "tier 4 artefacts")
    are not valid entries (DLMS-2026-0111 NR04)

CONTEXT_BOUNDARY/WRITES:
  - Exactly one artefact — if more than one output is required, split the
    agent into two agents (DLMS-2026-0111 NR05)
  - Path must be a complete, specific file path — not a directory

CONTEXT_BOUNDARY/NEVER:
  - Minimum 1 entry — "none" is not an acceptable value (DLMS-2026-0111 NR06)
  - Recommended minimum 2 entries: the WRITES path of the upstream agent in
    the same workflow, and at least one category of corpus resource that is
    reachable but not relevant to this agent's task

TOOL_ASSIGNMENT:
  - No speculative tool assignment — every tool must map to a named step
  - The assignment of both a write tool and the corresponding verification
    tool (submitVerification) in the same specification is prohibited
    (DLMS-2026-0111 NR09)
  - If the tool_name is a tool namespace prefix (e.g. agentcreation.*), one
    row per specific operation is required — wildcard rows are not permitted

GOVERNING_POLICIES:
  - The `- DLMS-2026-0108` and `- DLMS-2026-0016` entries are mandatory and
    must be listed first before any additional documents
  - Additional policies are added based on the agent's specific function and
    scope; the agent-specification-author is responsible for identifying all
    applicable governing documents at specification time

STAGE_GATES:
  - PRECONDITIONS must reference the upstream agent's output artefact, not
    a generic condition ("task received" is not an acceptable precondition)
  - POSTCONDITIONS must name the specific file path from the WRITES section
    plus any secondary signals (e.g. "result field is non-null", "status is
    PASS")

## VALIDATION_RULES

V01: AGENT_IDENTITY section is present and is the first body section.
V02: AGENT_IDENTITY contains non-empty values for all 6 fields.
V03: PURPOSE section contains exactly one sentence.
V04: CONTEXT_BOUNDARY section contains non-empty READS, WRITES, and NEVER.
V05: READS contains no category labels — all entries are specific identifiers.
V06: WRITES contains exactly one artefact with a non-empty path.
V07: NEVER contains at least one specific, named entry.
V08: TOOL_ASSIGNMENT is a markdown table with exactly three columns.
V09: Every planned tool has exactly one row in TOOL_ASSIGNMENT.
V10: No TOOL_ASSIGNMENT row has an empty or generic task_step.
V11: The specification does not assign both a write tool and
     agentcreation.submitVerification to the same agent.
V12: GOVERNING_POLICIES section lists DLMS-2026-0108 and DLMS-2026-0016.
V13: STAGE_GATES section contains non-empty PRECONDITIONS and POSTCONDITIONS.
V14: CHANGE_LOG is present and is the last section; contains v0.1.0 entry.

## STORAGE

Artefacts conforming to this template are stored as `agent_artefact` entities in
TypeDB. Two distinct `artefact_type` values correspond to the specification stage:

- `agent-spec`: written by `agent-specification-author` via `agentcreation.writeSpec`.
  The `content.sections` JSON object holds all 8 required section names as keys.
- `agent-spec-review`: written by `agent-specification-reviewer` via
  `agentcreation.submitReview`. The `content.result` field is `PASS` or `FAIL`;
  `content.failed_checks` lists any NR IDs that did not pass.

Pipeline agents access both artefact types through `agentcreation.getArtefact`
(query by `role_id` + `artefact_type`). No filesystem copy is created for
either artefact.

Full content JSON schemas for `agent-spec` and `agent-spec-review` are defined in
`.github/skills/agent-creation-patterns/SKILL.md § ARTEFACT_CONTENT_SCHEMAS`.
