## SUMMARY
This template defines the structure of a Definition of Done completion record
for the Agent Creation Stage — the 7-gate lifecycle that governs the production
of every new DLMS agent class under DLMS-2026-0108. The agent-creation-orchestrator
must produce a completed record attesting the passage of all mandatory gates before
a newly created agent class is registered in the TypeDB roster and tool-access-registry.
A single fail verdict on any mandatory gate item blocks registration.

## TARGET_DOC_TYPE
dod-agent-creation-record

## PURPOSE
The Agent Creation Stage DoD is the binding completion gate that confirms a
new agent class is structurally, behaviourally, and governance-compliant before
it enters the active DLMS agent roster. It provides an auditable, sequential
record of the seven creation lifecycle stages, ensuring that no agent is
instantiated without documented evidence of request approval, problem analysis,
specification review, instruction authoring, verification, registry update, and
corpus index update.

## RECORD_SCHEMA

### Header_Fields

FIELD_01:
  name:        dod_id
  type:        string
  required:    true
  nullable:    false
  format:      DOD-agentcreation-{role_id}-{timestamp}
  example:     DOD-agentcreation-agent-specification-author-20260310T1030
  description: Unique identifier for this DoD completion record. Immutable.

FIELD_02:
  name:        role_id
  type:        string
  required:    true
  description: The proposed role_id of the agent class being created.
               Must match the proposed_role_id in the originating agent
               request (DLMS-2026-0112).

FIELD_03:
  name:        request_id
  type:        string (UUID v4)
  required:    true
  description: The request_id from the originating agent request record.
               The agent-creation-orchestrator uses this to link the DoD
               record to the approval chain.

FIELD_04:
  name:        approval_artefact_id
  type:        string
  required:    true
  description: The approval_artefact_id from the approved agent request.
               Must be non-null. This is the authority reference that all
               subsequent workflow stages inherit. A DoD record without a
               valid approval_artefact_id is invalid.

FIELD_05:
  name:        stage
  type:        string
  required:    true
  value:       agent-creation
  description: Fixed value. Identifies this as an Agent Creation Stage DoD
               record. Distinct from the standard corpus document Creation
               stage (DLMS-2026-0024).

FIELD_06:
  name:        evaluated_by
  type:        string
  required:    true
  description: agent_id of the agent-creation-orchestrator completing this
               record. Must be agent:agent-creation-orchestrator.

FIELD_07:
  name:        evaluated_at
  type:        datetime
  required:    true
  format:      ISO 8601 with timezone
  description: Timestamp when the final gate evaluation was completed.

### Gate_Items

Each gate item represents one stage in the 7-stage agent creation lifecycle.
Each item carries three sub-fields:
  result:    pass | fail
  mandatory: true | false
  notes:     string | null  (required when result is fail)

GATE_01:
  id:          GATE-AGENTCREATION-01
  label:       Approved request exists
  stage_name:  Request and Approval
  description: >
    An agent request artefact conforming to DLMS-2026-0112 exists with
    status: approved AND approval_artefact_id non-null. The request must
    have been submitted by an authorised principal and reviewed by the
    agent-creation-orchestrator. No agent creation workflow may begin
    without a fully approved request record.
  check:       TypeDB `agent_artefact` with `artefact_type: agent-request-record` and
               matching `role_id` exists; `approval_artefact_id` is non-null in content
               (assertAgentArtefactExists). For retire_agent requests: `sysadmin_approval_artefact_id`
               also non-null in content when proposed_tier <= 14.
  mandatory:   true
  governed_by: DLMS-2026-0108 R01–R03; DLMS-2026-0112

GATE_02:
  id:          GATE-AGENTCREATION-02
  label:       Problem analysis reviewed
  stage_name:  Problem Analysis
  description: >
    The agent-problem-analyst has produced a problem analysis artefact
    and the agent-creation-orchestrator has confirmed the analysis is
    complete and non-trivial. The analysis must: (a) validate the
    problem_statement from the request, (b) confirm the evidence_of_need
    reference is substantive, (c) identify any existing agents that partially
    address the problem, and (d) state why a new agent class is warranted
    rather than modification of an existing agent. An analysis that
    recommends modification over creation must be escalated; the
    creation workflow is suspended until the discrepancy is resolved.
  check:       TypeDB `agent_artefact` with `artefact_type: agent-problem-analysis` and
               matching `role_id` exists (assertAgentArtefactExists); `content.recommendation`
               is "proceed_with_creation"; `request_artefact_id` in content matches
               the originating `approval_artefact_id`.
  mandatory:   true
  governed_by: DLMS-2026-0108 R04

GATE_03:
  id:          GATE-AGENTCREATION-03
  label:       Specification authored and reviewed
  stage_name:  Specification Authorship and Review
  description: >
    An agent specification artefact conforming to DLMS-2026-0113 exists,
    has passed all 14 validation rules (V01–V14) defined in that template,
    and has been reviewed by the agent-specification-reviewer and found
    compliant with the Agent Specification Standard (DLMS-2026-0111).
    All 14 normative requirements (NR01–NR14) must be satisfied. The
    specification must reference this request's approval_artefact_id in
    AGENT_IDENTITY.request_ref.
  check:       TypeDB `agent_artefact` with `artefact_type: agent-spec` for this `role_id`
               exists with all 14 DLMS-2026-0111 NR requirements recorded as pass in content;
               AND TypeDB `agent_artefact` with `artefact_type: agent-spec-review` for this
               `role_id` exists with `result: PASS` in content (assertAgentArtefactExists
               with requiredContent).
  mandatory:   true
  governed_by: DLMS-2026-0108 R05; DLMS-2026-0111; DLMS-2026-0113

GATE_04:
  id:          GATE-AGENTCREATION-04
  label:       Instruction file authored
  stage_name:  Instruction File Authorship
  description: >
    An instruction file (.agent.md) conforming to DLMS-2026-0114 FORMAT_A
    has been produced by the agent-instruction-author. The file must: (a)
    be located at .github/agents/{role_id}.agent.md, (b) have frontmatter
    with name, description, tools, model, and user-invocable, (c) have a
    body beginning with READS:/WRITES:/NEVER: context declaration, (d) have
    a body token count <= 440 tokens (400-token target with 10% tolerance),
    and (e) contain no prohibited patterns from DLMS-2026-0114
    PROHIBITED_01–PROHIBITED_05. Companion SKILL.md files, if present,
    must also conform to DLMS-2026-0114 FORMAT_B.
  check:       File exists at .github/agents/{role_id}.agent.md AND all
               DLMS-2026-0114 V01–V16 validation rules pass AND body
               token count <= 440.
  mandatory:   true
  governed_by: DLMS-2026-0108 R06; DLMS-2026-0114

GATE_05:
  id:          GATE-AGENTCREATION-05
  label:       Verification passed
  stage_name:  Specification Verification
  description: >
    The agent-specification-verifier has independently verified the
    instruction file (.agent.md) against the approved specification.
    Verification confirms that: (a) every element of the specification's
    CONTEXT_BOUNDARY, TOOL_ASSIGNMENT, GOVERNING_POLICIES, and STAGE_GATES
    sections is faithfully encoded in the instruction file, (b) no content
    in the instruction file exceeds what the specification authorises, and
    (c) the instruction file introduces no new tools, READS entries, or
    NEVER omissions not present in the specification. A verified-pass
    audit event must exist with the verifier's agent_id.
    The agent-specification-verifier must be different from the
    agent-instruction-author (DLMS-2026-0108 R07).
  check:       TypeDB `agent_artefact` with `artefact_type: agent-verification-record` for
               this `role_id` exists with `result: PASS` in content (assertAgentArtefactExists
               with requiredContent); `verifier_actor_id` in content ≠ `instruction_author_actor_id`
               in the referenced `agent-instruction-record`.
  mandatory:   true
  governed_by: DLMS-2026-0108 R07–R08; DLMS-2026-0111 NR01–NR14

GATE_06:
  id:          GATE-AGENTCREATION-06
  label:       Registries updated and audit event emitted
  stage_name:  Registry Update and Registration
  description: >
    The agent-registry-updater has updated all three registries and emitted
    the agent_created audit event in a single atomic transaction: (a) TypeDB
    agent_class entity has been written with all required attributes
    (role_id, tier, tier_label, agent_status: active, agent_description,
    spec_doc_id, instruction_path, agent_created_at, agent_created_by),
    (b) the tool-access-registry has been updated with the new agent's
    permitted tools, (c) dlms/dlms-agent-roster.md has been updated with
    the new agent class entry, and (d) an agent_created audit event with
    the agent's role_id, tier, and approval_artefact_id exists with a
    timestamp matching the roster write transaction.
    Co-transaction failure (roster written without audit event, or vice
    versa) constitutes a data integrity violation.
  check:       TypeDB agent_class entity with role_id exists AND
               agent_status == "active" AND tool-access-registry contains
               entries for this role_id AND dlms-agent-roster.md contains
               this role_id AND an agent_created audit event for this
               role_id exists with timestamp coincident with the roster write.
  mandatory:   true
  governed_by: DLMS-2026-0108 R09–R10; DLMS-2026-0110 R10 (by analogy)

GATE_07:
  id:          GATE-AGENTCREATION-07
  label:       Corpus index updated
  stage_name:  Corpus Index Update
  description: >
    The corpus-index.md has been updated to include the new agent's
    specification document under the Wave 15 section (or the current
    active wave section if a later wave has commenced). The index entry
    must include: doc_id, title, doc_type, tier, and a brief description.
    This gate ensures no new agent specification document becomes an orphan
    that is reachable in the file system but invisible to the corpus index.
  check:       dlms/corpus/corpus-index.md contains an entry for the
               new agent's spec_doc_id AND the entry accurately reflects
               the specification document's title and doc_type.
  mandatory:   false
  governed_by: DLMS-2026-0108; corpus-index.md conventions
  notes_when_fail: >
    Corpus index update is non-blocking — a missing index entry does not
    prevent the agent from being registered and activated. However, the
    agent-creation-orchestrator must schedule the index update as a
    follow-on task within the same workflow cycle and flag the omission in
    the DoD record. A missing index entry that persists for more than 7
    days is escalated to SysAdmin.

### Attestation_Block

attestation:
  dod_id:          {value from Header FIELD_01}
  verdict:         pass | fail
  blocking_items:  list of GATE IDs where result: fail AND mandatory: true
                   (empty [] when verdict is pass)
  observations:    list of GATE IDs where result: fail AND mandatory: false
                   (empty [] when no non-mandatory gates failed)
  signed_by:       agent_id — must be agent:agent-creation-orchestrator
  signed_at:       ISO 8601 datetime

## ADVANCEMENT_RULE

A new agent class may be registered in the TypeDB roster, tool-access-registry,
and dlms-agent-roster.md if and only if:
  attestation.verdict == pass
  (i.e. attestation.blocking_items is an empty list [])

This means all six mandatory gates (GATE-01 through GATE-06) must have
result: pass. GATE-07 (corpus index update) is non-blocking and may register
as fail without preventing registration, subject to the follow-on scheduling
requirement in GATE_07.notes_when_fail.

An agent class with verdict: fail on any mandatory gate is not registered.
The agent-creation-orchestrator must return the workflow to the failed stage,
remediate the failing gate condition, and re-evaluate the DoD. Each
re-evaluation produces a new DoD record; prior records are retained as
audit evidence and must not be deleted.

## VALIDATION_RULES

V01: dod_id is non-null and matches DOD-agentcreation-{role_id}-{timestamp}.
V02: stage value is exactly "agent-creation".
V03: verdict is exactly "pass" or "fail" — no other values permitted.
V04: When verdict is "fail", blocking_items list is non-empty.
V05: When verdict is "pass", blocking_items is an empty list [].
V06: All 7 gate items are recorded — no gates may be skipped.
V07: evaluated_by is agent:agent-creation-orchestrator.
V08: approval_artefact_id in the DoD header matches the approval_artefact_id
     in the originating agent request record.
V09: signed_by matches evaluated_by.
V10: GATE-05 result is pass only when verified_by differs from the
     instruction_authored_by actor recorded in GATE-04.
